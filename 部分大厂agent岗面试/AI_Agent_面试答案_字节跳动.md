## 一、Agent 一、二面基础题

### 1. Planning 规划是 Agent 框架做的还是大模型做的？

大模型擅长根据自然语言目标拆解任务、选择工具和估计下一步；Agent 框架负责保存计划状态、检查前置条件、执行工具、控制重试和处理失败。因此规划内容可以由模型生成，但执行和约束必须由框架掌握。

简单任务用 ReAct 边想边做；复杂任务先生成任务图，再由编排器逐步执行。高风险或固定流程的关键步骤使用代码状态机，模型只做识别、补参和异常分支。

### 2. 短期记忆和长期记忆有什么区别？

短期记忆服务当前会话和当前任务，强调时效性，例如最近消息、待办、工具结果和临时变量；长期记忆跨会话复用，强调稳定性和可检索性，例如用户偏好、历史结论、业务知识和成功经验。

短期记忆使用会话状态、窗口和摘要；长期记忆使用结构化表保存事实，向量库保存可语义检索内容，并附来源、时间、权限和置信度。临时推断未经验证不能写入长期记忆。

### 3. 工具使用 MCP 还是自己写？大模型工具实现有什么好处？

MCP 适合把工具描述、参数、返回结果和服务边界标准化，便于多个 Agent 复用；自己写适合内部逻辑简单、性能要求高、协议和权限需要完全控制的场景。实际可以采用“内部 Tool Gateway + MCP 适配层”。

大模型工具调用能把语言理解和确定性执行连接起来，让模型查询实时数据、调用计算服务和推进流程。但工具不会自动变安全，仍需要 Schema、权限、超时、幂等、审计、重试和人工确认。

### 4. Self-Attention 为什么分 Q、K、V？

输入序列经过三组线性变换得到 Q、K、V：

```text
Q = XWq, K = XWk, V = XWv
Attention(Q,K,V) = softmax(QK^T / sqrt(dk))V
```

Q 表示当前位置想找什么，K 表示每个 token 具有什么可匹配特征，V 表示真正被聚合的内容。先用 Q 和 K 算相关性，再用权重加权 V；除以 `sqrt(dk)` 防止点积过大造成 softmax 饱和。

多头注意力让不同头学习不同关系。同一个 token 的词向量可以相同，但加上位置编码后输入不同，经过注意力结合上下文后，最终向量通常也不同。

### 5. Python 多线程为什么有 GIL？Lock 和 RLock 区别是什么？

CPython 的 GIL 是解释器级互斥锁，主要简化对象引用计数和内存管理。它限制多个线程同时执行纯 Python 字节码，但 I/O 阻塞、部分 C 扩展和网络等待期间可以释放 GIL，所以多线程适合 I/O 密集任务。

`Lock` 不可重入，同一线程拿到后再次 acquire 会阻塞自己；`RLock` 可重入，同一线程可以多次 acquire，但必须对应次数 release。CPU 密集型任务应考虑多进程、向量化或原生扩展。

### 6. To-Do List 为什么让模型更聚焦？如何落地？

长任务只依赖对话历史时，模型容易忘记目标、重复执行或过早结束。To-Do List 把目标拆成带状态、输入、输出和完成标准的任务，相当于外部工作记忆和进度控制器。

落地时维护结构化状态 `pending/running/done/blocked`，每次工具调用前选择当前任务，调用后更新状态；新信息可以追加或重排，任务结束做验收。要限制任务粒度、最大步骤和循环次数，不能只在 Prompt 中放一段待办文字。

### 7. Skills 的原理和底层实现是什么？

Skill 是按需加载的能力包，把领域知识、触发条件、步骤、工具规范、输入输出格式、示例和失败处理封装起来。底层通常包括：

1. Skill 描述文件和元数据，如名称、版本、触发条件、权限和依赖。
2. Registry 负责发现、版本管理和权限过滤。
3. Router/Planner 根据任务选择 Skill，并只加载相关指令。
4. Tool Executor 按 Skill 规定调用工具，执行 Schema、鉴权、重试和审计。
5. State Store 保存中间状态，Evaluator 用样例做回归。

Skill 不是简单 Prompt 模板，必须有边界、输入输出契约、工具权限、异常策略和评测集。

## 二、Agent 开发二面：架构与 Agent 设计

### 1. Agent 项目用什么架构？为什么选 LangGraph、自研、Master/Sub Agent 或 Workflow？

先按任务特征选型：固定步骤、规则明确的部分使用 Workflow/状态机；需要动态判断和工具选择的部分使用 ReAct；多个领域能力相互独立时使用 Master/Supervisor 路由到子 Agent。

LangGraph 适合快速构建有状态的图、检查点和人工介入；自研适合已有统一运行时、对性能、协议、权限和多租户隔离有要求的团队。早期优先模块化单体，只有工具隔离、独立扩缩容或团队边界确实需要时再拆多服务。

### 2. 是单体还是多工程？各 Agent 如何分工？

不按“一个 Agent 一个服务”机械拆分。可以先在一个运行时服务内隔离 Router、Planner、Retriever、Tool Gateway、Memory 和 Evaluator；存在独立扩缩容、权限边界、技术栈或团队边界时再拆工程。

分工按稳定业务能力划分，例如意图识别与路由、知识检索、数据查询、写入审批和结果校验。每个 Agent 有清晰输入输出和退出条件，Master 负责任务分解和汇总。

### 3. 首次生成和多轮补充的链路路由如何区分？

使用显式会话和任务状态，而不是只看聊天文本。状态包含 `conversation_id`、`task_id`、当前意图、已收集槽位、上次输出、待补字段、任务状态和版本。

请求进入后判断是否存在未完成任务、是否引用上轮结果、是否改变目标、是否只是确认或纠错。新任务创建新 task；补充信息合并旧 task；目标改变则关闭或挂起旧 task。路由要可回放，并使用幂等键避免重试产生重复写入。

### 4. Skills 功能原理和体系如何设计？

Skill 是按需加载的领域能力单元，包括描述、触发条件、步骤、工具、Schema、权限、样例和失败策略。启动时注册元数据；运行时 Router 选候选，结合权限和依赖加载指令，Planner 生成步骤，Executor 调工具，State Store 保存中间结果。

体系需要版本化、命名空间、依赖检查、冲突处理、超时和最大循环次数。评测集覆盖正常路径、缺字段、权限不足、工具失败和 Prompt 注入，发布前做回归。

## 三、Prompt 与上下文工程

### 5. Prompt 模板如何构建？上下文工程有哪些实践？To-Do List 为什么有效？

Prompt 分为固定规则、任务说明、动态状态、工具说明、证据和输出格式几个区域。固定规则版本化，动态信息结构化，检索结果带来源，输出尽量使用 Schema。

上下文工程的重点是选择和排序：当前任务、约束、待办和工具结果优先；旧消息摘要化；相同证据去重；外部内容标记为数据；超出 token 预算按优先级淘汰。To-Do List 通过外部状态告诉模型目标、下一步和完成条件，降低长上下文中的遗忘、重复和提前结束。

### 6. 做过查询改写吗？多维度查询改写是什么？缺信息时怎么交互？

查询改写不是简单换同义词，而是拆出意图、实体、时间、过滤条件、关键词、同义词、语言、需要字段和子问题。可以并行生成关键词查询、语义查询、过滤条件和多跳子查询，再分别检索并融合。

改写前先判断信息是否足够。缺少决定结果的字段时，返回澄清问题并保留任务状态；不影响粗召回时先做宽查询，再向用户说明不确定点。设置最大澄清次数，避免无限循环。

### 7. 什么是并行化意图识别？为什么做？如何实现？

一条请求可能同时需要识别主意图、实体、时间、风险、语言、是否需要工具和是否为多轮补充。把相互独立的判断并发执行，可以降低延迟；最后由合并器按优先级和置信度生成路由。

工程上使用异步任务或线程池并行运行轻量分类器/模型调用，设置超时和取消；合并时优先安全判断，再处理业务意图，冲突时回退到澄清。存在依赖的步骤仍然串行，并行也要控制成本。

## 四、评测与 Badcase 定位

### 8. Agent 整体效果怎么评估？没有用户反馈如何抽检？

建立覆盖各意图、难度、工具路径、无答案和安全场景的黄金集，做离线回归。没有显式反馈时，按意图、风险、低置信度、长链路、重试、耗时异常和随机样本分层抽检。

抽检保留完整 trace，用人工双审或模型辅助后再抽样复核，做 side-by-side 对比。指标包括任务完成率、答案相关性、事实一致性、引用准确率、工具成功率、人工接管率、P95 延迟和成本，不能只抽成功样本。

### 9. Badcase 如何快速定位？如何判断对哪个 Agent 做 SFT？

按 trace 判断错误发生在输入理解、路由、规划、检索、上下文、工具参数、工具执行、结果解析、最终生成还是安全策略。用相同数据和版本复现，逐层查看候选、Prompt、工具请求、返回值和状态变化。

只有问题是稳定、重复、可标注的模型行为，并且有足够高质量样本时才考虑 SFT。数据缺失、检索错误、工具不稳定、权限和 Prompt 冲突等问题不能靠 SFT 替代，先做错误分类和样本量判断。

### 10. Prompt 调优“修好一类、坏了一类”怎么办？

建立分桶回归集，记录每次改动对每类任务的增益和损失；将通用规则、场景规则和输出模板分层，按路由使用不同 Prompt；加入反例和边界条件，避免一条越来越长的指令解决冲突。

同时检查是否应该改检索、工具 Schema、模型路由或数据，而不是继续堆 Prompt。上线使用版本化、灰度和回滚，不能只看平均分。

### 11. Prompt 调到极限，优先换模型、扩参数还是 SFT？

- 知识缺失或信息不新：补 RAG、工具和上下文。
- 遵循指令但格式不稳：先改 Schema、Prompt 和解码参数。
- 通用推理、长上下文或工具规划不足：评估更强模型。
- 领域行为稳定、样本充足：考虑 SFT 或偏好优化。
- 只有少量 badcase：优先修数据和流程，不急着训练。

更大模型通常增加成本和延迟；SFT 依赖高质量、覆盖充分的数据，也可能过拟合。最终用离线分桶、线上灰度、成本和稳定性共同决定。

## 五、工程与底层基础

### 12. LLM 推理优化做过什么？Continuous Batching、KV Cache、vLLM 是什么？

Continuous Batching 让动态到达的请求共享批次；KV Cache 避免自回归生成时重复计算历史 Key/Value；Prefix Cache 复用相同系统 Prompt；vLLM 等运行时通过 PagedAttention 更高效地管理 KV Cache。还可以使用量化、批量 Embedding、模型路由和流式输出。

线上关注 TTFT、TPOT、P95 延迟、吞吐、显存、并发、错误率和单请求成本。吞吐必须说明模型、硬件、输入输出 token、并发和 batch 条件，不能脱离条件报数字。

### 13. 代码模型的分支覆盖率怎么计算？代码审核原理是什么？

分支覆盖率是测试执行到的分支数除以总分支数：

```text
branch coverage = executed branch edges / total branch edges
```

例如 `if/else` 通常有真、假两个分支，循环要考虑进入和不进入。使用 coverage.py、pytest-cov 或语言对应的插桩工具记录控制流边，再生成报告。覆盖率高不代表业务正确，还要覆盖异常、边界和断言质量。

代码审核结合 diff、AST/静态分析、类型检查、依赖和密钥扫描、单元/集成测试以及带仓库上下文的 LLM 审查。LLM 可发现逻辑问题和补测试建议，但不能代替编译、执行、权限检查和人工审批。

### 14. 单元测试的 Mock 怎么实现？AST 和 SFT 都搞不定怎么办？

Mock 的核心是依赖替换：通过依赖注入、patch 模块符号、Fake 实现或测试服务器控制外部服务返回值，并验证调用次数、参数和异常。Python 中可以用 `unittest.mock` 和 `pytest.monkeypatch`，注意 patch 的位置应是被测模块实际查找依赖的位置。

如果 AST 和 SFT 都处理不了，不能继续让模型猜。使用编译器、静态检查和沙箱执行得到客观反馈，补最小可运行样例和单元测试；复杂框架使用录制回放、契约测试和人工审查。必要时把代码拆成更小的纯函数。

### 15. Python 有真正的多线程吗？

CPython 受 GIL 影响，多个线程不能同时执行纯 Python 字节码，所以 CPU 密集型纯 Python 代码通常不能通过多线程线性加速。但 I/O 密集型任务可以并发等待网络、磁盘和数据库；NumPy 等释放 GIL 的原生代码也可能并行。CPU 密集型可以使用多进程、C/C++/Rust 扩展或向量化。

Lock 与 RLock 的区别见本文第一节第 5 题。

### 16. Self-Attention 原理以及 Q/K/V 作用

输入矩阵 `X` 经过三个参数矩阵得到 Q、K、V。用 Q 与所有 K 点积得到匹配分数，缩放后 softmax 得到权重，再对 V 加权求和。这样每个位置可以根据上下文动态聚合其他位置的信息。

Q、K、V 把查询关系和被聚合内容解耦；如果只用一个向量，匹配和内容表达会受限。相同 token 的词向量可以相同，但位置编码不同，经过注意力结合上下文后最终表示通常不同。

## 六、场景设计题

### 17. 带 TUI 的交互式视频剪辑工具 MVP 如何设计？

分层可以是：

```text
TUI/View：项目列表、时间线、快捷键、进度和错误提示
Application：命令分发、任务状态、撤销/重做、异步作业
Domain：媒体片段、时间线、裁剪/拼接/音视频轨道模型
Infrastructure：ffprobe/ffmpeg、文件系统、缓存、日志和进程管理
```

MVP 先支持导入、查看时长、标记起止点、裁剪、拼接、导出和进度。用 `ffprobe` 获取媒体信息，用 `ffmpeg` 执行裁剪和转码；长任务放 Worker，通过 stdout/stderr 解析进度，TUI 只订阅状态。项目文件保存操作历史和媒体引用，用命令模式实现撤销/重做，所有路径和参数校验，禁止直接拼接 shell 字符串。

## 七、团队与个人规划

### 18. 团队规模和分工如何？负责边界在哪？

按事实回答团队总人数、角色分工、协作方式、自己的模块和最终交付物。重点说明是否负责需求澄清、架构设计、开发、上线、指标和故障处理，而不仅是写接口；多人协作时说明接口边界和评审方式。

### 19. 作为项目负责人，如何处理里程碑、协作和阻塞？

把目标拆成可验收的里程碑和任务，给每项任务指定负责人、依赖、输入输出和截止时间，建立风险清单。同步时关注阻塞而不是只报进度；阻塞超过约定时间就升级，并给出降级方案。

每个里程碑有验收标准和可演示产物，需求变更先评估影响再重排。项目结束复盘计划偏差、质量问题和流程改进。

### 20. 为什么离开当前公司？下一份工作最看重什么？

可以说希望在更完整、更大规模的 Agent 场景中承担端到端责任，深入架构、评测、稳定性和业务结果。下一份工作看重真实问题、技术深度、团队协作、工程质量和成长空间。保持客观，不贬低当前公司，不把核心动机说成单一薪资因素。

## 八、AI Agent 秋招一面

### 1. 自我介绍

控制在 60 到 90 秒：

> 我主要关注大模型应用和 Agent 工程，做过 RAG、工具调用、上下文/记忆和任务编排相关工作。项目中负责过需求拆解、架构设计、核心链路实现和效果评测，比较关注的不只是模型能不能回答，还包括检索质量、工具安全、延迟、成本和 badcase 定位。希望继续参与真实业务场景，把 Agent 能力做成稳定可衡量的系统。

之后补充一到两个最相关项目，每个项目只讲背景、职责、难点和结果。

### 2. 项目介绍，重点介绍 AI Agent 项目

按背景、目标、架构、职责、难点和结果展开。架构要说明 Router、Planner、RAG、Memory、Tool Gateway、状态存储和评测如何连接；难点准备一个召回 badcase、工具失败或上下文超限案例；结果使用真实的准确率、召回率、任务完成率、人工耗时、延迟或成本。

不要只说用了某个框架、向量库和大模型，要说明为什么选、如何验证和失败时怎么处理。

### 3. MySQL 索引在什么情况下会失效？

常见情况：

- 对索引列做函数或表达式，如 `DATE(create_time)`。
- 隐式类型转换导致对列计算。
- 联合索引不符合最左匹配。
- 使用前导 `%` 模糊查询。
- 条件选择性低，优化器认为全表扫描更便宜。
- 索引列被计算、使用复杂负向条件或 OR 条件。
- 返回大量行或列，回表成本太高。
- 表很小，索引维护和扫描成本不划算。

通过 `EXPLAIN` 验证 possible keys、key、rows、filtered 和 Extra，不能只根据 SQL 表面判断。

### 4. LIKE 模糊查询什么时候会失效？

`LIKE 'prefix%'` 通常可以使用 B+Tree 前缀范围；`LIKE '%keyword'` 和 `LIKE '%keyword%'` 通常不能使用普通 B+Tree。函数、类型转换、排序规则、低选择性和优化器成本也可能导致全表扫描。

任意位置匹配应考虑全文索引、ngram、倒排索引或 Elasticsearch。

### 5. 消息队列在 AI Agent 系统中的作用是什么？为什么不直接用数据库？

用户请求、文档解析、Embedding、异步检索、长任务、工具事件和评测任务耗时不同。消息队列可以解耦生产者和消费者，吸收流量峰值，提供异步处理、重试、延迟消息、顺序、消费组和失败转移，也方便多个模块订阅事件。

直接用数据库会造成服务强耦合，通常需要轮询，难以处理突发流量和消费进度。数据库保存最终业务状态，MQ 传递事件；重要场景可用 Outbox 保证事务和消息一致性，消费者必须幂等。

### 6. 多模态大模型结构是什么？视觉编码器如何连接语言模型？

典型结构是视觉编码器、模态投影层和语言模型：

```text
图片/视频
  -> patch 切分与位置编码
  -> ViT/ConvNeXt 等视觉编码器
  -> 视觉特征
  -> Projector / Q-Former / MLP 映射到 LLM 隐藏维度
  -> 视觉 token 前缀或 Cross-Attention
  -> 自回归生成文本
```

视觉编码器把图像转为视觉 token；投影层解决视觉特征空间和语言模型隐藏空间的维度与分布差异。常见方式是把视觉 token 和文本 token 拼接后输入语言模型，另一类在语言层增加 Cross-Attention，让文本 token 查询视觉特征。

训练一般分阶段：先做图文对齐，再做多模态指令微调。视频还要处理时间位置编码或帧采样，音频需要声学编码器；视觉 token 数量要控制，否则会显著增加上下文和 KV Cache 成本。

### 7. Redis 在 AI Agent 系统中有哪些应用？如何设计缓存？

Redis 可用于会话状态和短期记忆、热点知识或 Embedding 缓存、查询结果、幂等键、分布式锁、令牌桶限流、任务进度以及 Pub/Sub/Streams。它适合低延迟临时状态，不应无条件替代持久化数据库。

可采用 Cache-Aside：先读缓存，未命中读源数据并写入。Key 包含租户、权限范围、数据版本和模型/索引版本，避免串数据；TTL 加随机抖动，single-flight 或分布式锁防止击穿；不存在结果做短 TTL 负缓存防穿透；更新源数据时主动失效或使用版本化 key。

Embedding 和答案缓存要考虑模型、Prompt、知识库版本和权限。敏感信息不应进入无隔离共享缓存，同时监控命中率、延迟、内存、淘汰和错误率。

### 8. RAG 为什么引入父子索引？BM25 和向量如何融合？

父子索引让小子块负责精确命中，大父块提供完整上下文；命中子块后通过 `parent_id` 取父章节，再去重、Rerank 和按 token 预算截断。

BM25 和向量并行召回，分别取候选后融合。简单方法是分数归一化加权，更稳健的方法是 RRF；融合后交给 Cross-Encoder Rerank，并根据查询类型动态调整关键词和语义权重。评测要按问题类型分桶。

### 9. ReAct 的工程实现和消息格式如何设计？

ReAct 在“判断下一步、执行工具、观察结果”之间循环。工程上要设置最大步数、超时、错误分类、重试上限和循环检测。

助手发起工具调用：

```json
{
  "role": "assistant",
  "tool_calls": [
    {
      "id": "call_123",
      "type": "function",
      "function": {
        "name": "search_orders",
        "arguments": {"user_id": "u1"}
      }
    }
  ]
}
```

工具返回：

```json
{
  "role": "tool",
  "tool_call_id": "call_123",
  "content": "{\"items\": 3, \"source\": \"order_db\"}"
}
```

内部可以记录 Thought、Action、Observation trace，但不必把完整思维过程暴露给用户。输出先做 JSON Schema 校验，再进入 Tool Gateway；工具结果限制大小、脱敏并标记来源。

### 10. Tool response 应该用什么角色？为什么？

使用 `role=tool` 并带对应 `tool_call_id`。模型可以明确区分工具执行结果、用户新指令和助手文本，并在并行调用时准确对应每个结果。若框架不支持标准角色，也要保留等价的调用 ID、工具名、状态、结果和错误字段。

### 11. Agentic CPT、SFT、RL 三阶段训练流程是什么？

- Agentic CPT：继续预训练领域语料、工具文档、代码和交互轨迹，让模型学习领域语言、任务模式和工具协议，目标仍是 next-token prediction。
- SFT：用高质量指令、规划、工具调用、观察结果和最终答案轨迹监督微调，让模型学会任务行为和输出格式；错误轨迹要过滤。
- RL：在模拟或真实环境中，以任务完成、工具成功、事实正确、成本和安全为奖励，优化多步决策；要防止奖励投机、循环和分布偏移。

CPT 补基础和领域分布，SFT 教行为范式，RL 优化交互结果。如果根因是数据、检索或工具缺失，训练不能替代系统修复。

### 12. Agent 记忆机制如何设计？短期和长期如何实现？

短期记忆放最近对话、当前任务、待办和工具结果，使用窗口、摘要和状态存储控制 token；长期记忆保存经过确认的用户偏好、稳定事实、历史结论和可复用经验，用结构化表加向量检索，并带来源、时间、权限和置信度。

写入经过抽取、去重、敏感信息过滤、冲突检测和生命周期管理；读取按任务相关性召回，不把所有长期记忆塞进 Prompt。临时计划和中间结果属于工作记忆，任务结束清理，只有经过验证且有复用价值时才沉淀。
