## 一、复盘重点

这组题横跨 Agent、LLM、后端基础和协议生态。回答时应先给结论，再给原理、边界和一个例子。遇到“你做过吗”，没有做过就直接说“没有在线上做过，但我理解其原理是……；如果实现，我会从……验证”。

## 二、问题逐题复盘

### 1. 说说对 Agent 和 LLM 的理解

LLM 是根据上下文进行概率生成的模型，本身主要负责理解和生成，不天然拥有可靠的长期记忆、实时世界状态或执行能力。Agent 是围绕模型构建的任务闭环：接收目标，维护上下文，决定下一步，调用工具，观察结果，根据结果继续、结束或转人工。

可以抽象为：

```text
目标/上下文 → 模型决策 → 工具执行 → 观察结果 → 更新状态 → 再决策
```

Agent 的工程难点不止是 Prompt，还包括工具权限、状态持久化、循环终止、超时、重试、评测和成本控制。不是所有聊天机器人都需要 Agent；如果没有外部动作、没有多步决策，普通 LLM 调用可能更合适。

### 2. Java 为什么不支持多继承，以及为什么 C++ 支持？

Java 的类不支持多继承，主要是为了避免菱形继承、成员冲突和初始化顺序复杂化，降低对象模型和语言规则的复杂度。Java 通过接口实现多类型契约；接口可以有 `default` 方法，但冲突时需要显式重写解决。

C++ 支持多继承，是因为它更强调底层能力和表达力，同时提供虚继承、显式限定、虚函数等机制处理共享基类和歧义，但代价是对象布局、构造析构、方法解析和维护复杂度更高。

不要说“Java 完全不能多继承”：Java 的类只能继承一个直接父类，但可以实现多个接口。C++ 多继承也不是“天然更好”，是能力与复杂度的取舍。

### 3. Linux 基础命令

常用命令应能说明用途和排查场景：

| 目的 | 命令示例 | 复盘要点 |
|---|---|---|
| 查看目录/文件 | `pwd`、`ls -lah`、`find` | 先确认路径和权限 |
| 查文本/日志 | `rg "keyword" file`、`less`、`tail -f` | 线上日志先按 request ID 过滤 |
| 进程/资源 | `ps aux`、`top`、`free -h`、`df -h` | 区分 CPU、内存、磁盘问题 |
| 网络 | `ss -lntp`、`curl -v`、`dig` | 看监听、连接、DNS 和响应 |
| 权限/文件 | `chmod`、`chown`、`du -sh` | 最小权限，避免随意 `sudo` |
| 进程控制 | `kill -TERM pid` 后再考虑 `kill -KILL` | 先优雅退出，保留现场 |

排查要遵循现象 → 指标 → 日志 → 复现 → 修复 → 验证的顺序，不要一上来重启导致现场丢失。

### 4. Git 的 rebase 之类高级命令

`git rebase target` 会把当前分支相对共同祖先的提交重新应用到 `target` 之上，历史更线性，但会改写提交 ID。冲突时：解决文件 → `git add` → `git rebase --continue`；想放弃用 `git rebase --abort`。

常见命令：

```bash
git fetch origin
git rebase origin/main
git rebase -i HEAD~N
git reflog
git cherry-pick <commit>
git stash push -m "wip"
git bisect start
```

公共分支不要随意 rebase 后强推；个人分支可以在确认没有他人基于它开发后使用 `--force-with-lease`。`reflog` 可以帮助找回本地引用移动前的提交，但不是永久备份。

### 5. HTTP 和 TCP 的区别，抓包有做过吗？

TCP 是传输层协议，提供面向连接、可靠、有序的字节流，通过序列号、确认、重传、流量控制和拥塞控制工作。HTTP 是应用层协议，规定请求、响应、方法、状态码、Header 和 Body，通常运行在 TCP 之上；HTTP/3 则基于 QUIC/UDP。

抓包时要明确问题：连接没建立、TLS 失败、服务端慢、响应体错误还是客户端解析错。工具可以用浏览器 DevTools、`curl -v`、Wireshark、tcpdump 或服务端 access log。抓包可能涉及隐私和密钥，生产环境要遵守脱敏和权限要求。

如果没有真实抓包经历，可以说：

> 我没有独立负责过复杂线上抓包，做过的主要是用 `curl -v` 和浏览器 Network 看请求链路；对于更底层的 TCP 重传，我会用 Wireshark/tcpdump 按连接四元组和时间线分析，而不会把 HTTP 日志当成 TCP 抓包。

### 6. HTTP 和 HTTPS 的区别，加密的过程

HTTPS 是 HTTP over TLS。TLS 主要提供机密性、完整性和服务器身份认证。简化流程是：客户端发送支持的版本和密码套件，服务端返回选择结果和证书；客户端校验证书链、域名和有效期，双方通过密钥交换得到会话密钥；后续应用数据用对称加密传输，并带完整性保护。

实际 TLS 1.3 的握手细节和密钥派生不能用 TLS 1.2 的旧流程混说。面试时应说明“这是简化描述，具体取决于 TLS 版本和密码套件”。HTTPS 不等于业务一定安全，证书校验、Cookie 属性、鉴权、重放防护和服务端权限仍然重要。

### 7. WebSocket 长连接和 SSE

WebSocket 通过 HTTP Upgrade 建立持久的双向连接，客户端和服务端都可以主动发送消息，适合双向实时协作、在线状态和交互式 Agent 控制。需要处理心跳、断线重连、连接数、背压、鉴权和消息顺序。

SSE 是基于 HTTP 的服务端到客户端单向事件流，客户端通常用 `EventSource` 接收 `text/event-stream`，天然适合模型流式输出、通知和日志推送。客户端要主动发消息时仍需另外调用 HTTP API。

选择时看通信方向和基础设施：单向推送优先 SSE，双向低延迟交互考虑 WebSocket。两者都是长连接，都需要代理超时、断线恢复、事件 ID 和资源上限设计。

### 8. DNS 解析

典型解析路径是：应用/浏览器缓存 → 操作系统缓存 → 本地递归 DNS → 根域名服务器 → 顶级域名服务器 → 权威 DNS，递归服务器按 TTL 缓存结果。最终得到 A/AAAA、CNAME 等记录，再建立连接。

排查 DNS 问题时使用 `dig domain`、`dig +trace domain`，对比不同 DNS、IPv4/IPv6 和 TTL；同时区分 NXDOMAIN、超时、解析到错误地址和地址可达但服务异常。DNS 负载均衡受缓存和 TTL 影响，修改记录不会保证所有客户端立即生效。

### 9. Redis、并发系统

Redis 常见用途是缓存、分布式锁、计数、限流、短期会话和任务队列。缓存要考虑穿透、击穿、雪崩、一致性和热 Key；锁要有唯一 token、过期时间、释放校验，不能只用 `DEL key` 删除别人的锁。

并发系统要先明确共享资源和不变量，再选互斥、CAS、队列、数据库唯一约束或事务。高并发 Agent 场景还要关注模型限流、工具并发上限、重复执行和背压。Redis 不是万能的强一致数据库，不能在没有确认持久化、故障转移和一致性要求的情况下承诺绝对不丢数据。

### 10. OpenAI 协议，新版旧版的区别是否知道？

稳妥回答是：

> 我了解常见的演进方向，但不敢把某个 SDK 版本的字段当成永久标准。旧式接口通常围绕 `messages` 的聊天补全组织请求；较新的 Agent/Responses 类接口会更强调统一响应对象、工具调用、结构化输出、流式事件和多模态内容。具体字段、模型兼容性和弃用时间要以当前官方文档及项目依赖版本为准。

复盘时重点掌握接口抽象，而不是死背 JSON：输入内容、模型决策、工具调用、工具结果、最终输出、usage、错误和流式生命周期。迁移时要检查工具 schema、消息格式、流式事件、上下文/缓存语义、重试和观测字段，不能只改一个 endpoint 名称。

### 11. Anthropic 的协议知道不知道？

可以回答其核心概念：请求通常包含模型、系统指令、消息内容、生成上限等；工具调用会经历模型提出工具请求、应用执行工具、应用回传工具结果、模型继续生成的闭环；流式模式会以事件流返回增量内容和结束事件。

但不同 SDK 和版本的字段名可能不同，不能把 OpenAI 的消息结构直接套过去。`[不确定]` 对某个具体版本的 prompt caching、extended thinking、computer use 或流式事件字段，如果没有实际查过文档，应明确说“我知道能力方向，但不确认该版本的精确字段”。

### 12. MCP

MCP 可以理解为连接模型应用与外部工具/资源/提示的协议化方式。典型参与者包括 Host、Client 和 Server：Host 管理会话与用户权限，Client 连接 Server，Server 暴露工具、资源或提示，模型应用根据协议发现和调用它们。

安全重点是工具最小权限、服务端来源、参数校验、用户确认、审计、超时、返回内容大小和提示注入防护。MCP 能统一连接方式，但不会自动保证工具安全、结果正确或任务幂等。

`[不确定]` 对具体版本的 transport、capability 字段和 SDK API 不要凭印象回答；可说“我掌握角色和调用生命周期，具体协议字段需要结合面试项目版本确认”。

### 13. Skill 加载机制

Skill 可以看成按需加载的能力说明或操作规程，通常包含名称、适用范围、输入输出、约束、工具使用方法和示例。加载机制应避免把所有 Skill 全塞进上下文，可以先用元数据做匹配，命中后再读取详细指令。

一个可靠流程是：注册 Skill → 元数据检索/路由 → 加载指令 → 校验权限和依赖 → 执行 → 记录版本与结果。要防止 Skill 描述冲突、恶意指令、版本漂移、上下文过长和工具越权。Skill 是“如何做”的知识，不应替代权限系统和程序校验。

### 14. Agent 循环机制

Agent Loop 通常是：读取目标和状态 → 生成下一步动作 → 校验动作 → 调用工具 → 观察结果 → 更新状态 → 判断完成/失败/继续。循环必须有最大步数、deadline、Token/费用预算、重复动作检测和终止条件。

伪代码：

```text
while not terminal:
    if deadline_exceeded or budget_exceeded: stop
    action = model.decide(state)
    validate(action)
    if action.type == FINAL: return action.answer
    result = tool.execute(action, timeout=step_timeout)
    state = state.append(action, result)
    if repeated_or_invalid(state): replan_or_escalate()
```

不要把模型返回 `done=true` 直接当作成功；最终结果应通过工具、规则或测试验收。

### 15. PDF 处理逻辑

先判断 PDF 是文本型、扫描型还是混合型，再决定解析路径。文本型提取文字、页码、标题和表格；扫描型先 OCR；表格/图片需要保留坐标和页码；复杂版面要做分块、去页眉页脚和结构恢复。

随后进行清洗、分段、元数据标注和索引。问答场景要保留来源页码，生成答案时要求引用证据。需要处理加密、乱码、超大文件、重复页、表格错位和 OCR 误识别。不能只看“抽出了文字”就认为处理正确，应抽样对比原页并设置解析失败转人工的分支。

### 16. Claude Code 怎么用

可以从工程协作角度回答：先让工具读取项目约束和目标，再让它分析而不是直接大改；将任务拆成小步，要求先写/运行测试，再修改；使用版本控制查看 diff；对命令执行、文件修改和外部访问保留审查边界。

它适合辅助理解代码、生成测试、定位问题和迭代实现，但不能替代人工 code review，也不能把它声称执行过的命令当作真实证据。`[需替换]` 如果你实际使用过，应补充具体场景；没用过时可说“我了解这类 coding agent 的工作方式，但没有把它作为项目主流程使用”。

### 17. cc 开源、OpenClaw、DeepSeek Harness 等热点是否了解

这类题的正确重点不是抢着背项目名，而是说明自己如何判断：看官方仓库/文档、许可证、提交活跃度、架构、工具权限、评测结果、部署成本和安全问题。不同项目名称可能存在同名、改名、版本变化或社区二次包装。

稳妥回答模板：

> 我听过这个方向，但没有在生产环境使用，不能确认它当前版本的所有实现细节。我的理解是它们都在探索 Agent 编排、工具调用或 Harness 工程化；如果要评估，我会重点看状态管理、循环控制、工具沙箱、可观测性、评测和失败恢复，而不是只看 Demo。
