# 蚂蚁 AI-Agent 开发秋招一面：问题与参考答案

> 来源：用户提供的“蚂蚁 AI-Agent 开发秋招一面经”截图。共 24 题，覆盖 Agent 架构、记忆/RAG、模型参数、MySQL、Redis、消息队列、缓存、算法和反问。个人项目、团队规模和指标必须按真实经历填写。

## 一、Agent 架构与工程

### 1. 自我介绍

用“背景 → Agent 相关项目 → 我的职责 → 结果 → 求职动机”讲 60~90 秒。重点说亲自设计或实现的模块，例如路由、RAG、Tool Gateway、状态机、评测或上线运维；不要把团队成果全部说成个人成果。

### 2. 最有代表性的项目/实习产品

按业务痛点、用户流程、系统架构、关键技术、个人贡献和结果展开。建议画出“请求 → 路由 → 规划 → 检索/工具 → 状态 → 校验 → 输出”的链路，并准备一个失败案例：当时的现象、定位过程、改动和指标变化。没有真实数据就明确说明统计口径尚未建立。

### 3. 除了该项目外还参与过哪些项目？

按相关性选择一到两个，突出可迁移能力：后端服务、数据/检索、模型调用、稳定性或团队协作。每个项目只讲目标、负责边界、难点和结果，不要堆技术名词。

### 4. 为什么用 Markdown 做记忆管理？相比 RAG 有什么考虑？

Markdown 适合人可读、可审查、可版本控制的任务记忆：计划、决策、约束和阶段总结都能直接 diff，调试和迁移成本低。RAG 更适合大规模、跨文档的事实检索，支持权限过滤、向量/关键词召回和增量索引，但需要解析、切片、Embedding、召回评测和一致性治理。

两者不是互斥关系：用 Markdown/结构化文件保存小规模任务工作记忆，用数据库或向量库保存长期事实；在线把相关片段检索进上下文。Markdown 不能替代并发控制、权限和原子写入；多实例部署要使用版本号、文件锁或对象存储，避免覆盖。

### 5. 记忆更新如何保证语义匹配准确？匹配错误如何处理？

更新前先做事实抽取、规范化和去重，保存 `memory_id、内容、来源、时间、作用域、置信度、版本`。召回时结合关键词/向量相似度、实体和时间过滤；高风险记忆要求证据或用户确认。写入后做 Schema、冲突和敏感信息校验。

匹配错误时不要静默覆盖：标记候选为低置信度，回读原文或向用户澄清；冲突保留多个版本并按来源、新鲜度和可信度决策，支持撤销和过期。线上监控误召回、漏召回、人工修改率和记忆删除请求。

### 6. 为什么采用 Agent Teams？相比 Workflow 的优势？

Agent Teams 适合任务专业边界明显、需要并行探索或不同权限的场景；每个 Agent 有独立工具、上下文和输出契约，Supervisor 负责分解、汇总和终止。优势是专业化、并行和故障隔离。

Workflow 适合步骤稳定、合规要求高、验收条件明确的流程，状态和重试更可控。Teams 的代价是协调消息、上下文同步、成本、冲突和失败传播。实际常用混合架构：确定性步骤用 Workflow，模糊子任务交给受限 Agent。

### 7. 线上要求全流程自动化、不依赖人工审核，如何保证稳定和可靠？

自动化不等于取消约束。为每个任务定义输入/输出 Schema、完成条件、最大步数、deadline、token/费用预算和降级路径；工具经网关鉴权、参数校验、限流、超时、重试、幂等和审计。高风险动作即使默认自动，也要采用最小权限、沙箱、可回滚事务和事后对账。

上线前用黄金集、故障注入和回放测试覆盖无答案、模型异常、下游 5xx、重复消息和 Prompt 注入；线上监控任务完成率、错误率、P95 延迟、成本和异常分布，灰度发布并保留一键回滚。

### 8. 一个 Agent 调用多个工具，如何设计整体流程并管理顺序？

先把工具声明为带输入输出 Schema、依赖和副作用级别的能力。Planner 生成 DAG 或结构化步骤；无依赖的查询并行，有依赖的步骤串行，写操作放在证据和校验之后。Executor 为每步保存状态、attempt、幂等键和结果摘要。

步骤失败按错误类型处理：瞬时错误有限重试，参数错误回到模型补参，权限错误直接终止或澄清，业务冲突进入补偿/人工队列。全局设置预算和循环检测，最终由程序检查实际结果而不是只看模型文本。

### 9. 大模型调用外部工具的底层机制？如何决定调用哪个工具？

服务端先把工具名称、描述、参数 Schema 注入模型请求；模型返回结构化 `tool_call(name, arguments, call_id)`，网关校验并执行，再以带 `call_id` 的 tool message 返回结果，模型据此继续或结束。模型选择依赖工具描述、当前目标、上下文和策略 Prompt；真正的可用工具集合还要经过租户、角色和风险策略过滤。

为提高选择准确率，工具描述写清适用/不适用场景和示例，减少重叠；候选多时先用规则或小模型路由，再让大模型补参。对高风险工具要求确认和二次校验。

### 10. Agent 系统通常由哪些核心模块组成？

接入与鉴权、会话/任务状态、意图路由、Planner/Policy、LLM Gateway、Tool Registry/Gateway、RAG/Rerank、短期/长期记忆、执行器、工作流/队列、结果验收、安全权限、观测评测和成本计量。模块边界应通过结构化协议连接，模型不直接操作数据库或 shell。

### 11. 如何理解短期记忆和长期记忆？实现方式？

短期记忆是当前会话/任务的消息、计划、待办、工具结果和临时变量，放在状态存储或缓存中，用窗口、摘要、TTL 控制；长期记忆是跨会话仍有复用价值的偏好、稳定事实和经验，使用结构化数据库保存事实、向量索引支持语义召回，并带来源、时间、权限、置信度和删除机制。

长期记忆必须经过筛选、去重、冲突检测和隐私过滤，不能把模型猜测直接写入。两类记忆都要支持版本、过期和回放。

### 12. MCP 是什么？解决什么问题？

MCP（Model Context Protocol）是一种把模型与外部工具、资源和提示模板连接起来的开放协议，统一能力发现、参数 Schema、调用和结果传递。它降低了每个 Agent 为每个工具单独写适配器的成本，便于工具复用和权限治理。

MCP 不等于安全层或业务编排器；服务端仍要做鉴权、租户隔离、输入校验、超时、审计和幂等。生产环境还要锁定协议/SDK 版本，限制可访问资源并防止 Prompt 注入通过工具返回结果传播。

### 13. Agent Harness 包含哪些关键能力？为什么企业级 Agent 需要？

Harness 提供任务状态机、上下文组装、工具网关、预算/超时/循环控制、重试与恢复、人工审批、沙箱、观测 trace、评测、版本和回滚。企业场景任务长、工具有副作用、涉及权限和合规，单靠模型循环无法保证可审计、可恢复和成本可控，因此需要 Harness 把模型决策包在工程约束内。

### 14. Skill 懒加载如何实现？为什么需要？

启动时只注册 Skill 的名称、摘要、触发条件、版本、权限和依赖；路由选出候选后，按需读取完整指令、Schema、示例和工具清单，执行结束释放或缓存。这样可以减少首轮 token、降低干扰和冷启动成本，也便于按权限隔离。

懒加载要处理版本锁定、依赖缺失、加载失败、缓存失效和冲突；Skill 文本不能绕过系统权限，工具网关必须再次校验。用命中率、加载延迟和任务成功率评估是否值得缓存。

## 二、模型参数与数据库/中间件

### 15. Temperature、Top-k、Top-p 含义及影响

Temperature 在 softmax 前缩放 logits，越低越确定，越高越随机；Top-k 只保留概率最高的 k 个 token；Top-p（nucleus）保留累计概率达到 p 的最小候选集合。Temperature 控制整体随机度，Top-k/Top-p 控制候选截断，三者叠加时需用评测集调参。结构化抽取通常低温并固定随机种子，创意生成可适当提高。

### 16. Temperature=0 为什么仍可能有差异？

Temperature=0 通常表示近似贪心，不保证严格确定性。差异可能来自并列 logits 的 tie-break、服务端动态批处理、量化/硬件非确定性、MoE 路由、系统 Prompt/检索结果变化、工具返回时间和随机采样实现。要提高稳定性，固定模型和 Prompt 版本、检索排序、工具结果、种子（若服务支持），使用 Schema/规则校验，并对关键结果做重试和一致性检查。

### 17. MySQL 事务 ACID

- **Atomicity 原子性**：事务中的操作全成功或全回滚；
- **Consistency 一致性**：提交后满足约束和业务不变量；
- **Isolation 隔离性**：并发事务按隔离级别互不产生不允许的中间影响；
- **Durability 持久性**：提交结果在崩溃恢复后仍存在。

InnoDB 通过 undo/锁/MVCC/redo 等机制实现这些性质；隔离级别越高通常并发代价越大。ACID 不能替代跨服务一致性，跨服务要用 Outbox、Saga 或补偿。

### 18. redo log、undo log、binlog 的作用和区别

`redo log` 是 InnoDB 的物理/页级重做日志，采用 WAL 保证崩溃恢复和持久性；`undo log` 保存旧版本，用于回滚和 MVCC 一致性读；`binlog` 是 Server 层的逻辑变更日志，服务于主从复制和增量恢复。三者记录粒度、归属和用途不同。

提交涉及 redo/binlog 的协同（常说“两阶段提交”）以避免已提交事务在两份日志中不一致。binlog 不是回滚依据，undo 也不是复制日志。

### 19. Redis 缓存穿透、击穿、雪崩及方案

- **穿透**：请求不存在的数据，缓存和数据库都查不到。用参数校验、布隆过滤器、空值短 TTL 和限流。
- **击穿**：某个热点 key 过期瞬间大量请求打到数据库。用互斥锁/single-flight、逻辑过期、热点不过期和预热。
- **雪崩**：大量 key 同时过期或 Redis 故障。用 TTL 随机抖动、多级缓存、限流/熔断/降级、集群和预案。

### 20. 消息队列如何保证消息不丢？生产端/消费端需要什么保障？

生产端开启持久化与确认（ack），发送失败重试但使用幂等消息 ID；数据库与消息需一致时采用 Outbox/本地消息表。Broker 做副本、刷盘和合理的 min in-sync replicas。消费端先完成业务处理再 ack，失败重试并进入死信队列；消费者以业务唯一键或去重表保证幂等。

“至少一次”通常意味着可能重复；“恰好一次”需要端到端事务/幂等语义而非只依赖 MQ 参数。监控积压、重试、死信和消费延迟。

### 21. 分布式缓存如何设计和应用？

采用 Cache-Aside：读先查缓存，未命中读源并写入；更新源数据后主动删除/版本化 key，必要时延迟双删。Key 带租户、权限、数据版本、模型/索引版本；TTL 加抖动，single-flight 防击穿，空值防穿透，热点预热。

缓存只放可重建或可接受短暂不一致的数据；重要状态仍持久化。跨地域要明确一致性和故障切换，敏感数据必须隔离加密。监控命中率、内存、淘汰、延迟、回源 QPS 和错误率。

### 22. 限流、熔断、降级分别解决什么问题？

限流控制进入系统的请求速率，防止过载（令牌桶可允许突发）；熔断在下游连续失败或变慢时暂时停止调用，避免级联故障；降级是在资源不足或依赖不可用时返回缓存、简化结果、异步受理或转人工。三者通常配合：限流保护入口，熔断隔离故障，降级维持核心可用。

## 三、算法题

### 23. 有 n 个会议，给出开始和结束时间，如何判断一个人能否参加完所有会议？

若一个人只能同时参加一个会议，按开始时间排序，检查相邻会议是否满足前一个结束时间 `<=` 后一个开始时间；只要出现重叠就不能参加完。端点是否相等按题意决定，通常 `[start, end)` 下相等可以衔接。

```python
def can_attend_all(meetings: list[tuple[int, int]]) -> bool:
    meetings = sorted(meetings, key=lambda x: x[0])
    for (prev_s, prev_e), (cur_s, cur_e) in zip(meetings, meetings[1:]):
        if prev_e > cur_s:
            return False
    return True
```

时间复杂度 O(n log n)，空间复杂度 O(n)（若允许原地排序可降到 O(1) 额外空间）。若题目改成求最少会议室，则使用按开始排序 + 最小堆维护结束时间。
