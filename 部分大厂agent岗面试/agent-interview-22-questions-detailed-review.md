## 一、先建立一个统一的回答框架

这 22 道题看似分散，实际上都在考 Agent 能不能从 Demo 变成可靠系统。回答时可以按下面的顺序组织：

1. 先定义概念，避免把框架、协议、策略和业务系统混为一谈；
2. 说明核心数据流和状态如何变化；
3. 解释失败、超时、权限、成本和评测怎么处理；
4. 最后补自己的项目事实；没有做过就明确说“我理解原理，但没有在线上负责过”。

一个通用 Agent 链路可以抽象成：

```text
用户目标
   │
   ▼
任务路由 / 风险判断
   │
   ├──简单任务──> 直接回答
   │
   ▼
规划或决策 ──> 工具/子 Agent 执行 ──> 观察结果
   ▲                                      │
   └────────状态更新、校验、重试、重规划──┘
                  │
                  ▼
           完成 / 澄清 / 人工确认 / 失败
```

不要把模型输出的“已完成”当成真实完成。真实完成通常需要程序化验收：文件确实存在、测试确实通过、数据库状态确实变化、引用确实存在，或者用户明确确认。

## 二、Agent Loop、Harness 与安全

### 1. Agent Loop 的双循环怎么设计，外循环和内循环分别负责什么？

#### 核心结论

“双循环”不是一个所有框架都统一规定的术语。工程上常见的解释是：

- 外循环负责一个任务或计划的生命周期；
- 内循环负责某个阶段中的模型决策、工具调用和观察。

也有系统把外循环称为“规划循环”，把内循环称为“单步 ReAct 循环”。面试时最好先说清楚自己的定义。

#### 一种可落地的设计

**外循环**面向任务级状态：

- 创建任务、读取任务状态和 deadline；
- 生成或修订计划；
- 选择下一个步骤；
- 控制全局预算、最大步骤数和人工审批；
- 处理步骤成功、失败、超时、取消和恢复；
- 在所有步骤完成后做最终验收。

**内循环**面向步骤级执行：

- 把当前步骤、相关上下文和工具描述交给模型；
- 获得结构化动作；
- 校验动作和参数；
- 执行工具或子 Agent；
- 把工具结果作为 observation 写回状态；
- 判断本步骤是否完成，或需要继续调用工具。

伪代码如下：

```python
while not task.is_terminal():
    enforce_deadline_and_budget(task)

    step = scheduler.next_step(task)
    if step is None:
        return verifier.final_check(task)

    while not step.is_terminal():
        action = model.decide(build_step_context(task, step))
        policy.check(action, task.identity)

        if action.type == "finish_step":
            step.mark_succeeded(action.summary)
            break

        result = tool_runner.execute(
            action,
            timeout=step.remaining_timeout(),
            idempotency_key=f"{task.id}:{step.id}:{step.attempt}"
        )
        step.append_observation(result)

        if should_stop_inner_loop(step, result):
            break

    recover_or_replan_if_needed(task, step)
```

#### 两个循环之间要共享什么

需要共享任务 ID、步骤 ID、当前计划版本、预算、权限上下文、产物引用和 trace ID；但不应把所有历史原文无限复制到每一轮 Prompt。状态存储和 Prompt 上下文应分离。

#### 常见坑

- 内外循环都让模型决定是否结束，造成互相等待或无限循环；
- 只有“成功/失败”两个状态，无法表示等待审批、未知状态和恢复中；
- 工具超时后直接重试，没有确认外部副作用是否已经发生；
- 只限制内循环步数，没有限制总 Token、总金额和总时间；
- 计划不断被修改，却没有计划版本和审计记录。

#### 面试中的稳妥说法

> 我把双循环理解成任务级编排循环和步骤级执行循环。外循环负责计划、状态和恢复，内循环负责当前步骤的决策、工具调用和观察。具体项目是否严格采用这个命名，要以代码结构为准；如果项目只有一个循环，我不会为了贴概念强行说成双循环。

### 2. Agent 的权限控制怎么做？如何约束 Agent 对高风险操作的行为？

#### 核心原则

Prompt 不是安全边界，模型说“我有权限”也不代表真的有权限。权限必须在模型之外由服务端、策略引擎和运行时强制执行。基本原则是：最小权限、默认拒绝、显式授权、可审计、可撤销。

#### 建议分成六层

1. **身份层**：确认用户、租户、Agent 身份和调用来源；
2. **能力层**：给 Agent 分配有限的工具集合，而不是全量工具；
3. **资源层**：限制能访问哪些文件、表、项目、用户和环境；
4. **参数层**：限制金额、路径、数量、时间范围、域名和数据范围；
5. **运行时层**：沙箱、网络出口控制、文件系统隔离、CPU/内存/时间预算；
6. **审批与审计层**：高风险操作先预览，得到用户或人工批准后执行，并记录证据。

可以将操作分级：

| 风险级别 | 例子 | 推荐策略 |
|---|---|---|
| 低 | 查询公开资料、读取允许的项目文件 | 自动执行，限制范围 |
| 中 | 修改代码、创建文档、发送测试请求 | 沙箱执行，展示 diff 或预览 |
| 高 | 删除数据、付款、生产发布、发送外部消息 | 二次确认/审批，强幂等和审计 |
| 不允许 | 绕过权限、窃取凭证、访问未授权数据 | 直接拒绝并记录 |

工具服务端要重新校验权限，不能只依赖模型生成的参数。例如文件删除工具应该检查调用者是否拥有目标文件、路径是否在允许根目录内、是否存在幂等键，并在执行前返回预览。

#### 高风险操作的推荐链路

```text
模型提出动作
  → 参数和权限校验
  → 生成影响预览 / dry-run
  → 用户或审批人确认
  → 带幂等键执行
  → 查询结果并记录审计
```

#### 常见误区

- 把“系统提示词里写禁止删除”当作权限控制；
- 给所有 Agent 一个万能 shell 或数据库账号；
- 只校验工具名，不校验参数中的 URL、路径和资源归属；
- 没有区分只读工具与有副作用工具；
- 高风险工具支持自动重试，却没有幂等和状态查询。

### 3. Agent 的上下文管理，怎么做压缩和裁剪的？Claude Code 怎么做的？

#### 先区分三种东西

- **持久化状态**：任务、计划、文件、工具结果和审计记录，应该放在数据库、对象存储或工作区；
- **会话历史**：用户和 Agent 的可追溯对话，通常可以长期保存，但不必每次全部放进 Prompt；
- **当前上下文**：本轮模型真正看到的内容，需要严格控制 Token、相关性和顺序。

上下文管理的目标不是单纯“尽量塞满窗口”，而是在有限预算下保留对当前决策最有用的信息。

#### 压缩方法

1. **尾部保留**：保留最近几轮对话，适合当前指代和未完成任务；
2. **摘要压缩**：将较早历史压成目标、已确认事实、已完成步骤、未决问题和约束；
3. **结构化状态**：把计划、变量、错误、文件列表、测试结果放成 JSON 或表格，而不是自然语言长段落；
4. **检索式恢复**：只有当当前任务需要时，按实体、文件、步骤或时间检索历史；
5. **工具输出裁剪**：保留状态码、关键字段、错误摘要和产物引用，大日志放文件；
6. **代码/文档分块**：只放相关函数、调用链和 diff，避免把整个仓库重复塞进上下文；
7. **上下文分层**：稳定规则、任务状态、当前输入、工具结果和参考资料分开管理。

#### 裁剪时不能只按长度

可以综合新近性、相关性、任务依赖、来源可靠性、是否为用户明确约束和是否为未完成事项。用户刚确认的约束通常比一段旧的模型推测更重要。压缩后最好保留来源或原文引用，避免摘要把假设写成事实。

#### Claude Code 具体是怎么做的

这里要把“能从产品行为/CLI 看到的事实”和“没有公开的内部算法”分开。根据本机安装的 Claude Code `2.1.207` 的 CLI 帮助、可观测命令字符串和配置项，Claude Code 的长会话上下文管理大致是下面这条链路：

```text
项目/用户规则加载
  ├─ CLAUDE.md / .claude/rules
  ├─ Skill、插件、MCP 能力元数据
  └─ 当前工作目录与附加目录
          │
          ▼
按需读取文件、搜索代码、调用工具
          │
          ▼
工具结果、对话历史、计划和模型输出进入当前会话上下文
          │
          ├─ /context：查看上下文使用情况
          ├─ /compact：主动压缩旧对话和工具结果
          └─ 自动压缩：接近可用上下文上限时生成摘要并继续会话
          │
          ▼
会话持久化 / --continue / --resume / --fork-session
```

**第一层：上下文不是“整个仓库一次性上传”。** Claude Code 从当前工作目录开始，通过文件读取、Glob/Grep、编辑和命令执行工具按需获得代码和结果；`--add-dir` 可以把额外目录加入本次会话的可访问工作区。项目规则通常通过 `CLAUDE.md`、`.claude/rules` 等加载。`--bare` 模式会跳过 CLAUDE.md 自动发现、插件、Hooks、MCP 等定制化加载，因此它更适合需要显式提供上下文的最小化运行，而不是日常项目开发。

**第二层：工具结果会持续占用会话上下文。** 本机版本的提示中明确提醒：MCP 工具结果会在当前会话剩余时间里留在上下文中；如果工具返回大日志、长网页或大段 JSON，后面每一轮都可能受到影响。实际优化不能只压缩用户对话，还要限制工具输出：分页、摘要、只返回关键字段，把完整内容写入文件并在 Prompt 中传文件路径或引用。

**第三层：自动压缩不是简单删除最早几条消息。** Claude Code 会在上下文使用量接近配置的自动压缩窗口时，对会话做压缩摘要，再把摘要作为后续会话的历史基础。当前版本的提示说明，自动压缩窗口取“配置值”和“模型最大上下文窗口”中的较小者；可以在配置中调整自动压缩，也可以用环境变量 `CLAUDE_CODE_AUTO_COMPACT_WINDOW` 覆盖配置。`/compact` 适合在进入大规模工具调用或长代码修改前主动触发，并可以附带压缩重点，例如要求保留当前目标、约束、已修改文件、测试结果和未解决问题。

**第四层：自动记忆与会话压缩是两条不同链路。** 自动压缩解决“本次会话上下文快满了”；自动记忆解决“以后会话是否值得保留某些经验”。本机版本提供 `autoMemoryEnabled` 配置，并支持关闭自动记忆；二进制中也能看到默认的项目相关记忆目录、`MEMORY.md` 和 `/memory` 入口。适合写入记忆的是稳定的项目事实、用户偏好、常用命令和经过验证的排障结论，不适合写入一次性的模型猜测、密钥和未经确认的敏感信息。

**第五层：会话持久化与上下文压缩也不是一回事。** `--continue` 用于继续当前目录最近的会话，`--resume` 用会话 ID/名称恢复会话，`--fork-session` 可在恢复时创建新的会话 ID，`--no-session-persistence` 则禁止保存会话，后者的会话不能恢复。也就是说，压缩后的摘要、原始会话记录和自动记忆可能属于不同的存储/生命周期，不能把“能 resume”理解成“模型永远保留了全部原始上下文”。

**第六层：缓存优化依赖稳定前缀。** 本机 CLI 提供 `--exclude-dynamic-system-prompt-sections`，其说明是将工作目录、环境信息、记忆路径和 Git 状态等机器相关内容从系统 Prompt 移到首条用户消息，以提高跨用户 Prompt Cache 的复用率。工程上可以据此理解为：稳定的系统规则、工具目录和项目指令应尽量保持前缀一致；时间戳、随机 ID、动态日志和变化频繁的工具结果应放在后面。具体缓存命中率、缓存块边界和 Claude Code 服务端的实现没有完全公开，不能把它说成“每次都能命中 KV Cache”。

**第七层：压缩有保护机制，但不是万能恢复。** 本机版本包含自动压缩反复触发/快速重新填满上下文的告警逻辑，提示开发者减小单次读取或使用 `/clear`；这说明长会话治理还需要从源头控制工具输出，而不是无限依赖压缩。如果一个工具每次返回整个构建日志，压缩后下一轮又马上塞满，问题在工具输出策略，不在摘要不够聪明。

#### 面试推荐回答

> Claude Code 不是把整个仓库永久放在 Prompt 里，而是以当前工作目录为边界，通过 Read、搜索、编辑和命令工具按需读取内容。对长会话，它有会话级上下文、工具结果、自动压缩和自动记忆几层机制：`/compact` 或自动压缩负责把旧对话和工具结果归纳成摘要，`CLAUDE.md`/Skill/记忆文件负责跨任务提供规则和经验，`--continue`/`--resume` 负责恢复会话。MCP 工具返回的大结果会持续占用本次上下文，所以需要分页、摘要和文件引用。至于内部摘要模型、精确触发阈值、缓存块边界和自动记忆的完整写入策略，我没有把它们当成公开确定事实，具体要以当前版本官方文档和部署配置为准。

#### 这段回答中不要说错的地方

- 不要说“Claude Code 会自动把整个仓库建成向量库并持续检索”；是否使用索引、如何检索取决于具体功能和版本；
- 不要说“压缩后原始消息一定完全可恢复”；压缩的目的恰恰是用摘要替代部分历史上下文；
- 不要说“工具结果只在当前一轮有效”；MCP 大结果可能持续占用当前会话上下文；
- 不要把自动记忆、`CLAUDE.md`、会话 JSON 和 Prompt Cache 说成同一个存储系统；它们承担不同职责；
- 不要给出未经核实的默认 Token 阈值、摘要模型、缓存命中率或内部目录结构。

#### 资料与核验边界

- Claude Code 官方文档入口：[Memory](https://code.claude.com/docs/en/memory)、[CLI usage](https://code.claude.com/docs/en/cli-usage)、[Settings](https://code.claude.com/docs/en/settings)、[MCP](https://code.claude.com/docs/en/mcp)；
- 官方代码仓库：[anthropics/claude-code](https://github.com/anthropics/claude-code)；
- 本次复盘还核对了本机 Claude Code `2.1.207` 的 `claude --help` 和本地可执行文件中的版本相关提示。由于当前运行环境访问 Anthropic/GitHub 外部站点失败，上述官方页面链接作为面试前复核入口保留；涉及精确版本、默认值和内部实现时，应以当日能打开的官方文档为准。

#### 验证压缩是否损失信息

准备一组长任务回归集，比较压缩前后：关键约束记忆率、文件定位准确率、工具参数正确率、任务成功率、Token、延迟和错误类型。上下文压缩不是越激进越好。

### 4. 什么是 Harness？讲讲思想，还有 Agent 中怎么去实现？

#### 定义

Harness 可以理解为围绕模型构建的“运行时骨架”或“控制平面”。它不等于模型，也不只是一个 Prompt 模板，主要负责让模型能力在真实系统里可执行、可约束、可恢复、可观测。

典型职责包括：

- 会话和任务状态；
- 计划/工作流编排；
- 工具注册、发现和调用；
- 权限、沙箱和审批；
- 超时、重试、取消、恢复和幂等；
- 上下文组装、摘要和预算；
- 事件、日志、trace、指标和成本统计；
- 结果验收、人工介入和版本发布。

#### 一个最小 Harness 的模块

```text
Task API
  ├─ Session / State Store
  ├─ Planner / Router
  ├─ Context Builder
  ├─ Policy Engine
  ├─ Tool Registry + Tool Runner
  ├─ Loop Controller / Scheduler
  ├─ Checkpoint + Recovery
  ├─ Verifier
  └─ Trace / Metrics / Audit
```

#### 实现思路

先定义统一的任务和步骤状态，再定义工具契约和事件模型。模型只返回结构化动作，例如 `call_tool`、`ask_user`、`finish_step` 或 `replan`；Harness 校验动作后才执行。每一次状态变化写入事件或 checkpoint，外部副作用必须带幂等键。

对不同任务可以复用同一个执行器，只替换计划、Skill、工具和验收器。这样 Prompt 可以迭代，底层状态和安全能力仍然稳定。

#### Harness 与 workflow 的区别

Workflow 通常强调业务流程节点和依赖；Harness 更强调 Agent 运行时的动态决策、工具边界、上下文和恢复。两者可以组合：固定流程由 workflow 编排，节点内部由 Harness 承载 Agent Loop。

### 5. 如果 MCP 工具（Skill）过多，如何让 Agent 检索效率更高？调用工具的准确性更高？工具过多怎么优化上下文窗口占用？

#### 不要把所有工具完整 schema 一次性暴露

工具太多会造成三类问题：模型选择困难、工具描述占用上下文、相似工具导致参数混淆。推荐采用“分层发现 + 动态加载”：

1. 只注入工具目录摘要：名称、领域、用途、风险级别和关键词；
2. 先由路由器根据用户任务召回少量候选 Skill；
3. 对候选工具加载完整 schema、示例和约束；
4. 调用前做权限和参数校验；
5. 调用后只将结构化结果和必要证据回传。

#### 提升检索和调用准确率

- 工具命名采用稳定的领域/动作/对象层级，减少同义名称；
- 描述写“何时使用、何时不要使用、必填参数、失败语义”，不要只有一句口号；
- 给工具做标签、输入输出类型、权限、成本和副作用分类；
- 先做意图/领域路由，再做工具选择；
- 用工具 schema 和服务端校验限制参数，不依赖示例；
- 对高风险工具要求预览和确认；
- 通过离线任务集评估工具选择准确率、参数准确率、无效调用率和重复调用率；
- 相似工具建立互斥规则或统一入口，让服务端再路由到具体实现。

#### 上下文优化

可以将工具信息拆成三层：

| 层级 | 内容 | 进入时机 |
|---|---|---|
| 目录层 | 工具名、领域、简短用途、风险 | 常驻或按会话缓存 |
| 能力层 | 输入输出、约束、失败码、示例 | 路由命中后加载 |
| 执行层 | 当前参数、结果、证据 | 调用前后临时加入 |

Skill 文档也应拆成元数据、主流程、参考资料和示例。大段帮助文本放外部文件，模型按需读取。工具结果要分页、摘要或落盘，不要把几十万行日志直接塞回上下文。

### 6. 有没有对 Token 的消耗做过一定的优化？怎么做的？

先把 Token 分成输入、输出、工具描述、工具结果、历史对话和重试消耗，建立每次任务的成本账单。没有账单就无法判断优化是否有效。

常见优化手段：

1. **Prompt 分层**：稳定规则与动态内容分开，减少重复拼接；
2. **历史摘要**：只保留当前任务所需事实和未决事项；
3. **工具动态加载**：先目录召回，再加载少量完整 schema；
4. **结果压缩**：工具返回摘要、ID、状态和引用，大内容写文件；
5. **结构化状态**：计划、变量和错误使用短字段，而不是重复解释；
6. **限制输出**：给不同步骤设置合理的最大输出长度，要求先给结论和证据；
7. **模型路由**：分类、提取、校验等简单任务使用更低成本模型；
8. **减少无效重试**：对参数错误、权限错误和不可重试业务错误不重复调用；
9. **缓存**：缓存稳定的系统前缀、检索结果、工具元数据和确定性工具结果；
10. **批处理/并行**：对可并行的独立小任务合并请求，但要控制并发和上下文大小。

需要同时看 Token、延迟、缓存命中率、任务成功率、工具错误率和最终成本。只压缩 Token 导致准确率下降，不算有效优化。

### 7. CLI 和 MCP 之间有什么区别？你怎么做选型的？

#### 先说本质

- **CLI** 是面向用户或脚本的命令行交互界面，通常通过进程、标准输入输出、退出码和文件传递信息；
- **MCP** 是面向模型应用与外部能力之间的协议化连接方式，强调工具/资源/提示的发现、调用和会话能力。

两者不是完全互斥的技术。一个 MCP Server 可以在内部调用 CLI；一个成熟 CLI 也可以被 Harness 包装成 MCP Tool。

| 维度 | CLI | MCP |
|---|---|---|
| 主要调用者 | 人、脚本、CI | Agent Host/模型应用 |
| 接口形态 | 命令、参数、stdout/stderr、退出码 | 结构化能力发现、工具调用、资源/事件 |
| 优势 | 调试直观、生态成熟、适合自动化 | 对 Agent 统一、可发现、可结构化 |
| 风险 | 参数解析、文本输出不稳定、进程管理 | 协议/权限/会话复杂，工具暴露面变大 |
| 适合 | 本地开发、一次性运维、CI | 多工具 Agent、跨语言集成、受控能力平台 |

#### 选型标准

- 只需要人工或 CI 调用，CLI 足够；
- 需要让多个 Agent 发现并调用结构化能力，考虑 MCP；
- 已有稳定 CLI 且不想重写，可先做 MCP 适配层；
- 高风险操作不能因为使用 MCP 就自动放权，仍需独立权限和审批；
- 看调用延迟、并发、流式事件、错误语义、部署位置、版本管理和审计。

### 8. MCP 网关和传统的后端网关有什么区别？需要多关注什么问题？

#### 功能定位

传统后端网关主要处理服务到服务或客户端到 HTTP API 的路由、鉴权、限流、负载均衡、熔断、协议转换和观测。MCP 网关除了传输层能力，还要处理面向 Agent 的能力发现、工具/资源注册、会话、schema、工具结果和模型可调用边界。

两者可以叠加：MCP 网关负责协议适配和工具治理，传统 API Gateway 负责后端服务网络治理。不要把 MCP 网关理解成天然安全的“万能 API 网关”。

#### MCP 网关更需要关注的风险

1. **工具暴露面**：哪些工具对哪个 Agent、用户和租户可见；
2. **提示注入**：工具返回的文本、网页和文件可能携带恶意指令；
3. **数据外泄**：模型可能把敏感上下文作为参数发给外部工具；
4. **权限传递**：区分用户权限、Agent 权限、工具服务账号权限；
5. **参数与资源校验**：防 SSRF、路径穿越、越权 ID、超大请求和危险命令；
6. **副作用治理**：幂等键、dry-run、审批、补偿和审计；
7. **会话和状态**：连接生命周期、断线重连、事件顺序、取消传播；
8. **可靠性**：超时、限流、熔断、背压、隔离和降级；
9. **版本兼容**：工具 schema、能力声明和服务端版本变化；
10. **可观测性**：记录调用者、工具、参数摘要、结果摘要、耗时、成本和错误。

一个安全边界是：MCP 网关只负责“是否允许调用”，工具后端仍要对资源归属和业务权限做最终校验。

### 9. Agent 出现幻觉的话，怎么优化？

先区分幻觉类型，不同问题不能都靠改 Prompt：

- **事实幻觉**：生成了没有证据的事实；
- **来源幻觉**：引用了不存在或不支持结论的来源；
- **工具幻觉**：调用不存在的工具、参数或字段；
- **状态幻觉**：声称完成了实际上没有完成的动作；
- **计划幻觉**：计划步骤依赖不存在或无法执行；
- **记忆幻觉**：把旧信息、错误摘要当成当前事实。

治理方法：

1. 让模型区分事实、推断和不确定项；
2. 对知识型问题使用检索，并要求保留来源和页码；
3. 对实时状态使用工具查询，不用模型记忆；
4. 使用结构化输出和 schema，服务端校验字段；
5. 对文件、代码、数据库和任务结果做程序化验收；
6. 设置拒答、澄清和人工确认路径；
7. 让高风险动作采用预览—确认—执行；
8. 建立按类型分桶的幻觉评测集和 Badcase 闭环。

“降低幻觉”不能只看回答是否流畅，应看事实准确率、引用支持率、工具参数正确率、错误动作率和人工抽检结果。

## 三、缓存、工具加载与 Agent 评测

### 10. 如何提升 Agent 的缓存命中率？渐进式加载工具或技能会不会导致 KV 缓存失效？

#### 先区分缓存层

- **业务缓存**：缓存用户无关且可复用的业务查询结果；
- **检索缓存**：缓存 query embedding、召回结果和 rerank 结果；
- **工具元数据缓存**：缓存 Skill 描述、schema 和版本；
- **HTTP/API 缓存**：缓存稳定的 GET 或资源响应；
- **Prompt/prefix/KV cache**：推理服务复用相同前缀已经计算过的中间状态。

这些缓存的命中条件不同，不能把业务缓存命中率等同于 KV cache 命中率。

#### 提升命中率的方法

1. 固定稳定前缀的顺序、格式和版本；
2. 把不稳定的时间、随机 ID、动态日志放到后面；
3. 共享系统指令、工具目录和公共规则，减少无意义差异；
4. 对查询、权限和资源变化设置正确的 cache key；
5. 对工具 schema 做版本化，避免无关字段频繁变化；
6. 对缓存设置 TTL、容量、租户隔离和敏感信息策略；
7. 监控命中率、命中 Token、节省成本、失效原因和错误复用。

#### 渐进式加载与 KV Cache 的关系

一般的 prefix/KV cache 只在前缀 Token 完全一致、模型和相关推理配置兼容时复用。渐进式加载工具会改变 Prompt 中的工具描述或工具 schema，因此**变化点之后**的缓存通常不能直接复用；变化点之前的稳定前缀是否仍能命中，要看推理服务的缓存实现和 Prompt 拼接顺序。

例如：

```text
[稳定系统指令][稳定公共规则][动态工具列表][用户问题]
```

如果动态工具列表放在中间，它后面的用户问题位置也随内容变化，后半段更难复用；如果公共前缀稳定、动态工具放在靠后位置，通常更有利于复用稳定前缀。但这不是对所有服务的绝对保证。

工具“渐进式加载”还可能提高整体成本收益：单次请求的工具描述少了，虽然某些 KV 前缀需要重新计算，但输入 Token 和工具选择错误可能下降。应该通过实验比较总 Token、TTFT、缓存命中 Token、工具准确率和任务成功率。

此外，工具结果本身通常不会自动成为下一次请求的 KV cache；它需要作为新的上下文进入下一次推理。具体 prefix cache 语义依赖模型服务实现。

### 11. 怎么评估 Agent 效果的好坏？Agent 上线之后遇到过什么问题？

#### 评估维度

**任务效果**：任务成功率、最终验收通过率、步骤成功率、用户目标完成率。

**决策效果**：路由准确率、计划合理性、工具选择准确率、工具参数正确率、无效/重复调用率。

**知识质量**：事实准确率、引用支持率、检索召回率、拒答准确率。

**工程质量**：首 Token 延迟、总延迟、P95/P99、错误率、超时率、重试率、并发、吞吐和可用性。

**成本质量**：输入/输出 Token、工具成本、模型成本、单任务平均成本、缓存节省量。

**安全质量**：越权调用率、敏感信息泄露、提示注入成功率、危险动作拦截率和人工审批率。

#### 评测方法

- 离线固定集：正常、边界、长上下文、工具失败、多轮补充和对抗样例；
- 程序化验收：文件、测试、数据库状态、引用和 schema；
- 人工 rubric：相关性、完整性、事实性、可解释性和安全性；
- LLM-as-a-judge：作为辅助并做校准和人工抽检；
- 灰度发布：按用户/流量/任务类型切分，设置回滚阈值；
- 线上抽检：重点抽低置信度、高成本、高延迟、异常重试和高风险任务。

#### 常见线上问题

- 平均延迟正常，但工具超时导致 P99 很差；
- 数据或工具版本变化，离线评测通过但线上召回/参数失败；
- 上下文增长使 Token 成本和模型响应时间逐步上升；
- 重试缺少幂等键，导致重复写入或重复发送消息；
- 用户输入、网页或工具返回内容触发提示注入；
- 依赖服务限流、连接池耗尽、事件流断线；
- 模型升级后某一类 Prompt 变好，另一类回归；
- 日志没有保存 Prompt、模型、Skill、工具和状态版本，无法复盘。

`[需替换]` 面试中如果被问“遇到过什么问题”，要填真实案例：现象 → 定位 → 修复 → 结果 → 后续防护。没有线上事故可以说开发阶段遇到过什么，不能把假设事故说成真实经历。

### 12. 场景类问题：让你设计一个写 PPT 的 Skill，你会怎么设计？

#### 先定义输入输出

输入：主题、受众、页数、时长、语言、品牌规范、参考资料、交付格式和是否允许使用外部素材。

输出：PPT 文件、页面结构、素材引用、生成日志、渲染预览、校验报告和未解决问题列表。

#### Skill 的分层设计

1. **需求澄清**：确认主题、受众、风格、页数、素材和验收标准；
2. **内容规划**：生成叙事主线、章节、每页目的和讲述要点；
3. **素材检索**：读取用户文件、图表和图片，保留来源和版权信息；
4. **页面设计**：为每页选择版式、标题、正文、图表、图片和备注；
5. **生成文件**：调用受控的 PPT 生成工具或模板系统；
6. **渲染检查**：生成缩略图或 PDF，检查溢出、重叠、字号、颜色和空白；
7. **语义检查**：核对页数、标题层级、数字、引用和图表数据；
8. **修订闭环**：根据检查结果修改特定页面，重新渲染和验收。

流程可以是：

```text
需求 → 大纲 → 页面 spec → 资产与数据 → 生成 → 渲染
                                      ↑       │
                                      └─校验/修订
```

#### 页面 spec 示例

```json
{
  "page": 3,
  "purpose": "解释问题与方案关系",
  "layout": "two-column",
  "title": "...",
  "elements": [
    {"type": "text", "content": "...", "max_lines": 5},
    {"type": "diagram", "nodes": [], "edges": []}
  ],
  "sources": ["file:requirements.pdf#page=4"],
  "acceptance": ["no-overflow", "source-checked"]
}
```

#### 工程注意点

- Skill 只描述能力流程，真正的文件写入和网络访问由工具权限控制；
- 大图片、PDF 和 PPT 不能全部放进 Prompt，使用文件引用和中间产物；
- 生成必须可重试，页面级产物和版本要保存；
- 视觉检查不能只靠模型描述，至少要实际渲染后检查；
- 数据和引用必须可追溯；
- 需要防止用户资料中的提示注入影响工具权限。

面试时可以补充：`[需替换]` 你实际使用的 PPT 生成库、模板系统、渲染工具和验收指标。

## 四、记忆、协作、RAG 与自进化

### 13. 开放类问题：Pi Agent 的设计哲学、DeepSeek Harness 的设计哲学？不同 Agent 之间的区别、优势？

#### 先说明信息边界

“Pi Agent”和“DeepSeek Harness”可能指不同仓库、文章、内部项目或社区版本，单凭题目无法确定唯一对象。没有给出仓库链接、版本或具体实现时，不应该把某个印象说成官方架构。面试时可以先确认：

> 您指的是哪个仓库或版本？这两个名称在社区里可能有不同指代。我可以先从设计取舍比较，再结合具体实现回答。

#### 可以比较的设计维度

| 维度 | 轻量 Agent 取向 | Harness/平台取向 |
|---|---|---|
| 核心目标 | 小而清晰的 Agent Loop、易扩展 | 生命周期、工具治理、恢复和运维 |
| 抽象重点 | 消息、工具、扩展、用户控制 | 状态机、调度器、策略、观测、评测 |
| 优点 | 学习成本低、调试直观、改造快 | 适合长任务、多人/多租户和线上稳定性 |
| 代价 | 复杂任务需要自己补基础设施 | 组件多、约束多、维护成本高 |
| 适用 | 本地 coding、实验、单用户任务 | 企业 Agent、生产流程、平台化能力 |

如果题目中的 Pi Agent 确实强调轻量、可组合和用户可控，那么它的优势通常是核心机制容易理解、扩展路径清楚；如果 DeepSeek Harness 指的是面向复杂任务的运行时，它可能更关注计划执行、工具调用、状态和评测。但这些是**设计取向的推断**，不是对具体项目内部实现的确认。

#### 如何评价不同 Agent 的优势

不要只比“谁更强”，要按任务看：

- 单轮简单任务：延迟和上下文成本更重要；
- 长任务：恢复、checkpoint、预算和可观测性更重要；
- 多 Agent：通信协议、共享状态和冲突处理更重要；
- 高风险任务：权限、审批、审计和幂等更重要；
- 快速实验：扩展性、可调试性和改动成本更重要。

### 14. Agent 的长期记忆和短期记忆怎么设计？长期记忆存在冲突怎么办？

#### 短期记忆

短期记忆服务当前会话或任务，内容包括最近对话、当前目标、计划、工具结果、临时变量、未完成事项和错误。它不一定要永久保存，但任务恢复需要可靠状态。

存储可以使用会话状态表、缓存或任务数据库；大文件、代码和日志放对象存储，Prompt 只保留引用和摘要。

#### 长期记忆

长期记忆跨会话复用，适合稳定的用户偏好、项目事实、已确认规则和经验。每条记忆应带：

```text
memory_id
subject / scope
content
source
created_at / updated_at
confidence
authority
expiry
privacy / consent
```

向量数据库适合语义召回，但不负责最终事实判断；关键事实仍可存关系数据库、文档库或知识图谱，并保留来源。

#### 冲突解决

不要简单地“最新覆盖一切”。可以按以下顺序处理：

1. 判断是否同一实体、同一作用域和同一时间范围；
2. 比较来源权威性和是否为用户明确确认；
3. 比较时间、新鲜度和置信度；
4. 对无法自动解决的冲突保留多个版本，并向用户澄清；
5. 将纠正写成新事实，同时标记旧记忆失效，而不是物理删除所有审计；
6. 让用户查看、修改和删除自己的长期记忆。

例如用户偏好可能更新，法律/财务规则却不能只按“最近说过”覆盖权威文档。长期记忆还需要租户隔离、隐私控制、过期和防提示注入。

### 15. Agent 的历史记忆怎么做淘汰策略？

要先区分“从 Prompt 中移除”和“从持久化存储删除”。为节省上下文而淘汰，不等于数据删除；审计和合规数据通常需要独立保留策略。

#### 常用淘汰策略

- **TTL**：临时上下文到期清理，适合 session、验证码和短期缓存；
- **LRU**：长期未访问的记忆优先移出，简单但不理解语义重要性；
- **按重要性**：保留用户明确约束、任务依赖、权威事实和未完成事项；
- **按新近性与频次**：近期且多次被使用的记忆优先；
- **按作用域**：任务级结束后清理，项目级长期保留，用户级需授权；
- **摘要替代**：多轮对话压成阶段摘要，保留最近窗口和未决问题；
- **容量/成本淘汰**：按 Token、磁盘、向量索引和查询成本设上限；
- **冲突淘汰**：旧事实被明确纠正后标记失效，避免继续召回。

#### 对对话历史的实用策略

```text
保留：最近 N 轮 + 当前任务约束 + 未完成事项 + 关键工具结果
压缩：更早的对话、重复解释、已完成步骤、长日志
外置：完整文件、原始日志、审计事件、引用资料
删除：超过保留期且无合规/恢复价值的数据
```

每次摘要应经过结构化检查：目标、约束、已完成、未完成、决策、来源和风险不能丢。淘汰后通过长上下文回归集验证任务成功率，而不是只看 Prompt 变短。

### 16. 如果有多个 Agent 进行协作，不同 Agent 之间的通信是怎么做的？

常见通信方式有四种：

1. **直接消息**：Supervisor 把结构化任务发给子 Agent，适合简单委派；
2. **共享状态/黑板**：多个 Agent 读写任务状态，适合共享计划和中间结果，但要处理并发；
3. **共享产物**：代码、文件、报告和数据放工作区/对象存储，消息只传引用；
4. **事件总线**：通过事件通知状态变化，适合异步、长任务和解耦。

生产系统通常组合使用：消息传任务，状态库存状态，产物库保存大内容，事件总线传生命周期事件。

#### 通信契约

每条消息至少包含：

```text
message_id
task_id / parent_task_id
sender / receiver
type
schema_version
payload_ref
deadline
reply_to
idempotency_key
```

内容应区分任务请求、进度、结果、错误、审批和取消。不要让 Agent 之间只传自由文本；自由文本可作为解释，但系统决策依赖结构化字段。

#### 代码 Agent 与审查 Agent 示例

代码 Agent 输出分支或 diff 引用、修改文件、测试命令和结果；审查 Agent 读取需求、diff 和测试产物，返回严重级别、文件位置、复现条件和是否通过。审查失败后只把结构化问题发回代码 Agent，超过修复轮数转人工。

要防止两个 Agent 同时改同一个文件，可以用任务分支、文件所有权、锁、补丁合并和冲突检测。通信失败、重复消息和子 Agent 超时都要有重试/取消/降级策略。

### 17. RAG 怎么做分片？向量数据库的选择、原理？了解 GraphRAG 吗？

#### RAG 基本链路

```text
文档解析 → 清洗 → 分块 → 向量化/索引
用户问题 → 查询改写 → 召回 → 过滤/重排
→ 拼接证据 → 生成答案 → 引用与事实校验
```

#### 分片策略

不能只按固定字符数切。要结合文档结构和使用场景：

- 普通说明文档：按标题、段落和语义边界切；
- 长章节：使用父子块，检索小块，返回其父章节上下文；
- 表格：保留表头、行列关系、单位和页码；
- 代码：按文件、类、函数和调用关系切，保留语言和路径；
- PDF：保留页码、坐标、标题、图片/表格引用；
- 对话：按主题和阶段切，避免把无关轮次混在一起。

块太小，语义不完整；块太大，召回不精确且浪费上下文。块大小、重叠、Top-K 和重排模型都应通过评测集调，不应照抄一个固定数字。

#### 向量检索原理

Embedding 模型把文本映射为向量；查询向量与文档向量用余弦相似度、点积或距离函数比较，取 Top-K 结果。向量数据库通常还提供 ANN 索引、元数据过滤、分区、更新、删除和持久化。

#### 向量数据库选型维度

- 数据规模和向量维度；
- QPS、延迟和召回率；
- 是否需要混合检索、过滤、全文搜索和重排；
- 数据更新频率、一致性和删除语义；
- 多租户、权限、备份、容灾和运维成本；
- 部署形态、语言 SDK、生态和预算。

实际系统常用混合检索：关键词/倒排召回精确术语，向量召回语义相似内容，再用 reranker 综合排序。向量库不是越大越好，索引参数和数据质量同样重要。

#### GraphRAG

GraphRAG 在文档实体、关系、社区或事件基础上构建图，再用图遍历、结构化查询和向量检索回答关系复杂的问题。它适合“人物—组织—事件—时间”“实体间多跳关系”“全局主题总结”等场景。

代价是实体/关系抽取、图构建、更新和错误传播成本更高。简单 FAQ 不一定需要 GraphRAG。面试中应说明自己是否实际使用过；只了解原理时不要声称做过线上图谱。

### 18. Agent 的自进化、自我学习了解吗？

先区分几个概念：

- **在线适应**：根据当前上下文改变行为，不改变模型参数；
- **记忆积累**：把确认过的事实/经验写入长期存储；
- **策略优化**：通过轨迹、反馈和评测改 Prompt、路由、工具选择或工作流；
- **模型训练**：用数据做 SFT、偏好优化或强化学习，改变参数；
- **自我修改**：Agent 自己改代码、工具或权限，这属于高风险自动化。

生产环境更推荐受控的离线闭环：

```text
线上 trace/反馈
  → 脱敏与筛选
  → Badcase/成功样本集
  → 离线评测
  → Prompt/路由/工具/模型实验
  → 人工审查与安全测试
  → 灰度/可回滚发布
```

不建议让 Agent 在生产中无门槛修改自身 Prompt、工具权限或模型参数，否则容易发生错误累积、数据污染、奖励投机、提示注入和不可回滚。

如果做“自我学习”，需要记录样本来源、反馈可信度、版本、评测结果和回滚点；学习结果必须先经过离线集和安全集验证。`[不确定]` 如果题目指某个具体 Agent 框架的 self-evolution 模块，应结合其仓库版本回答，不能把一般设计当成项目事实。

### 19. Agent 的可观测怎么做？都做了什么？

#### Trace 设计

以一次用户请求为根 Trace，下面拆 Span：

```text
request
├─ route
├─ plan
├─ context_build
├─ llm_call
├─ tool_call
├─ child_agent_run
├─ verifier
└─ final_response
```

每个 Span 至少记录 task/run/agent/step ID、模型和 Prompt 版本、Skill/工具版本、输入输出摘要、Token、耗时、状态、错误、重试和成本。敏感原文应脱敏或只保留 hash、引用和权限范围。

#### 指标

- 任务成功率、步骤成功率、人工介入率；
- 工具选择/参数错误率、重复调用率、拒绝率；
- TTFT、总延迟、P50/P95/P99、超时率；
- 输入/输出 Token、缓存命中率、单任务成本；
- 上下文长度、压缩次数、重规划次数；
- 失败类型分布、模型版本回归、租户/任务分桶表现；
- 安全拦截、越权尝试、提示注入检测结果。

#### 日志与事件

日志用于排查细节，指标用于趋势和告警，事件用于任务状态和异步恢复。需要保存计划版本、工具参数摘要、外部请求 ID 和产物引用，才能重放或复盘。日志必须考虑隐私、密钥、用户文件和提示注入内容，不能为了“可观测”而无限采集原始数据。

#### 告警和验证

为高风险任务设置成功率、长尾延迟、工具错误、成本和安全告警；上线前用 trace 回放和离线回归，线上用灰度、抽检和自动回滚。可观测不是把日志打满，而是让问题可以定位到模型、Prompt、上下文、工具、网络或业务数据。

### 20. 模型的 Temperature、Top-k、Top-p 有什么用？

这些参数控制生成时从候选 Token 中采样的范围，但不同厂商/模型是否支持、默认值和实现细节可能不同。

- **Temperature**：调整概率分布的尖锐程度。较低通常更稳定、确定性更强；较高通常更多样，但也可能增加跑偏和幻觉。它不是“智能程度”参数。
- **Top-k**：只在概率最高的 K 个 Token 中采样。K 越小候选越窄，K 越大候选越多；并非所有 API 都开放该参数。
- **Top-p / nucleus sampling**：从累计概率达到 p 的最小候选集合中采样。p 越小通常更保守，p 越大更开放。

工程上不要同时随意调所有参数，否则难以知道改动原因。可以按任务设置：

| 任务 | 常见方向 |
|---|---|
| 工具调用、结构化输出、代码修复 | 低 Temperature，优先保证格式和稳定性 |
| 检索问答 | 低到中 Temperature，要求证据约束 |
| 头脑风暴、文案变体 | 适度提高 Temperature 或 Top-p |
| 严格确定性任务 | 尽量低采样，并配合程序校验 |

低 Temperature 也不保证事实正确；高 Temperature 也不等于更有创造力。若 API 不支持某参数，传参可能被忽略或报错，应查对应模型文档。工具 Agent 还应通过 schema、状态机和验收来控制行为，不能只靠采样参数。

### 21. `AGENT.md` 和 SKILL 文件的区别？

这个问题存在命名差异：有的工具使用 `AGENTS.md`，有的项目可能自定义 `AGENT.md`；它们不是全行业统一协议。回答时应先确认具体 Harness 的约定。

在常见 Agent 开发约定中，可以这样区分：

| 文件 | 作用 | 加载方式 | 内容示例 |
|---|---|---|---|
| `AGENT.md` / `AGENTS.md` | 项目或目录级工作规则 | 通常按目录层级自动发现，较长期生效 | 构建命令、代码规范、目录边界、测试要求 |
| `SKILL.md` | 某项能力的操作规程 | 按任务/能力匹配后按需加载 | PDF 处理、PPT 生成、数据库查询、部署流程 |

可以把前者理解为“在这个工作区做事必须遵守的环境约束”，把后者理解为“遇到某类任务时如何完成的能力说明”。一个 Skill 可能依赖项目级 Agent 指令，但不能绕过权限系统。

好的分工是：

- Agent 指令保持短、稳定、可审查；
- Skill 聚焦一个能力，声明触发条件、输入输出、工具、限制和验收；
- 大参考资料按需读取，不全部常驻上下文；
- 文件指令不等于授权，工具服务端仍要校验权限；
- 版本化 Skill，记录本次任务使用的版本，便于复盘。

如果面试官问的是某个特定产品的 `AGENT.md` 语义，应按该产品文档回答；不要把其他 Harness 的约定直接套用。

### 22. Plan-and-Execute 和 ReAct 的区别？怎么选择？

#### ReAct

ReAct 是“思考/决策—行动—观察”的交替过程。模型根据当前观察决定下一步，路径灵活，适合步骤较少、目标不完全明确、需要动态探索的任务。

优点：

- 不必预先规划全部步骤；
- 对工具结果和环境变化反应快；
- 实现相对简单。

风险：

- 可能循环、重复调用或目标漂移；
- 长任务中上下文不断增长；
- 难以提前展示计划和估算成本；
- 失败恢复边界不清。

#### Plan-and-Execute

先生成结构化计划，再由执行器逐步执行、验收，必要时有限重规划。适合步骤较多、有依赖、可定义验收标准和失败代价较高的任务。

优点：

- 计划可展示、审查和持久化；
- 步骤状态、重试和恢复更清晰；
- 可以并行无依赖步骤并做预算；
- 便于多 Agent 分工和阶段验收。

风险：

- 初始计划可能错误或过时；
- 多一次规划调用，增加延迟和 Token；
- 计划粒度不合适会限制灵活性；
- 如果无限 re-plan，反而变成不可控循环。

#### 对比表

| 维度 | ReAct | Plan-and-Execute |
|---|---|---|
| 决策时机 | 边观察边决定 | 先规划再执行 |
| 适合任务 | 短任务、路径不确定 | 长任务、多依赖、可验收 |
| 首次响应 | 通常更快 | 通常多一次规划 |
| 可观测性 | 需要额外记录 | 计划天然可观察 |
| 恢复能力 | 需要自行设计 | 适合 checkpoint 和状态机 |
| 主要风险 | 循环和漂移 | 计划错误和重规划成本 |

#### 实际选择

不要把它们当成二选一。可以采用混合方案：入口做轻量计划；稳定步骤由 workflow 执行；步骤内部用 ReAct 处理工具结果；失败时只重规划受影响的子图。选择依据是任务长度、路径稳定性、是否需要用户确认、失败代价、延迟、成本和评测结果。

面试中的总结回答：

> ReAct 更像局部闭环决策，Plan-and-Execute 更像任务级规划和执行。短、动态、低风险任务我倾向 ReAct；长、多依赖、需要恢复和审计的任务我倾向 Plan-and-Execute；实际工程会用状态机、验收器和有限重规划把两者组合起来。
