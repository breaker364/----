## 一、学业与毕业论文

### 1. 毕业是否有论文发表要求？

如实回答学校和实验室的要求即可：是否有硬性要求（几篇、什么级别）、自己目前的进度。注意两点：不要夸大到“已中顶会”却讲不出细节；如果暂无产出，也不要只说“没有要求”，补一句自己的工作什么时候能形成投稿，体现节奏是可控的。

### 2. 毕业论文的研究方向、创新点和数据指标优势

建议按固定结构讲 90 秒左右：一句话定义研究问题 → 现有方法的不足（创新点的靶子，没有这一句创新点就立不住）→ 2~3 个创新点，每个落到具体机制而不是口号 → 实验设置（数据集、基线、指标）→ 指标优势（“在 X 数据集上比 baseline 提升 Y%”）→ 当前进度。

准备时给自己压三层追问：这个创新点为什么有效、怎么验证是它带来的提升（消融）、什么场景下会失效。答不出第三层通常会被认为理解不深。

## 二、项目与模型训练

### 3. 项目 1 的核心创新点与提升的指标

框架：一句话项目背景和你的角色 → 对比对象（baseline 是什么方法）→ 核心创新点（机制层面，例如新的数据构造方式、奖励设计、Agent 结构），控制在 2~3 个，宁少而深 → 指标提升（说清口径：“任务成功率从 X% 提到 Y%，工具调用格式错误率下降 Z%”）。不要把团队成果全说成个人贡献，追问分工时要能拆清。

### 4. 是否进行了模型微调？纯 SFT 还是也做了 GRPO？

按真实情况回答。如果是“SFT 冷启动 + GRPO 强化”的组合，可以这样讲两者分工：SFT 用高质量轨迹做行为克隆，解决工具调用格式、基本策略和输出风格；GRPO 在此之上做强化，同一 prompt 采样一组 rollout，用组内奖励的均值当 baseline 算相对优势，不需要额外的 critic 网络，适合奖励可验证（RLVR）的场景。相比 PPO，它省掉价值网络、实现简单，代价是组内奖励方差小时梯度信号弱、样本利用率低。

如果没实际做过微调，就诚实说没有，但要能讲清上面这层区别，并补一句“如果做，我会先用 SFT 把格式和基本工具调用跑通，再上 GRPO 优化结果指标”。

### 5. 与纯 SFT 相比，GRPO 带来了多少提升？

个人数据题，必须用自己实验的真实数字。建议讲清三个维度：哪个指标提升（最终任务成功率、工具调用 F1、格式合规率）、提升多少（“从 X% 到 Y%，+Z pt”）、提升来自哪里（探索出了 SFT 轨迹之外的正确路径、格式奖励让输出更稳定、多轮自我纠错变多）。顺带能说清反方向的问题更可信：GRPO 之后哪些指标没动甚至变差（例如回答长度变长、通用能力波动），以及怎么处理的。

### 6. 训练用的什么显卡？多少张？

个人配置题，按真实情况说：卡型号和显存（A100/A800/H800/4090 等）、张数、模型尺寸、并行方式、训练时长。回答时能带上量级判断最可信：7B 全参 SFT 在 bf16 下参数加梯度加 AdamW 状态约 84GB，单张 80G 放不下，一般 4~8 张 A100 用 ZeRO-2/3 或 FSDP 分片；LoRA 可以降到 1~2 张。GRPO 还要在线采样，训练和 rollout（vLLM）通常分卡，开销明显大于纯 SFT。面试官真正想确认的是你真的跑过，所以说得清 batch size、梯度累积和有效 batch 怎么算，比报一个大的卡数更加分。

### 7. 奖励函数如何设计的？有没有满意或创新的设计？

按层次讲清结构：

- **结果奖励**：任务是否真正完成——单元测试通过、答案精确匹配、规则判分或判分模型打分，权重最高；
- **格式奖励**：工具调用是否合法（Schema 校验、参数完整）、思考/行动结构是否正确，主要用于训练早期稳住格式；
- **过程奖励**（如有）：关键步骤命中、中间状态正确性；
- **惩罚项**：重复动作、死循环、超长输出、无效工具调用、超时。

满意的设计可以讲两类，都属于防 reward hacking：一是格式分与结果分分离，并在训练后期对格式权重做退火，避免模型停在“刷格式”的局部最优；二是奖励要有区分度——GRPO 里组内 rollout 全对或全错时优势为 0、没有梯度，所以对部分完成的任务给部分分，让大多数组能产生有效信号。能讲出这个细节基本能证明真的训过。

### 8. 如何判断模型收敛？主要看 Loss 还是轮数？

结论先行：主要看验证集指标和 reward 曲线，训练轮数只是预算上限，loss 是辅助信号。

- SFT 阶段：train/eval loss 都进入平台、eval 指标不再提升即收敛，注意过拟合（train 降 eval 升）；
- RL 阶段：policy loss 本身波动大、趋近 0 也不代表收敛，不直观。真正看的是：平均 reward 平台化、固定 eval 集上的任务成功率、回复长度和 entropy 是否稳定（防止长度爆炸或塌缩成模板）、与参考模型的 KL 偏移是否受控。

实践做法是每个 checkpoint 在固定评测集上跑分，选最优 checkpoint 而不是最后一个，配合早停。

## 三、Agent 范式与项目实践

### 9. 介绍做过的 Agent 相关工作

个人经历题。建议按“项目 → 你负责的边界 → 关键技术决策 → 结果”组织，优先讲能体现 Agent 特有的工作：循环控制、工具网关、上下文管理、评测、失败恢复，而不是把普通 LLM 调用包装成 Agent。准备一个失败与修复的案例，比罗列功能更能体现深度。

### 10. Workflow 与 ReAct 的区别？

Workflow：控制流由代码或图预先编排，LLM 只在固定节点内完成任务（分类、抽取、生成），输入输出可预期。优点是确定性强、可测试、可审计、成本和延迟可控，适合流程稳定的业务（工单流转、审批、固定链路的数据处理）。

ReAct：模型在“思考 → 行动 → 观察结果”的循环里自主决定下一步调什么工具、何时结束。灵活，适合开放式、步骤无法预先穷举的任务；代价是步数和成本不可控、可能跑偏，需要最大步数、预算、工具白名单等护栏。

趋势是混合：确定性主干用 Workflow，模糊子任务交给受限的 ReAct 循环。可以引 Anthropic《Building effective agents》的观点：能用 Workflow 就不要上自主 Agent，从最简单的方案开始。

### 11. 你的项目是 ReAct 还是 Workflow 实现的？

个人题，但要讲出选择逻辑，不要只报名词。参考框架：“主干是 Workflow/状态机，因为业务流程固定、要可审计；其中 X 环节用 ReAct 循环，因为该步骤无法枚举所有路径；ReAct 部分加了最大步数、预算和白名单护栏。” 如果两阶段项目用了不同方案，正好对比着讲，能体现是权衡而不是跟风。

### 12. 项目 2 与项目 3 哪个难度更高？

个人题。建议从客观维度比较而不是拍脑袋：不确定性程度（路径能否预定义）、状态与上下文管理复杂度、工具和副作用的风险（只读还是可写）、评测难度、失败恢复代价。结论不重要，比较框架清晰、能举出具体难点例子才重要。避免“都差不多”这种和稀泥的回答。

### 13. 项目 2 采用的是 ReAct 还是其他范式？

个人题。按真实情况回答，重点补上“为什么”：选 ReAct 就说任务的开放性决定了必须让模型自主规划；选 Workflow 就说合规与稳定性要求；选 Plan-and-Execute、Multi-Agent 或其他范式就说清该范式的分工机制（谁规划、谁执行、如何汇总、如何终止）。

### 14. 项目 2 的技术栈是怎么考虑的？

建议按决策维度讲而不是报清单：

- **控制流**：需要循环、分支、checkpoint 就选 LangGraph 这类图编排或自研薄 loop，链式框架不够用；
- **模型接入**：官方 SDK 或统一网关，关注结构化输出、工具调用和流式的稳定性；
- **工具协议**：内部工具封装成统一 Schema，跨系统用 MCP；
- **可观测**：全链路 trace（每步的 prompt、工具调用、耗时、token），LangSmith/Langfuse 或自建日志；
- **成本与维护**：核心循环其实很简单，团队自研几十行可控性最高；框架的价值在生态和成熟护栏，代价是黑盒抽象和升级风险。

结论落点是“为可控性选型”：Agent 核心逻辑简单，难的是护栏和可观测，选型围绕这两点。

### 15. 项目 2 中最满意的实现是什么？

个人题。按“问题 → 方案 → 效果”讲一个点就够，深度优先。好素材举例：把大工具结果落盘、上下文只留引用，解决了上下文爆炸；工具失败后把错误信息结构化回传给模型，解决了失败后盲目重试；给循环加了重复动作检测与预算控制，解决了死循环烧钱。讲完主动说代价和边界（什么情况下该方案不成立），显得真实。

## 四、实习与 AI 编程工程化

### 16/17. 实习承担的工作 / 核心工作与最有成就感的部分

个人题。用“业务背景 → 你的职责边界 → 做了什么（重点 1~2 件）→ 量化结果 → 学到什么”。最有成就感的部分选“从 0 到 1 建了某机制”或“解决了某个线上问题”，讲清现象、定位过程、方案和指标变化。避免把实习描述成打杂，也避免全揽团队成果。

### 18. 实习期间用的哪个 AI 编程工具？

如实回答（Claude Code、Cursor、Copilot、通义灵码等均可）。重点是下一步能接住追问“怎么用的”：见 19、20 题。如果只用过 Web 版对话，就承认边界，同时讲清自己的使用方法论。

### 19. 是否用过 Claude Code？通常怎么用？

参考回答框架（按真实使用情况取舍）：它是终端里的 coding agent，核心是“给任务 → 它读代码库 → 计划 → 改代码 → 跑测试 → 提交”的循环。我通常的用法：

- 项目根目录放 `CLAUDE.md`/`AGENTS.md`，写构建命令、代码规范、目录结构，让它每次带着项目约定干活；
- 复杂任务先进 plan mode 审方案，确认后再动手，避免大改跑偏；
- 小步提交：任务拆小，每步 review git diff、跑测试，通过才进下一步；
- 用自定义 slash command、hooks、MCP 接内部工具，用 Skills 沉淀可复用流程；
- 高风险操作（删文件、执行命令、外发）保留人工确认。

一个到位的总结：把 AI 当“有工具权限但需要验收的初级工程师”管理——给清晰任务、限制权限、用测试和 diff 验收，而不是当搜索框用。

### 20. 如何保证 AI 生成的内容符合实际需求？

四道防线：

1. **输入侧**：把需求写成明确的验收标准（spec/issue/测试用例），并给足相关代码上下文，减少模型自由发挥的空间；
2. **过程侧**：小步任务、先计划后实现、限制改动范围，避免“顺手重构”半个仓库；
3. **验证侧**：测试先行（让 AI 先写测试再实现）、跑单元/集成测试、类型检查、lint，能跑起来验证的行为才算数，不看它“说做了什么”；
4. **审查侧**：人必须 review diff，关键模块和安全敏感代码（权限、资金、数据删除）逐行看，不符合就带着失败信息回炉重做。

核心观点：验收标准前置 + 机器可验证的闭环，是让 AI 产出可控的根本手段，而不是靠事后肉眼挑错。

### 21/22. 是否尝试过 Spec/SDD 驱动的编程？是否了解 TDD 和 SDD？

TDD（测试驱动开发）：先写失败的测试（红）→ 写最小实现让它通过（绿）→ 重构（Refactor）。在 AI 编程里价值被放大：测试是人机之间机器可验证的验收契约，先让 AI 写测试、人审测试，再让 AI 实现，通过即达标，把“生成是否正确”从主观判断变成自动判定。

SDD（Spec-Driven Development，规格驱动开发）：先写规格再写代码。流程通常是：明确需求规格（用户故事、验收标准）→ 技术方案（design）→ 拆任务（tasks）→ 按 spec 逐项实现，代表工具如 GitHub Spec Kit、AWS Kiro。规格是人机契约，评审规格比评审几万行代码便宜得多，且规格可以作为多轮 agent 迭代中不变的对齐锚点。

两者关系：SDD 管“做什么、为什么、边界在哪”，TDD 管“怎么验证做对了”。实践中组合使用效果最好：spec 定范围，测试定验收，agent 填实现。

### 23. 是否用过 Skills？用过哪些效果好的？

按真实情况回答。Skill 可以讲通用机制：把可复用的工作流和领域知识写成带触发条件的文档（如 SKILL.md），元数据常驻上下文，命中后才加载正文，按需展开，不撑爆上下文——相当于给 agent 挂载“操作手册”。

效果好的例子可结合自己实际用过的说：规范化提交/PR 的 skill、测试生成与回归 skill、文档格式转换（docx/pdf/pptx）skill、项目专属的调试手册和部署手册 skill。经验：description 写清触发条件和适用范围，正文写步骤、约束和示例，而不是堆资料；skill 不拥有额外权限，危险操作仍要过权限校验。

### 24. 如何保证代码可维护性、交接后仍能继续开发？

- **结构**：清晰的模块边界和依赖方向，接口契约稳定，内部实现可替换；
- **质量门禁**：类型标注、单元/集成测试、CI（lint + test）、统一的代码规范；
- **文档**：README 写清“如何跑起来、如何部署”，架构图说明核心链路，关键设计决策记 ADR（为什么这么设计，防止后人“看不懂就重写”）；
- **可观测**：规范的日志和关键指标，出问题能定位；
- **交接**：交接清单（环境、账号权限、已知问题、技术债）、小而频繁的 PR 让 review 有历史可查。

一句话总结：可维护性是约束的一致性——别人接手时，结构和文档能让他 30 分钟内改出第一个安全的 PR。

### 25. 参与过的较大项目大约多少行代码？都是 AI 写的吗？

个人题。如实报量级和比例，重点接住追问“你怎么管理这些代码”：哪些是人写的（架构、接口、核心算法）、哪些是 AI 写的（样板代码、测试、CRUD）、review 和测试如何兜底。如果大部分是 AI 辅助生成，坦然承认并接第 26 题的方法论，这不是减分项，讲清管理方式才是加分项。

### 26. 上万行 AI 辅助生成的代码，除了测试通过，如何保证后续易修改和维护？

核心观点先行：AI 生成的风险不是“跑不通”，而是风格漂移、重复造轮子、过度防御和隐藏耦合，时间一长没人敢改。所以约束必须由人提供：

- **人定架构，AI 填实现**：模块边界、接口、数据模型由人设计并 review，AI 只在边界内实现；
- **一致性约束写进规则文件**（CLAUDE.md/AGENTS.md）：命名、目录结构、错误处理方式、禁用的库，让每次生成遵守同一套标准，而不是每次风格都不一样；
- **模块化 + 单一职责**：保持小文件、小函数、清晰的依赖方向，AI 改动的影响面就可控；
- **测试分层作为安全网**：单测护逻辑、集成测试护边界、回归测试防改坏，重构时敢动手；
- **持续治理**：定期删除重复代码和死代码、依赖审计、文档与代码同步更新，防止熵单调递增；
- **每个模块有 owner**，AI 产出也走人审合入，保证任何一段代码都有人能解释。

### 27. 平时浏览 GitHub 吗？最近看到什么有意思的项目？怎么通过 GitHub 学习？

个人题，但建议认真准备一个近期真实看过的项目，能讲到机制层面。参考方向：开源 coding agent（Claude Code 的逆向分析、OpenHands、Aider）、Agent 框架源码（LangGraph 的状态机与 checkpoint 实现）、MCP 生态。学习方式讲成习惯：先读 README 和核心模块源码而不是只看 Demo；把有意思的设计在自己项目里复现验证；关注 trendings、awesome list 和关键作者；看到好设计记到笔记里形成自己的素材库。

## 五、Harness、Loop 与缓存机制

### 28. 是否了解 Harness 和 Loop 等概念？

了解，可以主动给出定义。Harness（工程脚手架）是包裹模型、把它变成可用 Agent 的整套工程：系统提示与角色设定、工具定义与执行网关、上下文管理、主循环、权限与沙箱、错误恢复、状态持久化、可观测与评测。模型是引擎，Harness 是底盘和驾驶舱——同样的模型，Harness 质量直接决定任务成功率。

Loop 是 Harness 的执行核心，一个最小闭环：

```text
while not 终止:
    读取目标与上下文 → 模型决策（思考 + 工具调用）
    → 校验动作 → 执行工具 → 观察结果回填上下文
    → 判断完成 / 重试 / 换路 / 超出预算则止损
```

循环必须有最大步数、token/费用预算和终止条件，否则死循环烧钱。Claude Code、SWE-agent 这类系统本质都是一个精细打磨的 Harness + Loop。

### 29. 是否研究或实践过 Harness 的错误恢复、上下文压缩和缓存机制？

分三块回答：

**错误恢复**：核心技巧是把错误结构化回传给模型——工具的 stderr、异常栈、校验失败原因作为 observation 回填，让模型看到错误后自我修正，而不是静默失败或盲目重试；瞬时错误（网络、限流）用有限重试加指数退避，逻辑错误交给模型改路；每步持久化状态（消息历史、任务清单、git commit），崩溃后能从 checkpoint 恢复而不是从头重跑；最后用最大步数、预算和转人工兜底。

**上下文压缩**：长任务下上下文是稀缺资源。手段包括：滚动摘要（旧历史压成 summary，保留目标和关键决策）；大结果外置——工具输出写文件，上下文只留路径和摘要；结构化状态（todo/plan 文件）替代重复读历史；子代理隔离探索性上下文，只把结论带回主线；工具结果限长和分页。设计要点是压缩不能丢任务目标、已完成结论和约束条件。

**缓存**：见 32、33 题。

### 30. 是否了解 Loop 和 Graph Engineering？

Loop 是 Agent 的执行引擎（见 28 题）。Graph Engineering 是把 Agent 的控制流显式建图为状态机/DAG：节点是步骤或子 Agent，边是条件路由，图负责循环、分支、并行、checkpoint 持久化和人工介入点（LangGraph 是典型实现）。和纯隐式 Loop 相比，图把控制流变成可声明、可测试、可恢复的结构：崩溃后能从某个节点恢复，关键节点可插人工审批，并行节点可同时跑。

### 31. 如何理解 Loop？为什么 Agent 需要 Loop 和 Graph 机制？

对 Loop 的理解：单次 LLM 调用是开环控制——模型对世界的假设没有机会被现实校验。Loop 把生成升级为闭环控制：行动 → 观察真实反馈 → 修正 → 再行动。这是 Agent 区别于“一次性生成”的本质：工具会失败、环境状态会变、需求有歧义，只有闭环才能试错和自我纠错（把报错喂回去，下一轮修好）。

为什么还需要 Graph：Loop 给了灵活性，但纯隐式循环有三个问题——不可调试（黑盒跑飞了不知道哪步错）、不可恢复（崩溃只能重来）、不可控（该审的地方没卡点）。Graph 把“哪步能并行、哪步要人审、失败从哪恢复”变成显式结构。一句话总结：LLM 负责节点内的概率决策，Loop/Graph 负责全局的确定性骨架——概率组件必须跑在可靠运行时上。

### 32. 是否了解大模型 Agent 的缓存命中机制？

了解。原理是 prompt/KV cache：LLM 推理时前缀相同的请求可以复用已计算的 KV，省算力、显著降低首 token 延迟和费用——Anthropic 显式缓存写入约 1.25 倍价、命中读取约 0.1 倍价，OpenAI 自动前缀缓存也有明显折扣（具体以官方定价为准），vLLM 等推理框架有 prefix caching。

命中条件是请求前缀逐 token 完全一致。所以 Agent 的缓存友好设计是：system prompt 和工具定义等稳定内容放最前且保持不变；消息历史只追加、不修改、不重排；每轮的新内容（工具结果、检索结果、当前时间）一律放尾部；并行工具调用的结果按稳定顺序回填。做得好的 coding agent 类 harness 长会话命中率可达 90% 以上，直接决定成本和响应速度。

### 33. 为什么不同 Agent 框架的缓存命中率有高低差异？

因为命中率完全取决于“前缀稳定性”，不同框架在这几点上设计不同：

1. **动态内容插入的位置**：把检索结果、新上下文插在历史中间会打断前缀，追加到尾部则不影响；
2. **每轮是否重写/重排消息**：有的框架每轮重建 prompt、改写历史，前缀全变；
3. **system prompt 里是否注入变化内容**：时间戳、随机 session ID、实时统计数据放在最前，每轮必 miss；
4. **压缩/摘要策略**：触发一次历史摘要，等于前缀全部作废，一次大 miss——所以压缩时机和粒度是关键权衡；
5. **工具定义与顺序**是否固定，多模态内容的编码是否稳定；
6. **会话复用方式**：独立会话各自冷启动，共享长前缀则可以接力命中。

结论：缓存命中率不是推理服务的属性，而是 Harness 设计质量的属性。harness 设计者才是缓存友好性的第一责任人。
