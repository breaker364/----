# 字节跳动 Agent 架构与推理工程面试复盘

> 适用场景：面试后复盘学习。本文根据题目截图整理，不代表候选人的真实项目经历。
>
> 标记说明：`[需替换]` 表示换成自己的项目事实和指标；`[不确定]` 表示没有核实的实现细节，不应在面试中编造。

## 一、这组题在考什么

图片三主要考察能否把 Agent 做成可演进、可评测、可运维的系统。建议按“架构选择 → 上下文与工具 → 评测闭环 → 底层推理”回答。任何线上吞吐量、延迟、SFT 结果、负责模块都应有真实记录；没有就说没有准确数据。

## 二、架构与 Agent 设计

### 1. 你们用的 Agent 框架是什么？ReAct 还是 Plan-and-Execute？

不要把框架名和策略名混为一谈。框架负责状态、工具、消息、执行和观测；ReAct/Plan-and-Execute 是任务决策策略。

ReAct 是边观察边决定下一步，适合路径不确定、步骤较短的任务；Plan-and-Execute 先生成结构化计划，再执行和校验，适合长链路、多依赖任务。实际系统可以混合：入口先做轻量规划，局部步骤用 ReAct，遇到失败允许有限 re-plan。

选型依据包括任务平均步数、路径稳定性、是否需要用户确认、失败代价、延迟和成本。`[需替换]` 具体框架和策略必须按你实际使用的版本填写，不要只说一个流行框架名。

### 2. 项目用的什么架构？LangGraph 还是自研？master+sub Agent 还是 workflow？选型原因是什么？

先讲架构抽象，再讲产品名。可以分为：入口与会话层、任务路由层、编排层、Agent/工具层、状态与记忆层、观测评测层。

| 方案 | 优点 | 代价 | 适合 |
|---|---|---|---|
| 图编排 | 状态和分支显式，易恢复 | 图设计和版本管理成本 | 有明确节点/分支的流程 |
| Master + sub-agent | 角色边界清楚，可委派 | 协调、上下文和失败传播复杂 | 专业分工明显的任务 |
| Workflow | 稳定、可审计、可重试 | 灵活性较低 | 固定业务流程 |
| 自研 Harness | 可贴合业务约束 | 维护成本和基础设施责任高 | 有特殊调度/安全要求 |

选择应由需求决定：流程稳定且合规要求高，优先 workflow；需要动态分支和状态图，选择图编排；子任务可独立验收且专业差异大，再考虑 master/sub-agent。自研的理由必须是具体缺口，如恢复语义、租约调度、成本预算或现有平台集成，不能只说“框架不够灵活”。

### 3. 做 Agent 还是多 Agent？各个 Agent 的核心任务和分工是什么？

单 Agent 的优点是上下文共享简单、协调成本低；多 Agent 只有在专业边界、权限边界或并行空间明显时才有价值。一个示例分工是：

```text
Supervisor：拆任务、分配、汇总、终止
├─ Researcher：检索并返回带来源的证据
├─ Coder：在受限工作区修改代码
├─ Tester：执行测试和生成诊断
└─ Reviewer：按验收标准检查结果
```

每个 Agent 应有明确输入输出、工具白名单、最大预算和完成条件。Supervisor 不应该拥有所有工具，也不应仅凭子 Agent 的自然语言说“完成”就结束；要检查结构化结果和实际产物。

### 4. 多智能体怎么协作？比如一个写代码、一个审查

代码 Agent 和审查 Agent 之间应通过明确契约协作，而不是共享一大段聊天记录。代码 Agent 输出 diff、测试结果、未解决风险和变更摘要；审查 Agent 输入 diff、需求和测试日志，输出按严重级别分类的问题，并给出文件/行号和复现条件。

协作流程可以是：需求 → 实现 → 静态检查/测试 → 审查 → 修复 → 回归 → 合并。审查 Agent 没有写权限时更安全；如果允许自动修复，要限制修改范围和轮数。多 Agent 并行时要避免同时修改同一文件，或者使用分支/补丁合并和冲突检测。

### 5. 首次生成和多轮补充的链路路由怎么区分和实现？

首先识别会话状态和用户意图：新任务、补充约束、纠错、追问、撤销、重新执行。路由依据包括是否存在未完成任务、当前步骤、引用的实体、显式动作词和上下文置信度。

不要让一个分类模型直接决定所有流程。可以用规则优先处理撤销/确认/重试等高确定性意图，再让模型对模糊输入结构化分类；分类结果经过状态机校验。新任务创建新的 task version，多轮补充生成 patch 并重新校验受影响步骤；如果补充改变了前置目标，应使旧计划失效，而不是悄悄沿用。

### 6. Agent 的记忆怎么设计？长短期分别怎么存储？

短期记忆是当前任务所需的工作上下文，如最近消息、计划、工具结果、错误和临时变量；放在任务状态存储或会话缓存中，并控制窗口、摘要和过期时间。长期记忆是跨会话、经筛选后可复用的用户偏好、事实或经验；应有来源、时间、置信度、作用域和删除机制，可使用数据库和向量索引，但不能把向量库当成事实真相。

写入长期记忆前应判断是否稳定、是否有隐私风险、是否得到授权；读取时按任务和权限检索，并标注来源。记忆要支持纠错、过期和冲突解决。`[需替换]` 你的项目应补充具体存储、召回策略和 TTL；没有做过就不要声称有完整长期记忆系统。

### 7. Agent 的 Skills 功能原理是什么？怎么设计和实现 Skills 体系？

Skill 是可组合的能力包，通常包含描述、适用条件、输入输出 schema、操作步骤、工具依赖、权限和版本。加载可以分层：先注入简短元数据，路由命中后再读取详细指令和示例，减少上下文开销。

体系设计要解决：发现、版本、依赖、权限、冲突、测试和回滚。Skill 中的文字不能绕过系统权限；工具调用仍需服务端校验。每个 Skill 应有离线样例和回归集，记录 skill version，输出带来源和执行证据。Skill 多了以后，重点从“写得更长”转向“路由更准、边界更清楚”。

## 三、Prompt 与上下文工程

### 8. 怎么构建提示词模板？上下文工程有哪些实践？to-do list 优化为什么能让模型更聚焦？

提示词模板建议分层：角色与边界、任务目标、输入数据、可用工具、输出 schema、验收标准、失败处理。将稳定规则与动态数据分开，动态内容带来源和时间，避免把历史噪声混入当前任务。

上下文工程包括摘要、裁剪、检索、结构化状态、工具结果压缩、消息分层和上下文预算。To-do list 的价值不是“让模型看起来更聪明”，而是把目标外化为有限的未完成项、依赖和完成条件，减少重复规划和目标漂移；如果列表过长、过细或由模型随意修改，反而会增加噪声。

### 9. 有没有做过查询改写？多维度改写是什么？需用户补信息时，交互和技术怎么实现？

查询改写适用于用户表达不完整、口语化或需要拆成检索子问题的场景。先保留原始 query，再生成结构化改写：意图、实体、时间范围、过滤条件、检索语言和缺失信息。多维度改写可以是同义表达、不同检索粒度、不同视角或多个子问题，但必须去重、保留约束并限制数量。

如果关键字段缺失，不应让模型猜。系统应生成澄清问题，说明为什么需要、给出可选项，并携带 `clarification_id`；用户补充后合并到状态，重新校验受影响查询。低风险缺省值可在明确告知后采用，高风险或影响范围大的字段必须确认。

### 10. 并行化意图识别是什么？为什么要做？怎么实现？

并行化意图识别是同时判断一个输入可能包含的多个意图或路由候选，而不是只输出一个标签。例如“查订单并申请退款”同时包含查询和售后动作。这样可以减少串行等待，并发现组合任务。

实现上可让分类器输出多标签及置信度，再由路由器按优先级、依赖、权限和冲突规则编排。无依赖的读取任务可并行，有写副作用的任务通常串行并要求确认；最终要做结果合并和冲突消解。并行不是越多越好，要设置并发上限、取消传播、超时和成本预算。

### 11. 怎么让模型规范调用工具，不瞎编参数？

工具描述要明确用途、必填/可选字段、类型、枚举、示例、错误和权限边界；用 JSON Schema 或同等结构化约束输出。服务端不能信任模型传参，必须再次校验类型、范围、身份、资源归属和幂等键。

对于高风险动作使用预览 → 用户确认 → 执行；对于查询类工具可以自动执行但限制频率。工具返回统一的成功/失败/可重试结构，避免把异常堆栈直接塞进上下文。监控参数错误率、工具拒绝率、重复调用率和副作用失败率，才能知道问题是在模型还是工具契约。

## 四、评测与 Badcase 定位

### 12. 怎么评估 Agent 效果？

不能只用一个“回答好不好”的主观分数。应按任务类型建立离线集和线上指标：

- 任务成功率、步骤成功率、最终验收通过率；
- 工具选择准确率、参数正确率、无效调用率；
- 事实准确率、证据引用命中率、幻觉率；
- 平均/分位延迟、Token/成本、重试率、人工介入率；
- 安全拒答、越权调用、重复副作用和投诉率。

评测集要覆盖正常、边界、对抗、长上下文、工具失败和多轮补充。离线评测用于回归，线上灰度和人工抽检用于发现分布变化。LLM-as-a-judge 可作为辅助，但要校准、抽检，并与程序化验收结合。

### 13. 没有用户反馈时，怎么做有效抽检？

建立分层抽样：按意图、模型版本、工具、错误类型、延迟区间、低置信度和高风险动作抽样；不要只抽最热门的成功样本。设置金标准或专家 rubric，双人标注一部分并计算一致性，对分歧样本复盘。

还可以使用程序信号：任务是否生成预期文件、测试是否通过、引用是否存在、工具参数是否被拒、是否超预算。没有用户反馈不等于没有评测，只是不能把线上满意度当作可用指标。需要避免用“模型自评自己”作为唯一抽检。

### 14. 出现 Badcase 怎么快速定位环节？如何判断该给哪个 Agent 做 SFT 优化？

先用 trace 把一次任务拆成路由、规划、Prompt/上下文、工具选择、参数生成、工具执行、结果解析和最终回答。对每个节点记录输入摘要、版本、输出、耗时、错误、重试和证据引用。

定位顺序可以是：是否路由错 → 是否上下文缺失/污染 → 是否工具描述或 schema 不清 → 是否参数校验失败 → 工具本身失败 → 结果合并/验收失败。只有当问题稳定、样本足够、错误边界清晰且 Prompt/规则/工具修复不能经济解决时，才考虑 SFT。

选择 SFT Agent 的原则是看“错误归因”而不是看谁最显眼：路由错误优化路由模型，工具参数错误可能先修 schema/约束，知识错误先修检索和数据，格式错误先用结构化输出或 parser。SFT 前要保留独立验证集，确认不是记忆训练集。

### 15. Prompt 调优“修好一类、坏了另一类”怎么解决？

这通常是过拟合某类样例、上下文冲突或规则互相覆盖。建立按场景分层的回归集，每次改动同时看总分、分桶分数、关键安全指标和成本；不能只看新增样例。

解决手段包括：把通用规则与场景规则分层；减少相互矛盾的示例；将稳定约束移到代码和 schema；对不同任务使用路由到不同模板；用版本化实验和灰度；必要时回滚。Prompt 不是越长越好，新增规则如果没有明确优先级，常常增加模型决策负担。

### 16. 工具调用失败、超时了怎么处理？

先分类：参数校验失败通常不应原样重试；限流、网络抖动和部分 5xx 可有限重试；业务不存在、权限不足应澄清或转人工；未知状态要先查询副作用再决定重跑。每次调用带 deadline、request ID、幂等键和取消信号。

超时后要记录超时位置，区分排队、连接、服务处理和读取超时；向 Agent 返回结构化错误和可执行的下一步，不要把内部堆栈当用户答案。可以降级到缓存、备用工具、异步任务或人工确认，但必须告诉用户状态。重试需指数退避、抖动、最大次数和总预算，并防止多个执行者同时产生副作用。

### 17. 开发 Agent 时踩过哪些坑？

可从下面选择真实发生过的部分，不能整段冒充经历：

- 把模型说“完成”当成任务完成，没有程序化验收；
- 工具 schema 写得模糊，导致参数缺失或类型错误；
- 上下文无限累积，延迟和成本逐渐失控；
- 重试没有幂等键，重复写入外部系统；
- 只测成功路径，没有模拟工具超时、限流、空结果和脏数据；
- 多 Agent 共享文件或状态，出现竞态和结果互相覆盖；
- 只看平均延迟，没有看 P95/P99 和长尾；
- 将线上日志直接送入 Prompt，带来隐私泄露或提示注入。

回答时用“现象—原因—修复—验证—后来如何防止”展开。`[需替换]` 加上你真实的一次事故或调试记录；如果没有线上经历，可以说“我在实验/开发阶段遇到过……，还没有独立处理过线上事故”。

## 五、工程与底层基础

### 18. LLM 推理优化做过哪些工作？用过 continuous batching、KV Cache、vLLM 吗？线上峰值吞吐量多少？

先区分自己真正做过的层次：应用侧并发与缓存、推理服务部署、模型量化/并行、还是算子和内核优化。Continuous batching 会动态把不同到达时间的请求合并，提高 GPU 利用率，但要处理请求公平性、调度、显存和长短请求互相影响。KV Cache 保存已计算的注意力键值，减少增量生成重复计算，但会占用显存，需要考虑 prefix cache、复用条件和淘汰策略。

vLLM 等推理引擎通常提供更高效的请求调度和 KV Cache 管理，但具体能力、版本和部署参数要以实际使用版本为准。`[不确定]` 没用过就直接说没在线上用过，不要因为知道概念就回答“用过”。

吞吐量回答必须给口径：输入/输出 token 数、并发数、模型和量化、硬件、平均还是 P95、首 Token 延迟还是总延迟、稳定时长。没有可核实指标时可说：

> 我没有保留经过压测口径统一的线上峰值，不能给出可靠数字。复盘时我会补齐硬件、模型、并发、输入输出长度和时间窗口，再分别报告 TTFT、TPOT、P95 延迟、tokens/s、错误率和成本。
