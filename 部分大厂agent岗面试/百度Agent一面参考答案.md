# 百度 Agent 一面：问题与参考答案

> 来源：用户提供的“百度 agent 一面（8.20）”截图。题目包含本地部署、缓存、Agent 记忆、网络与手撕；个人经历和框架版本请据实填写。

## 一、Agent 系统设计

### 1. Agent 部署在本地机器用于排查异常进程，需要注意什么？

先明确权限和边界：只读采集优先，禁止模型直接执行任意 kill、rm 或网络操作；高风险动作采用白名单、最小权限和人工确认。采集进程列表、CPU/内存/句柄、线程栈、日志和网络连接时要脱敏并限制采样频率。

运行环境应隔离（容器/沙箱），设置 CPU、内存、磁盘和执行时长配额；工具返回结构化数据而不是整段 shell 输出。Agent 先分析和给出证据，再由规则校验修复命令，执行前二次确认，执行后验证进程状态并记录审计 trace。断网或模型不可用时保留确定性诊断脚本。

### 2. 沙箱实例并发数量，需要考虑哪些问题？

容量规划要看 CPU、内存、磁盘、GPU、网络和下游服务的并发上限，区分启动并发、运行并发和排队长度。为每个实例设置配额、租约、超时和最大任务数，使用队列和信号量做背压；调度时考虑冷启动、镜像拉取、NUMA/GPU 亲和和资源碎片。

还要处理租户隔离、临时目录和网络 egress、日志量、僵尸实例、抢占与优雅回收。压测关注吞吐、P95 延迟、启动成功率、OOM、排队时间和单任务成本，并预留故障余量。

### 3. 给现有 Agent 扩展新能力，会设计哪些功能？

先定义能力边界和验收标准，再设计 Skill/Tool 接口、输入输出 Schema、权限、超时、幂等和错误码。路由层增加意图和版本兼容，状态层保存中间结果，评测集补正常、边界、权限和失败用例；上线采用灰度、监控和回滚。

如果能力涉及写操作，加入审批/回滚和审计；如果是长任务，使用队列和 checkpoint；如果依赖外部数据，明确缓存、版本和新鲜度，避免只在 Prompt 中“描述新能力”。

### 4. Agent 遇到无法解决的场景，应该怎么处理？

先判断是缺信息、无权限、工具失败、无知识还是模型不确定。保留当前 task 状态和证据，向用户提出最小澄清问题；工具故障则有限重试、切换降级路径或异步受理；高风险/低置信度转人工。明确告诉用户已完成、未完成和下一步，不编造结果。

所有失败使用结构化错误码并记录 trace，设置最大澄清次数、deadline 和预算；可恢复任务支持从 checkpoint 继续，不必从头重跑。

### 5. Agent 记忆模块如何设计？

分为工作记忆、会话短期记忆和长期记忆。工作记忆保存当前计划、待办、工具结果和临时变量；短期记忆保存本轮相关消息并通过窗口/摘要控制 token；长期记忆保存经过确认、跨会话仍有价值的偏好或事实。

记忆对象带 `id、scope、source、timestamp、confidence、version、ttl`，写入前做抽取、去重、敏感信息过滤和冲突检测，读取时按任务/权限召回。结构化事实用数据库，语义内容可用向量索引；原始证据保留在外部存储以便纠错、删除和审计。

### 6. 长期、短期记忆与当前上下文冲突，如何解决？

先按可靠性和时效性排序：当前用户明确指令和最新已验证业务状态通常优先于旧记忆；长期记忆必须带时间、来源和置信度。发现冲突时暂不覆盖，列出冲突证据并向用户澄清；若业务规则可判定，则按版本/生效时间选择并记录决策。

把冲突解决写成程序策略和可观测事件，而不是让模型自行“感觉哪个对”。更新长期记忆后使旧版本失效，支持撤销和 TTL；高风险场景必须人工确认。

### 7. 企业内部知识问答 Agent，整体方案如何做？

数据侧：接入文档/工单/数据库，解析清洗、去重、版本和权限，按结构切片并建立向量+BM25 索引。在线：鉴权 → 意图/敏感信息识别 → 查询改写 → 权限过滤 → 混合召回/Rerank → 父级上下文拼装 → LLM 生成带引用答案 → 引用/事实/安全校验；无依据则拒答或澄清。

系统侧配套 Tool Gateway、状态和记忆、缓存、消息队列、审计、评测和监控。指标包括 Recall@k、引用准确率、任务完成率、P95、成本和越权拦截率；增量更新、删除同步、索引回滚和多租户隔离必须可验证。

### 8. Agent 调用 Skill 工具的完整执行流程是什么？

注册 Skill 元数据 → 路由根据触发条件和权限选中 → 懒加载详细指令/Schema/示例 → Planner 生成结构化步骤 → 模型提出 tool call → 网关做鉴权、参数和风险校验 → 执行工具 → 返回带 `call_id/status/data/error/source` 的结果 → 更新状态/记忆和 trace → 判断完成、补参、有限重试或转人工 → 程序化验收后输出。

Skill 文本不拥有额外权限，工具网关必须独立校验；写操作使用幂等键和审计，结果过大要摘要或分页。

## 二、大模型基础

### 9. 简述大模型 token 生成原理

输入文本先经过 tokenizer 变成 token ID，Embedding 后进入 Transformer；因果注意力让每个位置只能看见前文，经过多层 Attention/MLP 得到最后位置的 logits。对 logits 应用温度、Top-k/Top-p 等解码策略得到下一个 token，追加到序列并循环，直到 EOS 或达到长度上限。训练通常用 next-token prediction 的交叉熵；推理阶段是自回归生成。

### 10. 大模型对话接口参数有哪些？分别什么意思？

常见参数有 `model`（模型版本）、`messages`（角色与内容）、`temperature`/`top_p`/`top_k`（采样随机性）、`max_tokens` 或 `max_completion_tokens`（输出上限）、`stop`（停止序列）、`stream`（流式返回）、`seed`（若服务支持）、`response_format/JSON Schema`（结构化输出）、`tools/tool_choice`（工具调用）、`timeout`、`metadata` 和安全/内容过滤配置。不同厂商字段不同，面试时先说明以具体 SDK 版本为准。

### 11. 大模型本身具备记忆能力吗？

模型参数记住的是训练分布中的统计模式，不等于按用户维度可更新、可删除的长期记忆；一次 API 调用通常只看传入上下文。会话记忆需要由应用保存历史、摘要、结构化状态或 RAG，再在请求时选择性注入。模型可能通过上下文表现出“记得”，但上下文窗口有限且会过期，不能当作事实数据库。

## 三、系统与网络基础

### 12. 查看机器 CPU、进程状态常用哪些命令？

Linux 常用：`top`/`htop` 看实时 CPU 和内存，`ps -ef` 或 `ps aux` 看进程，`pidstat -p <pid> 1` 看进程级 CPU/IO，`vmstat 1` 看系统运行队列，`free -h` 看内存，`uptime` 看负载，`lsof -p <pid>` 看文件/连接，`ss -lntp` 看监听端口，`journalctl`/`tail -f` 看日志。排查顺序是现象 → 指标 → 日志/线程 → 复现，先确认 PID 和权限再执行操作。

### 13. Docker 容器内运行程序，与直接在宿主机运行进程有什么区别？

容器共享宿主机内核，但通过 namespace 隔离进程、网络、挂载等视图，通过 cgroups 限制 CPU/内存，镜像提供可复现的用户态依赖。宿主机进程直接使用主机文件、网络和权限，隔离和发布一致性较弱但观测/性能路径简单。

容器并非虚拟机；错误的特权、挂载 Docker Socket、host network 或过宽 capability 会削弱隔离。生产要设置非 root 用户、只读根文件系统、资源配额、健康检查、日志/监控和镜像扫描。

### 14. TCP 相关机制，发生丢包时如何处理？

TCP 通过序列号、ACK、超时重传、快速重传/快速恢复、滑动窗口、流量控制和拥塞控制提供可靠有序字节流。接收方发现乱序会重复 ACK，发送方收到重复 ACK 或 RTO 到期后重传并降低拥塞窗口。

排查丢包要区分网络真实丢包、接收端处理慢、队列溢出和应用超时：看 `ss -ti`、网卡/内核丢包计数、RTT/重传率和抓包时间线。应用层还要设置合理连接/读超时、重试退避、请求幂等和熔断，避免重试风暴；不能无限重试或简单调大超时掩盖问题。

### 15. 访问下游 TCP 服务连接超时，完整排查思路？

按层定位：

1. 确认目标域名解析、IP、端口和配置版本；
2. 在同一网络命名空间用 `nc -vz host port`/`curl -v` 测连通，检查路由、ACL、安全组和防火墙；
3. 用 `ss -s`/`ss -tan` 看本机连接、SYN-SENT、端口耗尽和连接池；
4. 服务端看监听、backlog、线程/连接上限和 access log；
5. 抓包判断 SYN 是否发出、是否收到 SYN-ACK、是否被 RST/丢弃；
6. 若 TCP 已建立，再检查 TLS、协议握手、服务处理延迟和读超时。

修复后做端到端验证和压测，记录 DNS、连接、TLS、首字节和总耗时分段指标。

### 16. 传统后端开发与 Agent 开发哪个难度更高？

难点不同，不能简单比较。传统后端的接口、事务、并发和数据一致性通常更确定；Agent 还要处理模型非确定性、上下文、规划、工具副作用、评测和成本，因此系统边界更复杂。Agent 并没有降低后端要求，反而需要把确定性部分（权限、状态、重试、幂等、事务、验收）下沉到代码。

我会把 Agent 当作“概率决策组件 + 可靠后端运行时”：模型负责理解和选择，程序负责约束、执行和验证。成熟度取决于业务风险和可测性，而不是使用了多少模型。

## 四、手撕：反悔贪心与堆

### 17. 什么是反悔贪心？如何用堆实现？

反悔贪心先按局部最优做选择，同时把已选方案放入堆；当后续发现约束不满足或出现更优替代时，弹出代价最大的旧选择并换成新选择，相当于允许“撤销”过去的贪心决策。最常见模板是：按时间/收益排序，维护当前选择的最小堆或最大堆，在容量、数量或截止时间约束下回退。

例如选择截止时间内耗时最短的任务并最大化收益：先按截止时间排序，加入任务；若总耗时超出截止时间，就从最大耗时堆中撤销一个任务。每个任务最多入堆/出堆一次，复杂度 O(n log n)。

```python
import heapq


def max_scheduled_tasks(tasks: list[tuple[int, int]]) -> int:
    """tasks: (duration, deadline)，返回可按期完成的最多任务数。"""
    total = 0
    chosen = []  # 最大堆：用负数保存耗时最大的已选任务
    for duration, deadline in sorted(tasks, key=lambda x: x[1]):
        total += duration
        heapq.heappush(chosen, -duration)
        if total > deadline:
            removed = -heapq.heappop(chosen)
            total -= removed
    return len(chosen)
```

面试时要说明贪心不变量和为什么撤销的是“最不划算/最占资源”的元素；如果题目目标是最大收益而非最多任务，需要把堆中保存收益或损失，并证明交换/替换规则成立，不能机械套模板。
