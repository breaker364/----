# 携程 AI Agent 开发一面：问题与参考答案

> 来源：用户提供的“携程 AI Agent 开发一面（45-50min 纯技术面经）”截图。面试官为业务线资深开发，风格极度务实、不水八股：不深挖预训练原理，重点验证项目是否真的上过线，考察高 QPS 用户查询与票务酒店场景的幻觉管控。涉及个人项目的答案需替换成真实上线数据，以下内容用于组织技术表达。

## 一、项目深挖（占比高，连环追问）

### 1. 抛开 LangChain/LangGraph 封装，手写最小可用 Agent 循环的完整逻辑？

Agent 的本质就是一个 while 循环：把 system prompt、历史消息和工具 Schema 发给模型，模型要么返回最终回答（循环结束），要么返回 tool_calls（执行工具、把结果以 `role=tool` 消息追加回 messages、继续下一轮）。状态完全由 messages 列表承载，不需要任何框架：

```python
def run_agent(messages, tools, max_steps=8):
    for _ in range(max_steps):                      # 预算控制，防死循环
        resp = llm.chat(messages, tools=tools)      # 唯一的“智能”来源
        msg = resp.choices[0].message
        messages.append(msg)
        if not msg.tool_calls:                      # 不要工具 → 最终答案，退出
            return msg.content
        for tc in msg.tool_calls:
            try:
                args = json.loads(tc.function.arguments)
                result = tool_registry[tc.function.name](**args)
                payload = json.dumps(result, ensure_ascii=False)
            except Exception as e:                  # 解析失败/执行失败都回喂给模型
                payload = json.dumps({"error": str(e)}, ensure_ascii=False)
            if len(payload) > 8000:                 # 大结果截断，防上下文爆炸
                payload = payload[:8000]
            messages.append({"role": "tool",
                             "tool_call_id": tc.id,
                             "content": payload})
    return "已达最大步数，给出部分结果或转人工"
```

面试时要主动说出框架帮你隐藏的四件事：循环终止条件（无 tool_calls、max_steps、token/成本预算）、工具注册与 Schema 生成、错误回喂（工具报错不能抛异常中断，要作为 observation 让模型自己调整）、以及状态持久化（生产中 messages 要落 Redis/DB，支持断点恢复，不能只存在进程内存里）。能讲清这些，就证明不是只会调框架。

### 2. Agent 完整执行链路是什么？每一轮 LLM 调用前后做了哪些预处理和后置校验？

完整链路：请求鉴权 → 会话状态加载 → 输入校验/脱敏 → 意图识别与路由 → 组装上下文（system + 记忆 + 检索内容 + 工具子集）→ 进入循环【LLM 调用 → 后置校验 → 工具执行 → 结果写回】→ 终止后程序化验收 → 安全审核 → 返回。

每轮 LLM 调用**前**的预处理：检查 token 预算是否超限（超了先压缩）、按当前意图裁剪工具列表（不是全量塞）、历史消息和工具结果做截断/摘要、脱敏检查。调用**后**的后置校验：看 `finish_reason`（length 说明被截断）、tool_calls 的函数名是否在白名单内、参数过 JSON Schema 校验和业务校验（日期是否合法、城市是否存在、订单号格式对不对）、写操作再过权限和风险审批；校验失败不执行，把错误信息拼回消息让模型重试。循环退出后还要做引用校验（答案里的政策是否有检索证据支撑）和成本统计。核心思想是：模型只做决策，所有校验和执行都由确定性代码兜住。

### 3. Function Calling 的 JSON Schema 如何设计？参数校验失败、格式错乱怎么兜底？

Schema 设计原则：参数尽量少、平铺不深嵌套；`description` 里写清格式、单位、取值示例（比如“日期格式 YYYY-MM-DD，不能早于今天”）；枚举值用 `enum` 而不是自由文本（舱位写 `enum: [经济舱, 公务舱]`）；`required` 只放真正必需的字段，可选参数给默认值，减少模型编造；时间类统一约定时区和格式；一个工具只做一件事，参数歧义就拆工具。

兜底是分层的：第一层用宽松解析（json_repair 修常见格式错误，比如尾逗号、单引号）；第二层 pydantic/JSON Schema 严格校验，失败后**带错误信息重试**——把“参数 city 缺失且必须是合法城市”作为 tool 结果回喂，让模型自纠一次，必要时用 `tool_choice` 强制它重发；第三层程序补默认值或反问用户澄清（“您想查哪一天的航班？”）；重试仍失败就放弃该工具、走降级路径。所有格式错误都记 badcase 指标，错误率高说明 Schema 设计有问题，回去改描述而不是继续堆兜底。服务端永远不信任模型输出，这是底线。

### 4. 项目中什么时候用自主 Agent 推理，什么时候强制走固定 Workflow 规则？业务取舍标准是什么？

判断维度有四个：**错误成本**（涉及订单、退改、支付等资金写操作，模型自由发挥一次就是资损，必须走状态机）、**路径是否可枚举**（退票流程就五步，枚举得尽就 Workflow；开放式行程规划枚举不尽才用 Agent）、**时延要求**（高并发简单问答走固定链路，Agent 循环多轮 LLM 延迟扛不住）、**可验收性**（结果能否程序化判断对错）。

落地上是混合模式：Workflow 做骨架，个别节点内部允许有限自主。比如退改签整体走固定状态机（身份校验 → 订单查询 → 规则计算 → 二次确认 → 执行），但其中“帮用户理解退改条款”这个节点用 RAG + 小范围 Agent；行程攻略、模糊咨询走自主推理，但工具是白名单子集、有步数和成本预算、只读不写。给面试官的结论句：**“自主性是奢侈品，只在读路径和低风险场景放开；所有写路径和资金路径一律确定性代码。”**

### 5. 长对话上下文膨胀严重，你的上下文压缩放在 Agent loop 的哪一步？具体压缩策略？

位置有两个：主压缩点放在**每轮 LLM 调用前的组装阶段**——组 prompt 前先算 token，超过阈值（比如模型窗口的 70%）才触发压缩，平时不动；副压缩点在**工具结果写回前**，大结果当场摘要，不把 8000 字的原始 JSON 留在历史里。

策略是分层淘汰：system prompt 和最近 3-5 轮原文保留（指令和最新意图不能丢）；更早的轮次压成结构化摘要——已确认的槽位（目的地、日期、人数）、已做过的查询、未完成的事项，而不是让模型自由复述；中间的检索资料只留被引用过的片段；陈旧的失败重试记录直接丢弃。压缩用增量方式（新内容追加进摘要卡），避免每轮全量重新总结浪费 token。关键约束：**任务状态不能只活在上下文里**，槽位和待办同步存外部状态机，压缩丢了信息也能从状态机恢复。

### 6. 线上遇到过哪些 Badcase？幻觉、错调用工具、重复调用分别怎么修复？有无量化优化数据？

回答结构建议按“现象 → 定位 → 修复 → 数据”讲真实案例（以下数据为示例框架，务必换成自己的）：幻觉类，用户问某航司退改规则，模型在检索没命中的情况下按训练知识编了条款——修复是政策类问题强制走 RAG 且要求标注引用来源，检索分数低于阈值直接回复“暂未查到该政策，建议查看官方页面”，并加了“检索无证据不得回答政策类问题”的 system 约束，政策类事实错误率下降（如从 5% 降到 1% 以下）。错调用工具类，用户问“上海的迪士尼酒店”，模型调了机票查询——定位是工具 description 写得含糊，重写描述加 few-shot 示例、参数做硬校验拦截，工具误调率明显下降。重复调用类，工具返回空结果时模型反复用近似参数重查——修复是给工具结果加明确的 `has_result: false` 语义信号、相同参数签名去重、超 2 次注入系统提示要求总结，同时配上全局 max_steps。

要强调方法论：所有 badcase 进 trace 回放库，先归因（检索/模型/工具/Schema 设计）再修，修完把 case 加进回归评测集，防止改好一个坏两个。

### 7. 项目如何做版本迭代？Prompt 迭代、模型切换、框架升级如何保证稳定性？

核心是把不可变的东西版本化：Prompt 进 git，每次修改有版本号和变更说明；模型版本固定到具体快照（不用 floating 的 latest）；评测集版本化，每个线上 badcase 修完都沉淀进去。任何变更（Prompt、模型、工具描述、索引）上线前跑全量回归评测——规则校验 + LLM-as-judge + 关键 case 人工抽检，指标不达标不上。

上线用灰度而不是全量切换：新版本先 1%-5% 流量，对照旧版本看任务成功率、转人工率、延迟、单均成本四个指标，稳定再放大，出问题一键切回（Prompt 和模型路由都做成配置中心热切换）。模型切换要额外注意：不同模型的指令跟随和工具调用能力差异大，切换前用评测集跑分，必要时对 Prompt 做适配而不是直接复用。框架升级的原则是隔离——业务代码不直接依赖框架 API，中间留一层薄适配，升级时只改适配层，跑兼容性测试再发布。

## 二、RAG 检索与文档工程（高频考点）

### 1. 固定长度分块的致命缺陷是什么？你落地的语义分块、层级分块优化方案？

固定长度按字符数硬切，致命缺陷是把完整的语义单元切碎：政策条款的“编号 + 正文 + 适用条件”被切成两块，表格行和表头分离，召回回来的片段既不完整也没法引用，模型拿到半句话反而容易脑补幻觉。旅游政策文档（退改规则、签证要求）条款结构性强，这个问题尤其严重。

落地方案：**结构优先的语义分块**——先按文档标题、章节、条款编号切（HTML/Markdown 结构树），条款过长的再按句子边界二次切，每个 chunk 携带完整元数据（文档版本、生效日期、目的地、适用舱位/房型）。**层级分块（父子块）**：子块是条款/段落级别的细粒度文本，用于向量召回（短文本embedding更准）；父块是章节级完整上下文，命中子块后取其父块拼进 prompt，做到“检索用小块、生成用大块”。 chunk 之间保留重叠和前后文引用（“见上文第 X 条”做关联），表格整表成块并序列化成带表头的文本。

### 2. 旅游场景 PDF 混杂图文、表格、政策条款，文档解析难点怎么解决？

难点四个：扫描件和图片化的文字（要 OCR）、表格结构还原（PDF 里的表格是画出来的线，不是结构化数据）、双栏/跨页排版（阅读顺序错乱）、图文关联（图片说明和正文分离）。

解决路径：解析层用版面分析工具（unstructured、MinerU 或自研 pipeline）先做 layout detection，区分正文、标题、表格、图片区域；表格单独提取还原成 Markdown/HTML，整表作为一个 chunk 并把表头写进每行序列化文本（“经济舱 | 退票费 5%”这种自包含行，防止检索只命中半行）；扫描页走 OCR 后人工抽检；图片要么用多模态模型生成 caption 入库，要么明确丢弃并记录（不能默默丢信息）；跨页段落做合并处理。工程上最重要的是**解析质量监控**：抽样人工对比原文和解析结果、统计每类文档的解析失败率，badcase 驱动规则迭代；保留页码和章节路径作为元数据，答案引用能溯源到 PDF 第几页。

### 3. 多路召回（向量+BM25）各自解决什么问题？旅游模糊查询如何平衡语义与关键词精准度？

向量召回解决“意思对但字面不同”：同义改写（“退票”vs“取消预订”）、口语化描述（“适合带老人不折腾的海岛”），靠 embedding 的语义泛化能力。BM25 解决“字面必须准”：专有名词和编号（航司二字码 MU、酒店名、政策条款号 H5.2）、生僻词、新词（embedding 模型没见过的开业新酒店，向量效果差但字面匹配能命中）。两者互补，单路都有明显盲区。

旅游 query 的特点是短、实体密度高、错别字多、口语模糊。平衡做法是 query 理解先行：先做实体识别和归一化（“下周五”解析成具体日期、“魔都”映射上海、纠错“三亚湾”vs“亚龙湾”），把实体交给 BM25（配同义词词典和拼音纠错兜底）、把意图语义交给向量，两路各取 top-k 后用 RRF 或加权分数融合，再统一过 rerank。模糊诉求（“帮我找个暖和的地方”）实体缺失，靠向量 + 用户画像（出发地、偏好）补齐，补不齐就反问澄清，不做强行召回。

### 4. 上线 Rerank 前后，如何量化召回质量提升？核心评估指标有哪些？

前提是先建标注评测集：从真实 query 抽样（按意图、长度、实体类型分桶），人工标注 query-doc 相关性（二档或三档），这是所有量化的地基。离线指标用 **Recall@k**（top-k 里包含相关文档的比例，反映召回上限）、**MRR**（相关文档排多前，反映排序质量）、**nDCG@k**（考虑分级相关性的排序质量）；对比方式是同一批 query、同一个前置召回 top-50，分别测“裸向量/BM25 融合”和“加 rerank 后”的指标，控制变量才能归因。rerank 带来的提升会直接体现为“生成用同样 token 预算下，相关文档密度更高”。

线上验证看端到端代理指标：答案引用命中率、引用点击率、答案采纳率（用户没追问/没转人工）、人工反馈纠错率；同时盯成本和延迟——rerank 是对 top-k 逐对打分的交叉编码器，k 太大 P95 明显上涨，一般取 top 20-50 进 rerank、取 top 3-5 进 prompt。要能说出“离线指标涨了多少、线上哪个代理指标验证了、延迟代价多少”这三个数，才显得真的上过线。

### 5. 知识库政策、票价、酒店规则实时更新，如何解决内容过期、新旧数据冲突幻觉？

先把“更新”做成带版本的 pipeline：文档入库带 `version、effective_date、expire_date、source` 元数据，chunk 继承；新版本生效时旧版本不是物理删除而是软删除（tombstone），向量库做 upsert 同步更新，同时失效对应缓存。检索时按元数据过滤：只检“当前生效”版本，活动类内容按日期窗口生效/失效。这样从源头避免“新旧两条都召回”，而不是靠模型自己分辨哪条新。

剩下防线的三件事：prompt 层强制“只依据给定资料回答，并标注资料的生效日期”，让模型引用时带上时间属性；冲突检测层，入库时对同主题文档做相似度聚类，发现“同主题多版本并存”触发人工审核，防止漏更；验收层，对票价、退改这类高风险字段做规则校验（价格必须是接口返回值，不允许 LLM 生成数字），并定期抽查答案与最新政策的抽查一致率。旧数据过期幻觉（拿去年的政策回答今年）大多不是模型问题，是删除同步没做干净——向量库还留着已下线文档，这一点主动说出来很加分。

### 6. 低质 Query、模糊诉求、冷门目的地查询，如何避免检索空召回、错召回？

分层处理。**Query 理解层**先降质为优：意图分类识别这是知识咨询还是交易请求；槽位完整性检查，“我想退票”缺订单号就反问；改写扩展（同义扩写、HyDE 假设文档）提升模糊 query 的可检索性。**检索层设质量卡点**：召回分数低于阈值判定为空召回，此时不硬答——走降级路径（推荐相近热门内容 / 引导换表述 / 诚实说明“知识库暂未覆盖，建议咨询客服”），宁可不答也不编。**错召回卡点**：rerank 后 top1 分数仍低就判定无可靠依据，回答里明确说明依据有限；命中内容与 query 实体做一致性校验（问“三亚签证”不能答成“泰国签证”）。**冷门目的地**单独处理：维护覆盖范围清单，明确告知知识边界，同时把空召回 query 沉淀成统计报表，驱动知识库定向补全——把“答不了”变成可运营的输入。

## 三、记忆管理与会话设计（高并发场景重点）

### 1. Redis 在你的 Agent 系统中具体存储什么？会话状态、缓存结果、用户记忆如何区分？

三类数据用完全不同的 key 结构和生命周期：**会话状态** `sess:{session_id}:state`（Hash：当前任务类型、已填槽位、循环步数）和 `sess:{session_id}:messages`（List/Zset：消息历史，带序号），TTL 设 24-48h，过期可从 DB 冷数据恢复；**缓存结果**按归一化 query（实体标准化后）做 key，内容是公共知识（政策、攻略）才缓存，TTL 短（分钟级到小时级），可随时丢弃重建；**用户记忆** `user:{user_id}:memory`（Hash 存结构化画像 + set 存偏好标签），TTL 长，Redis 做热层、DB 做持久真相，写入双写或异步落库。

区分的本质是三个维度：**作用域**（session 级 vs user 级 vs 全局）、**生命周期**（请求内/会话内/跨会话）、**一致性要求**（会话状态丢了体验受损，缓存丢了只是多算一次）。把这三点说清楚，比背 Redis 数据结构更有说服力。

### 2. 多用户高并发同时在线，如何做会话隔离、记忆隔离？如何避免会话串扰？

隔离的第一原则：**所有状态 key 强制携带 `session_id/user_id` 前缀**，由框架从请求上下文注入，业务代码没有途径构造不带租户的 key；请求入口做鉴权校验（session 归属校验，防止拿别人的 session_id 直接访问）；日志和 trace 同样带会话维度，方便回放单个会话而不混入他人数据。

容易串扰的三个隐蔽点要主动讲：一是**缓存串扰**——带个人信息的查询结果（“我的订单”）绝不能进公共缓存，缓存 key 必须含用户维度或只缓存公共知识；二是**向量检索串扰**——用户私有记忆检索必须带 `namespace=user_id` 过滤条件，而不是检索后过滤；三是**异步并发写**——同一用户多端同时发消息，会话状态用版本号乐观锁（或按 session 分伞的分布式锁）避免消息交错，消息写入用 Redis 原子操作保序。最后用并发测试验证：模拟同一用户多端并发 + 多用户交叉请求，断言消息序列和记忆内容互不污染。

### 3. 短期滑动窗口记忆、长期用户画像记忆如何分层设计？

分三层。**工作层**：最近 N 轮原文消息（token 预算内滑窗），承载当前对话的指代和语境（“那改到后天呢”依赖上一轮）；**会话摘要层**：滑窗之外的历史压缩成结构化摘要卡（已确认槽位、做过哪些查询、用户表达过的约束），会话内跨轮复用；**长期画像层**：跨会话的结构化事实——常驻地、常用出行人（是否带小孩/老人）、舱位/酒店档次偏好、会员等级，来自对话后的异步抽取 + 关键信息用户确认，存 DB + Redis 热缓存。

注入顺序：system 指令 → 画像卡片（简短、标注更新时间）→ 会话摘要 → 滑窗原文 → 本轮检索内容。设计要点：每层信息带**来源和时效**（画像里“偏好经济舱”是一年前抽取的，权重应低于用户本轮明说的“这次要公务舱”）；写入有门槛和置信度，单次偶发表述不直接进长期记忆；用户可以查看和纠正自己的画像（合规要求，也是数据质量来源）。

### 4. 记忆库持续膨胀、检索精度下降，你的迭代优化方案是什么？

膨胀治理四个手段：**TTL 与衰减**——行程类记忆（某次具体旅行）结束后自动降权或过期，偏好类记忆按访问频率续期；**摘要合并**——定期把细粒度多条记忆聚类合并（“喜欢海岛”“去过三亚三次”“偏好潜水酒店”合并为“海岛度假偏好”卡片），控制条目数；**去重归一**——embedding 相似度高的记忆合并，冲突的按时间戳新覆盖旧；**写入门槛**——抽取时打分，低价值信息（一次性查询）不进长期库。

精度下降的对策：检索从“全库 top-k”改为**意图路由到子空间**（偏好/历史行程/合规约束分开索引），缩小候选集；加**时间衰减因子**参与排序（新记忆加权）；上线记忆命中率评测（召回的记忆是否真的被本轮用到）作为北极星指标，配合人工抽检。核心思想：记忆库不是越大越好，和 RAG 一样是检索质量问题，宁可少而准。

### 5. Token 溢出的多级兜底策略是什么？

按成本从低到高分级触发：**第一级，工具结果瘦身**——写回前就做字段筛选和截断，这是最大的膨胀源，成本为零；**第二级，检索内容裁剪**——按 rerank 分数截断，只留 top 片段，低分的直接丢；**第三级，历史压缩**——滑窗外的消息替换为摘要卡（增量摘要，避免重算）；**第四级，system 瘦身**——指令分层，本轮用不到的工具说明和 few-shot 摘除；**第五级，硬截断保底**——仍超限就从最旧消息开始丢，并注入一条“部分早期上下文已被省略”的系统标记，关键槽位从外部状态机恢复而不依赖对话历史；**极端情况**主动开新会话，携带摘要卡无缝衔接。同时监控 prompt token 的 P95 分布，设阈值告警，溢出频繁说明压缩策略参数要调。原则：让“必须裁剪”永远发生在第五级之前。

## 四、工具调用与 Agent 稳定性（面试重点扣分点）

### 1. Agent 出现工具死循环、重复调用同一接口，如何检测、截断、终止流程？

检测三道网：**预算网**——每会话 max_steps（如 8 步）、max_cost（token/调用费用）、max_wall_time（如 30s），任一触顶即终止，这是最硬的保底；**签名网**——对每次调用生成“工具名 + 规范化参数”签名，滑窗内同签名重复 N 次（或连续无进展、observation 与上次相同）判定循环；**模型网**——把最近几次调用列表给到一个轻量检查（规则或小模型），识别“换着参数查同一件事”的软循环。

截断分软硬：软截断是注入系统消息“你已连续多次调用相同工具且结果为空，请基于已有信息作答或询问用户补充信息”，给模型一次自纠机会；硬截断直接终止循环，输出已有部分结果 + 明确告知未完成部分 + 转人工入口。配套两件事：**写操作幂等键**——终止前已经发出的下单/退改调用不能重复执行；**事后归因**——循环 case 进回放库，多数根因是工具描述含糊或空结果语义不明，修 Schema 才是治本。

### 2. 工具接口超时、抖动、返回空数据，重试、降级、兜底策略如何设计？

**重试**：只对幂等读操作重试，写操作必须带幂等键才能重试；指数退避 + 随机 jitter，最多 2-3 次；区分错误类型——超时/429/503 可重试，400 参数错误重试无意义。**超时**：连接超时和总超时分开设，工具级超时小于整个 Agent 会话 deadline，防止单工具拖垮整链路。**降级**：连续失败触发熔断，走降级路径——查缓存快照（标注“数据更新时间”）、退化为规则计算（查不到实时票价就展示“暂无法查询实时价格”）、给出替代信息；降级结果必须打标，让上层和用户知道这不是实时数据。**空数据**：区分“业务真无结果”（直飞查不到，如实说明并推荐中转）和“接口故障伪装成空”（监控空返率异常告警）。高并发下还要有**舱位级预案**：大促前对非核心工具预挂降级开关，主链路保命。

### 3. 如何区分是模型输出问题，还是下游工具/业务接口问题？快速定位根因？

前提是**全链路 trace**：每轮 LLM 的完整输入输出、每次 tool_call 的参数、工具网关的校验结果、下游请求的 URL/响应码/耗时，全部按 trace_id 串起来可回放。定位顺序自上而下：先看**分层监控**——LLM 层指标（格式错误率、工具选择错误率，可用固定评测集复跑量化）、网关层（Schema 校验拦截数）、下游层（错误码分布、超时率、RT），哪层指标异常根因就在哪层；再看**单 case 回放**——拿 trace 里的原始输入固定 seed 复跑模型，能复现错误是模型/Prompt 问题，复现不了且下游有 5xx/超时记录就是接口问题。

典型信号对照：参数幻觉（编造不存在的城市、格式错乱）= 模型或 Schema 设计问题；schema 校验拦截多 = Prompt 描述不清；下游 5xx/超时 = 接口问题；答案内容错但工具返回正确 = 模型理解/生成问题；“该查的没查就回答” = 模型规划问题。讲的时候强调“归因不靠猜，靠评测集复跑 + trace 证据”。

### 4. 大量无效工具调用会拉高成本、拖慢 QPS，你做过哪些限流与拦截机制？

按调用链路从前往后拦：**入口层**——意图分类后按场景裁剪工具白名单（查攻略的会话根本不给下单工具，模型想调也调不了）；**校验层**——Schema 硬校验 + 业务规则拦截（查询日期在过去、人数超上限）直接拒绝，不透传到下游；**预算层**——会话级工具调用次数、token 预算、成本上限，超限终止；**限流层**——用户级/会话级令牌桶，下游接口按配额做信号量并发控制，排队 + 快速失败；**缓存层**——相同归一化 query 和工具参数短 TTL 缓存命中直接返回，这是消重复调用最有效的手段。再把“无效调用率”（校验拦截数 / 总调用数）做成核心监控指标，持续驱动工具描述和 Schema 优化。效果可以量化着说：例如缓存 + 白名单裁剪后单会话平均工具调用次数和 token 成本下降的幅度。

## 五、携程专属业务场景设计题（大概率出）

### 1. 设计旅游咨询 Agent：用户混合提问机票价格、退改规则、酒店政策、出行攻略，如何拆分多意图、并行调度工具、结果聚合，杜绝回答遗漏？

**多意图拆分**：query 理解阶段用 LLM 把混合提问分解为子任务列表，输出结构化 DAG——例如“3 月去三亚，机票多少钱？退改什么规则？亚特兰蒂斯适合带孩子吗？”拆为 `查机票(三亚, 3月)`、`查退改规则(依赖机票结果的具体航班)`、`查酒店政策(亚特兰蒂斯, 亲子)`；拆分时做**槽位共享**（目的地、日期、人数只解析一次，全局复用）和**依赖分析**（退改规则依赖选定的航班，是下游节点）。

**并行调度**：无依赖的子任务用 asyncio/线程池并行执行（机票查询和酒店政策查询同时发出），有依赖的等前置结果后触发；每个子任务独立走自己的检索/工具链，互不污染。

**聚合与防遗漏**：每个子任务产出结构化中间结果（结论 + 数据来源 + 置信度），聚合阶段按用户原始提问的顺序逐项作答，每项标注引用来源。**杜绝遗漏靠程序不靠自觉**：任务清单 checklist 由代码校验——每个拆分出的子任务必须有对应结论或明确的“暂时查不到”，缺失就补查一轮或在答案尾部如实声明，不允许静默吞掉。最后统一做一次整体一致性检查（价格数字必须来自接口、政策必须带引用），再输出。

### 2. 大促高峰期用户查询暴涨，如何控制 Agent 调用成本、保证高并发响应稳定？哪些场景强制切规则链路？

**流量分层削峰**：入口用小模型/规则做意图分类，简单 FAQ 和政策类 query 直接走单轮 RAG（一次检索一次生成，不进 Agent 循环），只有复杂多步任务才进完整 Agent——这一层通常能砍掉大半 LLM 调用量。**缓存**：大促热点可预期（目的地政策、退改规则、活动规则），提前离线预热生成 FAQ 缓存；在线按归一化 query 命中缓存。**模型分级**：简单任务路由到小模型，复杂任务才用旗舰模型，单位成本下降明显。**资源保护**：会话级调用预算、下游接口配额与信号量、队列排队 + 超时快速失败 + 异步通知，宁可让用户稍等也不雪崩。

**强制规则链路的场景**（可预测、有资金/合规风险、要求确定性）：交易写操作（下单、支付、退改签执行）走固定状态机 + 二次确认；价格展示必须实时接口返回，LLM 不得生成任何数字；合规强相关内容（退改条款、签证要求、保险条款）必须原文引用知识库，不允许自由生成；大促活动规则以活动系统的结构化数据为准。LLM 只负责理解和组织语言，事实和资金由确定性系统负责——这是大促稳定性设计的总原则。

## 六、工程落地与评测闭环

### 1. Agent 整套链路性能瓶颈大概率出现在哪一环？检索/推理/工具调用？怎么排查优化？

大概率是**推理环节**：每轮 LLM 调用秒级延迟，Agent 循环 3-5 轮就是两位数秒，且上下文越长 TTFT 越慢；其次是**串行的下游工具调用**（票务、酒店接口本身几百毫秒，串三四个就过秒）。检索环节相对可控（向量检索几十毫秒，rerank 看模型大小）。

排查靠**分段耗时 trace**：把每轮 LLM 耗时、检索耗时、每次工具耗时按 trace_id 串起来，看 P50/P95 分段瀑布图，长尾在哪一目了然——不要凭感觉猜。优化手段按瓶颈对症：推理慢 → 精简上下文（降 TTFT）、减少循环轮次（工具结果一次给够，避免挤牙膏式补查）、流式输出改善体感、简单任务路由小模型；工具慢 → 无依赖调用并行化、加缓存、给下游设超时熔断；全链路 → 首字节时间优化（先流式输出“我帮您查一下”再执行工具）。目标指标是端到端 P95 和首响应时间，优化后用同一 trace 口径对比。

### 2. 如何搭建自动化评测体系？如何量化任务成功率、幻觉率、用户解决率？

分四层搭建。**组件层**：检索 Recall@k/MRR、工具参数准确率（标注集上跑）、意图分类准确率。**端到端离线层**：黄金评测集（真实 query + 标注理想行为，含正常/边界/对抗/无答案 case），任务成功率用程序化验收（该调的工具调了吗、槽位填对了吗、结果对吗）+ LLM-as-judge 打分（答案相关性、完整性），**幻觉率**定义为“答案中无检索证据支撑的事实性陈述占比”——用引用核对（声明的来源里真的有这句话吗）+ 与事实库比对自动计算，抽样人工复核校准 judge。**线上层**：用户解决率用代理指标量化（会话内完成且无追问/无转人工/无差评的比例）、人工接管率、CSAT、badcase 率。**流程层**：评测跑在 CI，Prompt/模型/索引任何变更自动触发回归，指标对比报告不达标不放行；线上 badcase 定期回流进评测集，形成闭环。

### 3. 模型迭代、Prompt 迭代后，如何做基线对比、灰度验证效果？

**基线对比**：版本化一切（Prompt、模型、索引、工具描述），离线在同一评测集上跑新旧版本全量对比，报告核心指标（任务成功率、幻觉率、引用正确率）+ 分桶细分（按意图/难度），差异做显著性检验，防止小样本波动误判；同时记录成本和延迟，性能换效果要算账。**灰度验证**：先 shadow/影子流量（新版本对线上真实请求只记日志不返回用户），对比新旧真实输出差异；再小比例灰度 1% → 5% → 50%，用 A/B 看线上核心指标（解决率、转人工率、P95 延迟、单均成本）和**护栏指标**（幻觉投诉率、资损相关指标不能恶化），任一护栏指标劣化立即停止放量。**回滚**：Prompt 和模型路由做配置中心热切换，预演过一键回滚；灰度期间按分位数（P95/P99）监控而不是均值，长尾劣化往往先从长尾暴露。

## 七、手撕算法（中等难度，重边界）

### 题目理解

风格是字符串/数组处理、贴合业务 query 清洗：输入原始用户搜索串，输出规范化 query——去首尾与连续空白、剔除控制字符和零宽字符、全角转半角、统一小写、超长截断，并判断清洗后是否为有效 query。难点不在算法而在**边界完备性**：空输入、None、全空白、纯 emoji、超长截断截出半个词怎么办。

### 参考实现（Python）

```python
import unicodedata

MAX_LEN = 64  # 业务约定的 query 最大长度

def clean_query(raw: str) -> tuple[str, bool]:
    """清洗用户 query，返回 (清洗结果, 是否有效)。"""
    if raw is None:
        return "", False
    # 1. 全角转半角 + Unicode NFC 归一化（如繁体/组合字符统一形态）
    s = unicodedata.normalize("NFC", unicodedata.normalize("NFKC", raw))
    out = []
    prev_space = True                     # 用于把连续空白折叠成一个空格
    for ch in s:
        cat = unicodedata.category(ch)
        if cat.startswith("C") or cat == "Cf":
            continue                      # 控制字符、零宽字符直接剔除
        if cat.startswith("Z") or ch in "\t\n\r":
            if not prev_space:
                out.append(" ")
            prev_space = True
            continue
        prev_space = False
        out.append(ch.lower())
    s = "".join(out).strip()
    # 2. 截断到最大长度；若截断落在词中间，回退到最近的空格（中文则直接截）
    if len(s) > MAX_LEN:
        s = s[:MAX_LEN]
        cut = s.rfind(" ")
        if cut > MAX_LEN // 2:            # 只有回退点足够靠后才回退，避免剩太少
            s = s[:cut]
    # 3. 有效性：剥掉标点和符号后必须还有字母/数字/中日韩字符
    core = [c for c in s if unicodedata.category(c).startswith(("L", "N"))]
    return s, len(core) > 0
```

### 复杂度与容错说明

时间复杂度 O(n)（n 为输入长度，逐字符单遍扫描），空间 O(n)。容错逻辑要主动说明：`None`/非字符串入参不抛异常、返回空并标记无效（线上服务宁可吞掉脏输入也不能 500）；控制字符（`Cc`）和零宽字符（`Cf`，常见于复制粘贴夹带）剔除，防止它们污染下游检索或注入 prompt；连续空白折叠避免 BM25 分词产生空 token；截断回退到空格是针对英文词中截断，中文无空格直接截——两种语种的处理差异主动说出来是加分项。测试用例至少覆盖：正常串、全空白、纯 emoji/纯标点（应判无效）、全角字母数字（应转半角）、含零宽字符、恰好等于和超过 MAX_LEN、超长英文截断回退、`None` 入参。

面试官也可能追问变体：统计一天内 top-k 热门搜索词（清洗后计数 + 最小堆/`Counter.most_common`，O(n log k)）；或敏感词过滤（Trie 多模式匹配，O(总文本长 + 命中数)）。思路都是“先清洗归一，再在规范形态上做匹配”。
