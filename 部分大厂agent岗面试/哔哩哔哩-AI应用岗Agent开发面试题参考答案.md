## 2. 完整的 Agent 系统有哪些核心模块？和传统 LLM Chatbot 最大区别是什么？

**回答：**

一个完整 Agent 通常包括：

- 用户交互和任务接入层；
- 意图识别、任务路由和上下文管理；
- 规划或策略模块；
- 记忆模块；
- 工具注册、选择和执行模块；
- LLM 推理模块；
- 状态机或 Agent Loop；
- 安全、权限、可观测性和评测模块。

传统 Chatbot 主要是“用户输入 → 模型生成回复”，路径通常是单轮或固定多轮对话；Agent 的核心区别是它有目标和状态，能够根据中间结果动态规划，并通过工具对外部世界产生动作。也因此，Agent 需要处理执行失败、循环、权限、幂等、成本和最终结果验证。

## 3. Planning、Memory、Tool Use 和执行模块分别负责什么？

**回答：**

- **Planning**：把目标拆成步骤，确定顺序、依赖和下一步行动；简单任务可采用 ReAct，复杂任务可先生成计划再逐步执行。
- **Memory**：保存并在需要时召回历史信息，包括当前会话上下文、用户偏好、历史任务和长期知识。
- **Tool Use**：描述工具能力，选择合适工具，生成参数，并处理工具返回结果。
- **Execution**：真正执行工具或子任务，负责权限、参数校验、超时、重试、幂等、结果写回和错误处理。

Planning 决定“做什么”，Tool Use 决定“调用哪个能力”，Execution 负责“安全地做成”，Memory 则提供决策所需的历史状态。

## 4. 意图识别有哪些实现方式？规则匹配、小模型分类、LLM 分类分别适用于什么场景？

**回答：**

常见实现方式有关键词/正则规则、传统机器学习、Embedding 相似度、小模型分类、大模型零样本或少样本分类，以及规则和模型结合的级联方案。

| 方式 | 优点 | 适用场景 | 局限 |
|---|---|---|---|
| 规则匹配 | 快、可解释、成本低 | 意图少、边界稳定、强约束词明显 | 泛化差，维护成本会增长 |
| 小模型分类 | 延迟和成本较低，适合线上高并发 | 意图集合稳定、已有标注数据 | 对新意图和复杂语义适应较弱 |
| LLM 分类 | 泛化强，能处理复杂表达和新意图 | 意图少样本、语义复杂、需要快速试验 | 成本、延迟、稳定性和可控性较差 |

实际项目常用级联：先规则处理高置信度样本，再由小模型分类，低置信度或复杂样本交给 LLM，并设置兜底意图。

## 5. 大模型意图分类如何选择 Zero-shot/Few-shot？标注数据较少如何提高稳定性？

**回答：**

Zero-shot 不提供示例，只提供意图定义，适合意图少、定义清楚、需要快速验证的场景；Few-shot 提供少量具有代表性的输入和标签，适合用户表达多样、类别边界容易混淆的场景。

标注数据较少时可以：

1. 写清楚每个意图的定义、正例、反例和边界；
2. 采用稳定的标签枚举和结构化 JSON 输出；
3. 挑选覆盖不同说法的高质量 Few-shot，而不是机械堆样本；
4. 做同义改写、噪声和对抗样本增强；
5. 用规则处理高精度特征，用模型处理语义泛化；
6. 加置信度阈值、拒识类和人工兜底；
7. 固定模型参数和 Prompt 版本，建立离线评测集；
8. 通过混淆矩阵分析容易混淆的意图，针对性补数据。

## 6. RAG 从文档进入到最终生成答案的完整流程是什么？离线构建和在线检索分别有哪些步骤？

**回答：**

离线流程通常是：文档采集 → 解析和清洗 → 去重 → 按结构切片 → 添加元数据 → Embedding 向量化 → 写入向量库，同时建立关键词索引和版本信息。

在线流程通常是：接收问题 → 查询改写或拆分 → 识别过滤条件 → 生成 Query Embedding → 向量检索/关键词检索 → 合并候选 → 过滤和去重 → Rerank → 截取上下文 → 组装 Prompt → LLM 生成 → 引用和格式校验 → 返回答案。

生产系统还需要处理文档增量更新、删除同步、权限过滤、租户隔离、索引版本切换、召回日志以及无结果时的兜底回答。

## 7. 文档切片有哪些策略？RecursiveCharacterTextSplitter 的逻辑是什么？中文处理要注意什么？

**回答：**

常见切片策略包括固定长度切片、按段落/标题/章节切片、语义切片、递归切片、按问答对切片和父子文档切片。实际通常优先保留文档结构，再用长度限制兜底，并设置少量重叠。

RecursiveCharacterTextSplitter 的核心逻辑是：按一组分隔符从强结构到弱结构递归切分，例如先按段落，再按换行，再按句子或空格；如果某块仍超过目标长度，就使用下一级分隔符继续切分；最后将相邻的小块按 `chunk_size` 和 `chunk_overlap` 合并。

中文需要注意：

- 不能依赖空格判断词边界；
- 优先考虑标题、段落、句号、问号、分号等中文分隔符；
- 表格、代码、列表、PDF 双栏文本不能简单按字符截断；
- `chunk_size` 要结合 Token 而不是只看字符数；
- 重叠过大可能造成重复召回和上下文膨胀；
- 对标题、章节、页码、时间、权限等元数据要保留；
- 需要处理 OCR 错误、乱码、页眉页脚和跨页段落。

## 8. RAG 回答质量差如何定位？先查 Embedding、Chunk、Query Rewrite、Hybrid Search 还是 Rerank？

**回答：**

我会先区分是“召回不到”还是“召回到了但生成不好”，再按链路定位，而不是固定只查某一个环节：

1. 建立带标准答案和相关文档的评测集；
2. 检查 Query、权限过滤和元数据过滤是否正确；
3. 查看 Top-K 是否包含正确文档，计算 Recall@K、MRR 或 nDCG；
4. 如果正确内容完全不在候选中，重点查切片和 Embedding；
5. 如果原问题表述与文档差异大，检查 Query Rewrite、问题拆分和多查询；
6. 如果关键词、编号、专有名词容易漏召回，加入 Hybrid Search；
7. 如果正确文档在候选中但排序靠后，检查 Rerank；
8. 如果上下文正确但答案仍错，检查上下文截断、Prompt、引用约束和生成评测。

经验上，切片错误会直接破坏召回上限，Embedding 决定语义匹配能力，Hybrid Search 补关键词和精确匹配，Rerank 负责候选排序，Query Rewrite 负责把用户问题变成更适合检索的查询。应通过消融实验验证每个组件的真实收益。

## 9. Embedding 模型如何选择？不同模型会如何影响检索效果？

**回答：**

选择时主要看语言覆盖、领域适配、向量维度、最大输入长度、推理成本、延迟、部署方式、数据安全和在目标数据集上的 Recall@K/nDCG，而不是只看通用排行榜。

不同 Embedding 模型会影响：

- 同义表达和跨语言匹配能力；
- 专业术语、数字、实体和代码的区分能力；
- 长文本表示是否丢失关键信息；
- 向量库大小、检索速度和存储成本；
- 模型更换后的向量空间兼容性；
- 对 Chunk 长度、归一化和距离函数的敏感程度。

应使用真实业务查询做离线对比，并固定索引、Chunk、Top-K 等变量。更换 Embedding 通常需要重建索引，不能直接把不同模型产生的向量混在同一个空间中比较。

## 10. LangChain 的核心组件有哪些？相比传统 Chain，LCEL 做了哪些改进？

**回答：**

LangChain 常见核心组件包括模型封装、Prompt Template、输出解析器、Document Loader、Text Splitter、Retriever、Vector Store、Tool、Agent、Memory，以及 Runnable/Callback 等运行时能力。

传统 Chain 往往是固定的串行调用，组件之间耦合较强。LCEL 基于 Runnable 抽象，用管道和组合表达数据流，例如 `prompt | model | parser`，并支持：

- 统一的 `invoke`、批处理和流式接口；
- Runnable 的串行、并行、分支和 fallback；
- 更容易插入重试、超时、回调和 tracing；
- 更清晰的输入输出类型和组合关系；
- 更方便把检索、生成和解析组合成可复用流程。

具体版本 API 可能变化，不熟悉某个版本的细节时应以项目实际依赖为准。

## 11. Function Calling/Tool Calling 的执行流程是什么？模型如何判断调用工具并生成参数？

**回答：**

流程通常是：服务端定义工具名称、描述和 JSON Schema → 将工具声明传给模型 → 模型根据用户问题、系统指令和当前上下文决定直接回答还是返回工具调用 → 应用层解析调用 → 校验工具名和参数 → 做权限、风险和业务校验 → 执行工具 → 将结果以 tool message 写回上下文 → 再次请求模型生成最终答案或继续调用工具。

模型判断是否调用工具，依赖工具描述、当前任务、系统 Prompt、历史消息和模型本身的训练能力。参数来自模型生成的结构化 JSON，但模型输出不能直接视为可信输入，必须在服务端做类型、范围、必填项、权限和业务规则校验。

## 12. Agent 接入大量工具，如何避免工具描述过长导致 Prompt 膨胀？

**回答：**

可以采用分层和按需暴露：

1. 先用工具路由器或意图分类筛选候选工具；
2. 按领域分组，先暴露工具箱，再按需加载具体 schema；
3. 使用工具搜索工具，让模型先检索工具目录；
4. 合并高度相关的简单工具，减少重复描述；
5. 压缩描述，只保留用途、关键参数、限制和示例；
6. 把详细文档放到可检索知识库，不全部塞入 Prompt；
7. 让子 Agent 负责一个领域，主 Agent 只看到少量高层能力；
8. 做 schema 缓存、版本管理和工具使用统计，淘汰低价值工具。

还要同时关注工具选择准确率、Token 成本、延迟和错误率，不能为了缩短 Prompt 而丢掉必要的约束。

## 13. Prompt 如何设计和组织？System Prompt、Few-shot、CoT 分别做什么？

**回答：**

Prompt 可以按“角色与边界 → 任务目标 → 输入上下文 → 工具规则 → 输出格式 → 示例 → 兜底策略”组织。System Prompt 放稳定的角色、权限、安全边界和全局规则；用户消息放当前任务；检索内容和工具结果要明确标记为外部数据，避免和指令混淆。

- **System Prompt**：规定长期有效的行为和约束；
- **Few-shot**：通过示例展示输入、推理任务和期望输出格式，帮助模型理解边界；
- **CoT**：引导复杂问题进行分步推理。生产环境通常不要求暴露完整思维过程，而是要求模型输出简洁结论、关键依据或结构化中间结果。

Prompt 应版本化、可测试、可观测，避免把互相冲突的规则不断叠加进去。

## 14. 如何降低大模型幻觉？除了 Prompt 约束还有哪些工程方案？

**回答：**

可以从“提供依据、限制输出、验证结果、降低不确定性”四个方向做：

- 使用高质量 RAG，并要求答案引用可定位的证据；
- 对事实、实时数据和业务状态调用可靠工具或数据库；
- 使用 JSON Schema、枚举、类型和业务规则校验输出；
- 做答案与证据的一致性检查、引用检查和事实核验；
- 对检索不到依据的情况明确拒答或回答“不知道”；
- 采用低温度、受限解码或确定性规则处理关键字段；
- 使用多模型交叉验证、Self-consistency 或专门的校验模型；
- 设置置信度阈值、人工审核和高风险操作确认；
- 通过微调、偏好优化和领域数据增强模型稳定性。

不能只看语言是否流畅，要同时评估事实正确率、证据覆盖率、拒答准确率和关键业务字段错误率。

## 15. Agent 任务中重复调用工具、无法结束或循环，如何设计保护机制？

**回答：**

我会把保护放在运行时，而不是只写进 Prompt：

1. 限制最大步数、总耗时、Token 和费用；
2. 记录工具调用签名，检测相同参数的重复调用；
3. 检测状态没有变化、结果重复和工具交替调用形成的循环；
4. 设置单工具频率限制和重试上限；
5. 对写操作使用幂等键、事务或补偿机制；
6. 工具调用失败时区分可重试错误和不可重试错误；
7. 达到阈值时返回可解释的失败结果或转人工；
8. 用 trace、告警和离线回放定位循环原因。

## 16. Agent 中的 Memory 如何实现？短期记忆和长期记忆分别解决什么问题？

**回答：**

短期记忆是当前会话或当前任务的上下文，例如最近几轮消息、工具结果、计划和当前状态，主要保证任务连续性。长期记忆是跨会话保存的用户偏好、稳定事实、历史任务摘要或可复用经验，主要解决个性化和长期连续性。

实现上，短期记忆通常放在状态存储或消息历史中，并通过截断、摘要和 Token 预算控制上下文；长期记忆可以用结构化数据库、文档库或向量库保存，但要带用户、租户、时间、来源和权限元数据。

记忆不是越多越好，要考虑写入条件、更新和删除、过期、冲突、隐私、用户可见性以及错误记忆的纠正机制。

## 17. 如何设计记忆检索流程？历史信息如何筛选、存储和召回？

**回答：**

可以设计为：

1. **记忆抽取**：从对话和任务结果中识别稳定事实、偏好、约束和可复用经验；
2. **质量判断**：过滤临时信息、低置信度信息、敏感信息和重复内容；
3. **结构化存储**：保存内容、类型、用户/租户、来源、时间、置信度、版本和过期时间；
4. **多路检索**：按用户和权限先过滤，再进行关键词、向量、时间、新近度和重要性检索；
5. **排序与去重**：综合语义相关性、时效性、重要性和使用频率，去除冲突或重复记忆；
6. **上下文注入**：只把与当前任务相关的少量记忆放入 Prompt，并标记为参考信息；
7. **反馈更新**：根据用户纠正、任务结果和访问情况更新置信度，支持删除和遗忘。

权限过滤必须先于语义检索，不能把不属于当前用户或租户的信息召回后再补救。

## 18. 手撕代码：合并重叠区间（LeetCode 56），并分析复杂度

**回答：**

思路是先按区间左端点排序，然后从左到右扫描：如果当前区间与结果中最后一个区间重叠，就更新右端点；否则追加一个新区间。

```python
from typing import List


def merge(intervals: List[List[int]]) -> List[List[int]]:
    if not intervals:
        return []

    intervals.sort(key=lambda item: item[0])
    merged = [intervals[0][:]]

    for start, end in intervals[1:]:
        last = merged[-1]
        if start <= last[1]:
            last[1] = max(last[1], end)
        else:
            merged.append([start, end])

    return merged
```

设区间数量为 `n`：排序复杂度是 `O(n log n)`，扫描复杂度是 `O(n)`，总时间复杂度为 `O(n log n)`。输出数组之外的额外空间通常是 `O(1)`；如果把排序实现、输出和语言运行时的空间都计入，则空间复杂度可写为 `O(n)`。
