# 懂车帝 AI Agent 一面：问题与参考答案

> 来源：用户提供的“27 秋招懂车帝 AI Agent 一面面经”截图。答案强调企业级 Agent 的可控性；项目事实、框架版本和指标请按本人经历替换。

## 一、Agent 项目与架构

### 1. 自我介绍

用 60~90 秒说明教育/工作背景、与 Agent 相关的项目、亲自负责的模块和结果。建议突出 RAG、工具调用、任务编排、评测或线上稳定性中的两三项，并说明为什么对汽车内容/交易/服务场景感兴趣。

### 2. 介绍一个熟悉的 Agent 项目：解决什么问题？方案与落地流程？

按“业务痛点 → 用户输入 → 路由 → 检索/规划 → 工具 → 状态 → 验收 → 结果”讲。例如汽车知识助手可先识别车型、地区和问题类型，召回带版本和来源的手册/政策，必要时调用库存或计算工具，最后返回引用和适用条件。

落地流程包括数据接入与权限、离线索引、在线服务、灰度发布、监控和 badcase 闭环。重点说个人贡献：写了哪些接口/节点，解决过什么失败，指标如何测量。

### 3. 项目中的多 Agent 架构为何这样设计？如何分工？

只有当任务存在专业、权限或并行边界时才拆多 Agent。示例：Supervisor 负责路由、预算和汇总；Researcher 检索并返回证据；Vehicle-Data Agent 查询车型/库存；Calculator 负责价格或金融计算；Reviewer 做事实、权限和格式验收。每个 Agent 有独立工具白名单、输入输出 Schema、最大步数和完成条件。

如果任务路径稳定，优先 Workflow 或单 Agent，避免多 Agent 的通信成本、上下文重复和错误传播。Supervisor 不能仅凭子 Agent 的自然语言“完成”结束，要检查结构化结果和真实产物。

### 4. 多 Agent 之间的信息传递和协作机制？

通过结构化消息/事件而不是共享一整段聊天记录。消息包含 `task_id、step_id、sender、目的、输入、证据、状态、版本、trace_id`；大对象放对象存储，消息只传引用。同步调用适合短查询，长任务用队列和 checkpoint；并行任务通过依赖 DAG 汇合。

通信层提供超时、重试、幂等、顺序/因果标识和权限校验。共享状态采用数据库或状态存储，避免多个 Agent 同时覆盖；冲突按版本号/乐观锁处理。

### 5. 任务执行过程中，如何设计任务结束、异常退出和状态管理？

定义明确状态机：`created → running → waiting_input → retrying → succeeded/failed/cancelled`，每次状态迁移写入事件和版本。完成条件应是可验证的，例如结果 Schema 通过、引用存在、订单状态已更新，而不是模型文本说“已完成”。

异常按类型分类：参数/业务错误需补参或澄清；瞬时网络错误有限重试；权限/安全错误立即终止；超时保存 checkpoint 后异步恢复或降级。设置最大步骤、deadline、token/费用预算和循环检测，支持取消、重放和人工接管。

### 6. 项目落地遇到哪些棘手问题？如何优化解决？

可从以下真实案例中选一到两个：长上下文导致延迟上升（摘要、分层记忆、按需检索）；RAG 命中但答案错（父子索引、混合召回、Rerank、引用校验）；工具参数缺失（Schema、补参和确认）；下游不稳定（超时、熔断、幂等和降级）；多 Agent 循环（状态机、预算和终止条件）。回答用“现象—定位—改动—指标—副作用”闭环，不要只说“调了 Prompt”。

### 7. 如何搭建 Agent 应用评测体系？结果如何驱动优化？

离线黄金集覆盖高频、长尾、无答案、对抗、权限和工具失败；组件评测检索/分类/工具解析，链路评测任务完成和状态恢复，线上评测延迟、成本、错误率和人工接管。指标包括答案相关性、事实/引用正确率、召回率、工具成功率和 P95。

每条 trace 标记模型、Prompt、Skill、工具和索引版本；badcase 按路由、规划、检索、上下文、执行和生成分类。若是数据/工具问题先修系统，只有稳定且可标注的模型行为才考虑 SFT。变更采用分桶回归、灰度和回滚。

## 二、Tool、Skill、Workflow 与 Agent

### 8. 四者分别承担什么职责？区别是什么？

| 概念 | 职责 | 典型特征 |
|---|---|---|
| Tool | 一个可执行能力 | 明确入参/出参、副作用、权限和错误 |
| Skill | 可复用的领域能力包 | 触发条件、步骤、工具组合、Schema、版本 |
| Workflow | 确定性流程编排 | 节点/依赖/重试/审批/验收显式 |
| Agent | 目标驱动的决策执行体 | 结合上下文动态选择 Skill/Tool 并维护状态 |

Agent 不应直接绕过 Workflow 的合规节点；Skill 文字也不能替代 Tool Gateway 的权限校验。

### 9. 什么时候适合 Skill，什么时候设计 Workflow？

Skill 适合复用知识和操作套路、路径有一定弹性且需要模型选择工具的任务，如“查询车型并解释差异”。Workflow 适合步骤固定、依赖明确、必须审计或有事务边界的任务，如贷款审批、订单变更、内容发布。

混合方式通常更稳：Workflow 固定主流程，在某个节点调用受限 Skill/Agent 处理非结构化理解；Skill 输出结构化结果后再回到 Workflow。判断标准是路径稳定性、失败代价、合规要求、可验收性和延迟预算。

### 10. 哪些业务必须依赖 Workflow？为什么？

涉及支付/订单状态、风控与授信、权限审批、内容发布、数据迁移、批量写入、定时 SLA 或需要补偿事务的业务必须由 Workflow/状态机掌控。它们要求顺序、幂等、审批、超时、回滚和审计确定，不能让模型自由决定关键步骤。Agent 可以负责意图识别、信息补全和异常解释，但不能拥有越权写操作。

## 三、上下文、知识库与企业级能力

### 11. 什么是 Agent 上下文工程？实际解决什么问题？

上下文工程是对模型输入的信息进行选择、组织、压缩和版本管理，而不只是把历史消息拼接起来。实践包括：结构化任务状态、分层记忆、查询改写、混合检索/Rerank、工具结果摘要、来源与时间标记、token 预算、敏感信息脱敏和 Prompt 注入隔离。

它解决长上下文遗忘、无关信息干扰、事实过期、工具结果过大和多租户串数据。压缩后要回归检查目标、数字、约束、待办和证据 ID。

### 12. 成熟的企业级 Agent 系统需要哪些核心能力？

多租户鉴权与 RBAC、模型/工具/Skill/Prompt/索引版本管理、状态持久化与 checkpoint、超时重试幂等、沙箱和审批、RAG 与引用、可观测 trace、评测回归、成本计量、灰度回滚、数据脱敏、审计和灾备。系统要能回答“谁在什么版本下让 Agent 调了什么工具，结果是否真实完成”。

### 13. 给 Agent 配知识库，如何保证检索更准确？

先治理数据：去重、版本、权限、标题层级、表格/图片解析和更新时间；切片按语义结构而非固定长度，保存 `doc_id/section/parent_id/source/version`。在线用查询改写、关键词+向量混合召回、元数据过滤、父子上下文和 Rerank；生成要求引用证据，没命中则拒答/澄清。

评测分桶看 Recall@k、MRR/nDCG、引用准确率、答案事实一致性和延迟。对权限、删除、增量更新和索引切换做专项测试。

### 14. RAG 场景如何提升知识库召回与上下文匹配？

召回侧：按问题类型生成关键词、语义和过滤条件，多路并行后用 RRF/归一化融合；对表格、车型、法规等实体加入结构化字段和同义词。排序侧使用 Cross-Encoder 或规则 Rerank，并根据置信度动态扩大/缩小 k。上下文侧命中子块后取父章节，去重、按来源和时间排序，控制 token 预算。

上线后记录 query、候选、最终引用和用户反馈，针对漏召回、错召回、上下文过长分别修数据、索引、路由或 Prompt。

## 四、Vibe Coding 与开发规范

### 15. 如何理解 AI Coding 中的 Vibe Coding？安全可靠开发流程注意什么？

Vibe Coding 是用自然语言让模型快速生成/修改代码，适合原型和样板，但不能替代工程责任。安全流程是：先写需求和验收标准 → 让模型给方案和风险 → 小步生成 → 人工阅读 diff → 类型/静态检查 → 单元/集成测试 → 沙箱运行 → 依赖/密钥/权限扫描 → 代码评审 → 灰度发布与回滚。

禁止把生产密钥、隐私数据和未审查的模型代码直接投入线上；外部内容视为不可信输入，文件、命令和网络工具采用最小权限。

### 16. 使用 Vibe Coding 辅助开发时，人应重点关注什么？

关注需求是否被正确理解、接口/数据契约、异常和边界、并发与事务、安全权限、资源释放、可观测性、测试是否真的验证行为，以及生成代码的依赖许可证。逐段读 diff，要求模型解释关键假设；对 SQL、shell、鉴权、序列化和迁移脚本尤其不能盲信。

### 17. 拿到新开发需求，除了补充测试用例，还需提前做什么？

先澄清目标、非目标、用户和验收标准；阅读现有架构、接口、数据模型、部署和 `AGENTS.md`/项目规范；识别依赖、权限、兼容性、迁移、监控和回滚影响；拆分任务并估算风险。先写小型设计/接口契约和失败场景，再实现最小切片，最后补文档、指标和发布计划。

### 18. AGENTS.md 这类规则配置文件应包含什么开发规范和约束？

应包含项目范围、目录说明、构建/测试/格式化命令、代码风格、依赖和版本要求、接口/数据契约、禁止操作、权限/隐私要求、提交规范、验收标准和故障处理。规则要可执行、分层且版本化，明确优先级和适用目录；不要把秘密写入文件，也不要用含糊口号替代命令和边界。

## 五、算法题

### 19. LC11 盛最多水的容器：找组成最大容量的两根柱子

双指针从两端开始，容量为 `min(height[l], height[r]) * (r-l)`。每次移动较短的一侧，因为保留较短侧而移动较长侧，宽度变小且短板不会变高，不可能得到更优解。

```python
def max_area(height: list[int]) -> int:
    l, r, best = 0, len(height) - 1, 0
    while l < r:
        best = max(best, min(height[l], height[r]) * (r - l))
        if height[l] <= height[r]:
            l += 1
        else:
            r -= 1
    return best
```

时间复杂度 O(n)，额外空间 O(1)。边界包括空数组、长度 1、0 高度和很大的高度值（Python 不会溢出；其他语言用 64 位整数）。

### 20. 讲解整体解题思路、时间复杂度和空间复杂度

先定义面积公式和“移动短板”的不变量，再给出双指针流程，最后说明每个指针最多移动 n 次，所以时间 O(n)，只使用常数变量所以空间 O(1)。如果要求输出下标，同时在面积相同情况下取字典序最小/距离最短，要在更新 `best` 时补充明确的 tie-break 规则。
