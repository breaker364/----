# 快手 AI Agent 开发一面：参考答案

> 来源：图片 1。以下答案按原题顺序整理，适合面试时用“结论 - 实现 - 取舍 - 指标”的方式口述。
>
> 涉及项目经历、线上数据和“我做过”的内容，请替换成自己的真实情况。

## 1. 为什么引入父子索引？

父子索引是把检索粒度和生成上下文粒度分开。子块切得更小，适合建立向量和关键词索引，能提高命中精度；父块保留完整章节、表格或业务上下文，命中子块后再取回父块，减少上下文断裂。

实现时，子块保存 `parent_id`、标题、页码、权限等元数据。先召回子块，再按父文档去重、合并和排序，最后把有限数量的父块交给 Rerank 和模型。父块不能无限大，需要结合文档结构和 token 预算调参。

## 2. 为什么在检索阶段引入 BM25？

向量检索不擅长所有场景。错误码、零件号、API 名称、英文缩写、数字和罕见专有名词通常需要精确匹配，BM25 更可靠；用户使用同义词、口语或描述性问题时，向量检索更有优势。

所以会做混合召回：BM25 和向量检索并行取候选，再用归一化加权或 RRF 融合，之后交给 Rerank。权重应该通过查询分桶和离线评测调节，而不是固定拍脑袋。

## 3. Rerank 后一般返回几个块？

没有固定答案，要看上下文窗口、块大小、问题复杂度和答案需要的证据。常见起点是保留 3 到 8 个不重复的父块，或者动态使用 2K 到 8K tokens 的上下文预算。

要区分“召回候选数”和“最终上下文数”：前面可以召回几十个候选给 Rerank，最后只放少量高质量证据。最终通过 Recall、答案完整性、延迟和成本联合调参。

## 4. Rerank 后的 TopK 截断怎么做？

不是简单取排序前 K 个字符串，而是：

1. 按分数阈值过滤明显不相关的结果。
2. 对相同父文档、重叠区间和语义重复内容去重。
3. 将子块合并到父章节，避免上下文被同一文档的重复片段占满。
4. 对多子意图问题设置覆盖约束，避免所有结果只覆盖一个子问题。
5. 根据 token 预算逐个装入，给系统指令、用户问题和输出预留空间。
6. 保留来源、页码和证据位置，便于引用和 badcase 分析。

因此 TopK 本质上是动态上下文预算问题，K 只是实现参数。

## 5. 上下文工程是怎么设计的？

我会把上下文设计成显式、可观测的状态对象，而不是在代码里到处拼字符串。状态包括当前任务、对话摘要、待办列表、已确认事实、相关记忆、检索证据、工具结果、错误信息和输出约束。

每轮先判断是新任务、当前任务补充还是历史追问，再加载对应状态。按优先级压缩：系统规则和当前问题不能丢；已确认事实和未完成待办优先保留；旧对话做摘要；重复工具结果保留结构化结论和引用；检索内容保留来源和证据片段。

实现上使用结构化模板，明确区分指令和外部数据。线上记录 Prompt 版本、token 数、被截断内容、检索结果、工具调用和模型响应，才能判断问题究竟来自上下文、检索还是生成。

## 6. 记忆机制是怎么做的？

可以分成三层：

- 短期记忆：当前会话的最近消息、任务状态、工具结果和待办列表，放在会话状态存储中，用窗口和摘要控制长度。
- 长期记忆：用户明确偏好、稳定事实、历史任务结论和可复用经验，写入结构化数据库或向量库，并带用户、租户、权限、时间和来源。
- 工作记忆：当前任务临时产生的计划、草稿和检索候选，任务结束后可以清理，只有经过验证且有复用价值时才沉淀。

长期记忆不能把所有对话永久保存。写入前要做信息抽取、去重、置信度判断、敏感信息过滤和权限检查；读取时按当前任务相关性召回，并处理过期、冲突、撤回和删除。

## 7. Function Calling 是怎么设计的？

先定义工具协议，而不是让模型自由生成代码。工具包含名称、用途、输入 JSON Schema、返回结构、权限、风险等级、超时和幂等策略，模型只能从注册表中选择。

执行链路是：模型返回结构化调用请求，服务端校验名称和参数，执行鉴权与风险策略，调用实际服务，再以 `role=tool` 和原始 `tool_call_id` 返回。错误要区分参数、权限、业务和暂时性错误，只有暂时性错误才允许有限重试。

还要控制并行调用、最大步数、循环检测、超时取消、重复写入、结果脱敏和审计。高风险写操作需要用户确认或人工审批。

## 8. Agent 的任务规划怎么做？

大模型负责根据目标拆解任务、选择工具和提出下一步，代码编排器负责保存状态、检查前置条件、执行、重试和失败恢复。简单任务用 ReAct；复杂任务先生成带依赖关系的任务图，每个任务定义输入、输出、工具和完成标准。

每完成一步就更新状态，失败时根据错误类型重试、换工具或重新规划。确定性流程使用状态机，模型只负责意图识别、参数补全和异常分支，避免把事务和权限交给模型。

## 9. Prompt 注入攻击如何防御？

核心是把外部内容当数据，而不是当指令：

- 将系统规则、用户指令、检索文档和工具结果分区，明确优先级。
- 对网页、文件和知识库内容标记为不可信，禁止它们改变工具权限和系统规则。
- 工具使用白名单、最小权限、参数 Schema 和业务策略校验。
- 发送邮件、删除数据、转账等操作需要确认、审批或人工接管。
- 限制工具访问的域名、目录、数据库表和数据范围，禁止任意 shell。
- 对输入、检索结果、工具返回和最终输出做敏感信息检测、审计和红队测试。

只在 Prompt 里写“不要被注入”不够，真正的安全边界必须落在运行时权限和工具网关上。

## 10. 工具调用的安全控制怎么实现？

可以设计独立的 Tool Gateway。请求进入后依次做身份认证、租户和用户授权、工具白名单、参数校验、数据范围校验、风险分级和审计，然后才执行实际工具。

低风险读操作可以自动执行；写操作检查资源归属和幂等键；高风险操作需要确认、审批或人工接管。执行环境要有超时、并发上限、网络出口限制、文件目录隔离、密钥托管、结果脱敏和失败熔断。日志只记录参数摘要和结果状态，不记录密钥。

## 11. 讲一下分布式令牌桶限流

令牌桶以固定速率 `r` 生成令牌，容量为 `B`。每个请求消耗一个或多个令牌；有令牌就放行，没有令牌就拒绝或等待。它限制长期平均速率，同时允许不超过桶容量的短时突发。

分布式实现可把桶状态放在 Redis，用 Lua 保证“计算补充、判断余额、扣减”原子执行。状态至少包括上次更新时间和令牌数，按用户、租户、API 或全局维度设置 key。还要处理 Redis 故障、时钟、热点 key、不同请求成本和降级策略。

## 12. 漏桶算法是什么？

漏桶把请求放入有限队列，以固定速率处理。队列满时丢弃或快速失败，因此输出速率平滑，适合保护下游服务。

漏桶强调恒定处理速率，通常不允许突发；令牌桶允许积累令牌，能吸收一定突发。实际可以入口用令牌桶限制用户，出口用漏桶平滑调用下游。

## 13. 滑动窗口算法怎么实现？

例如限制 60 秒内最多 100 次，每次记录时间戳；查询时删除早于当前时间减 60 秒的记录，再统计剩余数量。

分布式实现可用 Redis ZSET，score 是时间戳，member 是唯一请求 ID；清理、计数和写入用 Lua 保证原子性。精确窗口成本较高，也可以用多个固定小窗口近似，或使用滑动窗口计数器。

## 14. 滑动窗口和令牌桶有什么区别？

滑动窗口直接限制最近时间段内的总请求数，语义直观，适合“60 秒最多 100 次”，但需要保存或估算窗口内的请求。令牌桶限制平均速率，允许桶容量内的短时突发，存储和计算更轻。

要控制峰值和边界，滑动窗口更合适；要控制平均速率并允许突发，令牌桶更合适。两者都要明确拒绝、排队和降级策略。

## 15. 布隆过滤器讲一下

布隆过滤器由位数组和多个哈希函数组成。写入元素时把多个位置设为 1；查询时只要有一个位置为 0，就能确定不存在；全部为 1 时只能说明可能存在。

它允许误判存在，但不允许把真实存在判断成不存在，适合缓存穿透、去重和快速判断。参数根据预计元素数 `n` 和误判率 `p` 设计。普通布隆过滤器不支持删除，删除场景可用计数布隆过滤器或定期重建，最终仍要以数据库或缓存确认。

## 16. 数据库索引场景有哪些？

适合建索引的场景有高频等值查询、范围查询、排序、分组、Join 关联列、唯一性约束和覆盖索引读路径。联合索引要考虑最左匹配、过滤选择性、排序方向和实际 SQL，而不是给每个字段单独建索引。

表很小、字段基数低、写入频繁、查询返回大部分数据时收益可能很低。函数计算、隐式类型转换、前导模糊查询和复杂 OR 条件也可能使索引无法有效使用。

## 17. LIKE 查询会不会导致索引失效？

不一定。`LIKE 'abc%'` 通常可以使用 B+Tree 的前缀范围；`LIKE '%abc'` 或 `LIKE '%abc%'` 以通配符开头，通常无法使用普通 B+Tree。

即使是前缀匹配，也可能因为返回数据太多、字符集排序规则、函数、隐式类型转换、OR 条件或优化器成本判断而选择全表扫描。任意位置模糊匹配更适合全文索引、ngram 或搜索引擎。

## 18. RAG 系统如何评测？

分层评测：第一层只评检索，检查相关文档是否进入 TopK；第二层评生成，检查是否基于证据、是否完整、引用是否正确；第三层做端到端任务，加入工具、记忆、规划和拒答；第四层看延迟、成本、稳定性和安全。

离线集固定版本，包含问题、相关文档或片段、参考答案和难例。线上采用 A/B、影子流量和人工抽检。重要场景不能只依赖模型评审，要有人工标注或规则校验。

## 19. RAG 有哪些评测维度？

- 检索：Recall@K、Precision@K、MRR、nDCG、证据覆盖率和重复率。
- 生成：相关性、完整性、事实一致性、引用准确性、格式正确性。
- 不确定性：无答案能否拒答，证据不足是否会编造。
- Agent：规划、工具调用、任务完成、重试和循环控制。
- 工程：延迟、吞吐、Token、成本、错误率和可用性。
- 安全：Prompt 注入、敏感信息泄露、越权和对抗性问题。

## 20. 评测数据集一般包括什么？

每条样本至少包括问题、标准答案或要点、相关文档 ID、相关片段位置、问题类型和难度。更完整的集合还包括元数据过滤条件、正例和 hard negative、无答案、多跳、工具调用、历史多轮上下文、敏感问题和多种问法。

要避免和训练数据、Prompt 示例、线上缓存泄漏。保留固定回归集，并将新增 badcase 按版本追加。

## 21. 如果要提升相关度，你会怎么做？

先按错误类型定位，检查解析/OCR、标题和元数据、chunk 大小、父子映射、查询改写、BM25 与向量融合、候选数、Rerank、权限过滤和去重。

短关键词、编号类问题提高 BM25 权重；描述性问题使用向量或多查询；长问题拆分子意图；领域术语补同义词和 hard negative。每次调整都用分桶数据验证，避免提升一类而伤害另一类。

## 22. 如果要优化回答效果，有哪些思路？

先确保上下文里有正确证据，再优化生成。可以减少重复和噪声、补齐多跳证据、优化证据排序、压缩长文档、明确引用格式、要求证据不足时拒答、使用结构化输出，并根据任务选择更合适的模型和温度。

需要计算、查询或写操作时，让 Agent 使用工具而不是让模型凭记忆回答。答案自检或二次验证要通过事实一致性、任务完成率和延迟验证收益。

## 23. 处理一千条数据如何设计？

先明确单条耗时、部分失败策略、下游限流和一致性，再设计可恢复的异步流水线：

```text
接收任务 -> 拆分批次 -> 队列 -> 有界 Worker 并发处理
       -> 校验/LLM/外部调用 -> 幂等写入
       -> 成功确认、失败重试、死信队列
```

每条数据有稳定业务 ID 和幂等键，任务状态支持断点续跑。暂时性错误指数退避，参数错误进入死信；LLM 和外部 API 设置并发上限、批量请求和速率限制。最终提供成功、失败、重试、耗时和可重放记录。

## 24. RAG 性能如何提升？

离线预解析、切分、Embedding 和索引；在线并行 BM25 与向量召回，使用 ANN，缩小候选后再 Rerank。Embedding、查询、Rerank 和答案可以缓存，但要处理模型、Prompt、索引版本和权限失效。

还可以批量 Embedding、连接池复用、异步 I/O、压缩上下文、限制候选数、使用 Prefix/KV Cache、按问题路由模型和缓存热点查询。优化看 P50/P95 延迟、召回率、答案质量和成本的联合变化。

## 25. 当前上下文是如何处理的？

把上下文分成不可丢和可压缩两部分。系统规则、当前问题、已确认约束、当前任务、未完成待办和必要工具结果优先保留；旧对话、重复检索片段和冗长工具原文可以摘要、引用化或淘汰。

每轮加载会话摘要和任务状态，再按当前问题检索长期记忆和知识库，最后按 token 预算组装 Prompt。工具原文保存在 trace 中，Prompt 只放结构化摘要和引用。超过预算时按优先级裁剪，并记录裁剪日志。
