# 滴滴 Agent 开发二面：参考答案

> 来源：图片 2。题目按“架构与源码、Skill、Agentic RAG、开放检索、动机”整理。
>
> Claude Code、Hermes 等框架可能存在不同仓库版本，面试时应先确认具体源码版本。下面给出可迁移的比较框架，不把某一版本细节说成绝对结论。

## 一、架构对比与源码理解

### Q1. Claude Code 和 Hermes 在设计模式上有什么区别？为什么不同场景会有不同设计？

以常见实现为例，Claude Code 更偏面向编码任务的工具循环：一个主 Agent 持有工作区状态，通过 shell、编辑器、搜索、Git 和测试工具不断观察、修改和验证；权限确认和工作区状态是重要边界。

Hermes 类框架通常更强调可扩展的 Agent runtime，把 Skills、工具注册、记忆或多步骤编排做成显式抽象，便于复用到不同领域。具体实现要以面试官指定的仓库为准，比较时可以从架构、状态、工具、记忆、安全和观测六个维度展开。

不同应用场景的设计不同，是因为目标函数不同：

- 编码 Agent 需要频繁观察和修改文件、运行测试、支持人类审批和回滚。
- 企业流程 Agent 更关心权限、审计、稳定状态、任务编排和多租户。
- 实时客服更关心低延迟、固定流程和可控输出。

因此不能只讨论哪种模式先进，要看任务不确定性、工具风险、状态生命周期、延迟和成本。大模型负责不确定判断，代码负责状态、权限、重试、事务和确定流程。

### Q2. Claude Code 和 Hermes 在记忆系统上有什么差别？

可以从记忆对象和生命周期比较。编码 Agent 的短期记忆主要是当前会话、工作区文件、命令输出、测试结果和 Git diff；上下文过长时需要摘要，但文件和测试结果本身仍是可重新验证的外部事实。

通用 Agent runtime 往往会显式管理会话状态、任务状态、Skill 经验和用户长期偏好，并通过数据库或向量库持久化。编码场景中代码当前状态比模型历史记忆更可靠；业务场景中的用户偏好、历史工单和流程结果才更适合长期记忆。

我的原则是按信息的稳定性、可验证性、隐私和复用价值决定是否记忆。临时中间结果进入工作记忆，跨轮仍成立的事实进入长期记忆，未经确认的模型推断不能直接写入长期记忆。

### Q3. 读完源码后，回看之前项目，哪些地方可以做得更好？

我会从“能运行”提升到“可控、可测、可恢复”：

1. 把 Agent 状态、消息、工具调用和任务结果定义成稳定协议，减少模块之间靠字符串传递。
2. 把确定性流程下沉到状态机或编排器，模型只负责判断和参数补全。
3. 增加工具网关、权限、确认、超时、重试、幂等和审计，避免工具直接暴露给模型。
4. 对 Prompt、Skill、模型和索引做版本管理，保留每次运行 trace，支持回放。
5. 分开短期上下文、长期记忆和任务工作区，增加摘要、淘汰、冲突处理和隐私控制。
6. 建立离线回归集、badcase 分类和线上指标，不再只靠几条演示样例判断效果。

## 二、项目深挖：Skill 设计与工程落地

### Q4. 企微群商机智能体的 Skill 如何设计？如何自动捡群聊、提取商机并写表格？

我会把 Skill 设计成“声明式能力 + 受控工具 + 可评测流程”，而不是一段很长的 Prompt。一个商机 Skill 至少包括触发条件、输入字段、步骤、工具、输出 Schema、权限、失败策略和评测样例。

整体链路是：

```text
群聊事件/增量同步
  -> 按会话和消息 ID 去重、补齐上下文
  -> 识别商机相关消息
  -> 提取客户、需求、产品、预算、时间、联系人等字段
  -> 输出字段值、证据消息和置信度
  -> 规则校验与低置信度人工确认
  -> 表格幂等 upsert
  -> 回写处理状态、日志和审计记录
```

“自动捡群聊”不能靠模型读取所有群，而应通过企业微信允许的事件订阅或增量同步接口，在租户、群和用户权限范围内获取消息。用 `message_id` 去重，按群、线程和时间窗口聚合上下文；隐私字段脱敏。

抽取结果使用结构化 Schema，例如 `lead_id`、客户名称、需求、预算、阶段、下一步、证据消息 ID、置信度和更新时间。低置信度或字段冲突时进入人工确认，不直接覆盖已有信息。写表使用业务唯一键和幂等 upsert，记录来源消息、Skill 版本、模型版本和操作者。

评估看字段准确率、召回率、重复率、误报率、人工修改率、端到端延迟和写入成功率，而不是只看写入行数。

## 三、项目深挖：Agentic RAG 系统设计

### Q5. 所有项目中哪个最有技术挑战？如何克服？

可以选择 Agentic RAG 来回答：

> 最有挑战的不是把模型接起来，而是让系统在真实问题上稳定找到证据并完成任务。难点主要有三类：文档结构复杂，简单切块会丢失标题、表格和跨段关系；问题需要查询改写、分解、多个数据源和证据验证；Agent 会引入循环、错误工具调用和不可复现问题。
>
> 我的做法是把解析、索引、召回、Rerank、上下文编排和生成拆成可观测阶段；召回侧使用父子索引、BM25 与向量混合，对复杂问题做查询分解；执行侧用状态机约束工具权限、重试和最大循环次数；评测侧建立带相关片段和 hard negative 的数据集，分别看检索、回答和端到端任务指标。

面试时要补充一个真实 badcase、自己的判断、采取的改动和指标变化，形成“问题 - 方案 - 结果”的闭环。

### Q6. 预处理已经做摘要，为什么还需要 Agentic RAG？

摘要解决离线压缩和索引问题，不能替代在线推理。传统 RAG 加摘要适合单轮、单主题、证据边界清晰的问题；Agentic RAG 在以下场景有价值：

- 问题包含多个子问题，需要拆分后分别检索。
- 需要根据第一次结果决定下一次查询或调用其他数据源。
- 需要跨文档、多跳证据拼接和冲突验证。
- 需要执行查询、计算、写入等工具，而不是只生成文字。
- 需要根据证据不足决定继续检索、澄清或拒答。

但它不是默认更好。简单问题、固定流程和低延迟场景应优先使用传统 RAG。所谓“读和写都搞不定”，通常是单次召回无法覆盖复杂读取路径，且结果还要写入外部系统并保证状态、权限和幂等，这时才需要 Agent 编排。

## 四、开放性问题：信贷风控检索系统

### Q7. 如何从黑产库召回行为模式相似的历史案例？和常规 RAG/Agentic RAG 有什么区别？

这个问题不能直接把交易文本做普通语义向量相似度。目标是发现异常行为模式，检索对象应是行为序列、时序统计和关系结构。

#### 数据与特征

- 将交易、设备、账号、IP、地址、商户和商品抽象成事件与关系，保存时间、间隔、金额分布、频率、失败率、设备切换、账号关联等特征。
- 对商户、店铺和商品做角色化或类别化编码，学习“短时间多账号共用设备”等不易被换店铺绕过的模式，而不是记住具体名称。
- 同时保留规则特征、统计特征、序列特征和图特征。序列可以用时间编码、Transformer/GRU 或 DTW 表示；关系密集时加入图查询或图 Embedding。
- 黑产库不是完整负样本，需要考虑正例稀缺、标签延迟、选择偏差和 hard negative，必要时按 Positive-Unlabeled 思路处理。

#### 检索链路

```text
当前交易事件
  -> 实时特征抽取和标准化
  -> 规则/范围过滤
  -> 行为序列向量召回
  -> 图关系或统计模式召回
  -> 精确特征相似度与时间衰减重排
  -> 返回相似案例、匹配特征、标签和证据
  -> 风险模型/规则/人工审核综合决策
```

多路结果可以用加权融合、RRF 或学习排序融合，权重通过时间切分的验证集校准。相似案例要返回“为什么相似”，例如设备共用、交易间隔、金额模式和账号关联，而不是只返回一个相似度。

#### 针对场景的调整

- 常规 RAG 关注文本语义相关性，这里改成行为、时序、图关系和异常模式相关性。
- 不能把商户和商品名称作为主要特征，否则黑产换店铺、换类目就能绕过。
- 检索结果是风险模型的证据，不让 LLM 单独作最终风控决定；要做阈值校准、成本敏感评估、人工复核和可解释输出。
- 在线主链路使用确定性检索和模型推理，低风险、证据不足或解释场景再由 Agent 补充查询。
- 评测关注 AUC、PR-AUC、召回率、误报率、漏报率、分层召回、延迟和概念漂移，不只看 Recall@K。

## 五、动机与反问

### Q8. 这次换工作的主要原因是什么？

可以采用“事实 + 发展方向 + 岗位匹配”的表达：

> 目前的工作让我积累了 Agent、RAG 和工程落地经验，但现在更希望参与规模更大、链路更完整的智能体系统，从 Demo 和局部能力深入到架构、评测、稳定性和业务指标。下一份工作我更看重真实场景、技术深度、工程规范以及承担完整结果的机会。离开当前公司主要是职业发展和岗位匹配考虑。

不要把重点放在抱怨公司、领导或同事上，也不要把离职原因说成与应聘岗位无关的临时因素。

### Q9. 如何理解“效率提升”和“效果提升”不能划等号？

效率提升是更快、更省人力或更低成本地完成同一件事；效果提升是最终业务指标变好，例如准确率、转化率、风险识别率或客户满意度提高。Agent 可能让特征开发更快，但如果新增特征没有信息增益、标签质量不足或模型瓶颈在其他地方，最终效果不一定提升。

项目立项时先定义北极星指标、基线、实验周期和归因方法，再决定是否引入 Agent。做小流量或离线回放，对比人工、原流程和 Agent 流程，确认特征质量以及下游模型的增量价值。复盘时把节省时间和业务效果分别统计，不能用前者替代后者。
