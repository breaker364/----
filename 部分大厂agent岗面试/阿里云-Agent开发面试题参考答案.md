## 3. 介绍一下你常用的 Skill

**回答：**

Skill 可以理解为可复用的任务规范或能力模块。它通常包含触发条件、输入输出约定、执行步骤、工具使用方式、约束和异常处理。

我会优先使用几类 Skill：

- **代码开发类**：读取项目结构、遵循项目约定、实现功能、运行测试；
- **检索和文档类**：搜索资料、读取文档、提取结构化信息；
- **数据处理类**：解析 CSV/Excel/PDF，完成清洗、统计和导出；
- **浏览器或外部系统类**：导航页面、填写表单、调用接口，但需要权限和副作用控制；
- **验证类**：运行测试、检查输出文件、核对结果后再汇报完成。

好的 Skill 不应该只是一个很长的提示词，而应当让任务边界、输入输出和验证方式都比较明确。

## 4. 这些 Skill 之间有什么区别？看过知名 Skill 里面是怎么写的吗？

**回答：**

Skill 的区别主要体现在四个方面：

- **触发范围不同**：有的处理一类任务，有的只处理一个动作；
- **依赖不同**：有的只需要本地文件，有的需要浏览器、数据库或外部 API；
- **执行方式不同**：有的偏知识说明，有的包含严格的操作流程；
- **风险不同**：读取文件的 Skill 风险较低，发送消息、删除文件、修改线上数据则需要确认、权限和回滚机制。

知名 Skill 的写法通常会明确：什么时候使用、什么时候不要使用、输入是什么、步骤是什么、输出是什么、失败时怎么办，以及不能违反的安全约束。

## 5. 自己写过 Skill 吗？用来做什么？写 Skill 要注意什么？

**回答：**

设计时主要注意：

1. 触发条件清晰，避免与其他 Skill 重叠；
2. 输入、输出和文件路径约定明确；
3. 步骤足够具体，但不要把所有场景写成不可维护的巨型提示词；
4. 工具权限最小化，对写入、删除、发送等副作用设置确认或保护；
5. 失败、超时、重试和部分成功要有处理方式；
6. 对结果做可验证的检查，不能只依赖模型说“已完成”；
7. 记录日志和版本，方便排查 Skill 为什么被触发、做了什么。

## 9. 你觉得写好 Harness，哪些是必须的？

**回答：**

一个可用的 Agent Harness 至少需要：

1. **统一状态**：保存用户输入、历史消息、工具结果、当前阶段和任务元数据；
2. **模型适配层**：统一不同模型的调用、流式输出、超时和错误格式；
3. **工具注册与执行器**：包含 schema 校验、权限、超时、重试、结果截断和审计；
4. **清晰的 Agent Loop**：决定何时思考、调用工具、继续执行或结束；
5. **可靠的终止机制**：最大步数、超时、预算、重复动作检测和人工接管；
6. **可观测性**：记录请求、步骤、工具调用、耗时、错误和最终结果；
7. **安全控制**：提示词注入防护、敏感数据保护、最小权限和高风险操作确认；
8. **评测和回放**：可以用固定任务重放，比较成功率、成本、延迟和错误类型。

## 10. Agent 工具调用有哪些方式？

**回答：**

常见方式包括：

- **原生 Function Calling/Tool Calling**：把工具名称和 JSON Schema 传给模型，模型返回结构化调用请求；
- **结构化输出**：让模型只输出符合 schema 的 JSON，再由程序决定是否执行；
- **ReAct 风格**：模型在“思考/行动/观察”之间循环，行动部分对应工具调用；
- **代码执行或 DSL**：模型生成受限代码、SQL 或工作流指令，由沙箱或执行器运行；
- **协议化工具接入**：例如通过 MCP 一类协议发现并调用外部工具；
- **固定工作流编排**：模型只负责分类或填参数，流程由程序预先定义。

生产系统通常会把模型决策和真正执行分开：模型提出调用意图，运行时做权限、参数、风险和资源检查后才执行。

## 11. 怎么保证 Agent 按需调用工具？

**回答：**

不能只靠一句提示词保证，需要多层约束：

1. 工具描述写清楚用途、适用条件、输入输出和禁止场景；
2. 给参数定义严格 JSON Schema，并在服务端二次校验；
3. 只把当前任务可能需要的工具暴露给模型；
4. 对工具调用做权限、参数范围、用户身份和风险等级检查；
5. 使用路由器或分类器先筛选工具，减少模型选择空间；
6. 通过最大步数、超时、重试上限和重复调用检测控制循环；
7. 对关键工具增加确认、幂等键、审计日志和人工兜底；
8. 用真实任务评测“该调用时调用、不该调用时不调用”的准确率。

## 12. 为什么有了 Agent 的设计？什么时候使用 Agent 合理？

**回答：**

Agent 的价值是让模型根据当前状态动态决定下一步行动，适合目标明确但路径不固定、需要多轮工具调用、需要根据中间结果调整计划的任务，例如复杂检索、代码修复、跨系统流程和异常处理。

如果流程固定、规则明确、延迟要求极低，普通函数、工作流或传统服务通常更可靠。使用 Agent 前应先确认：任务是否真的需要动态决策，错误是否可接受，工具是否可控，是否有超时、预算和人工兜底。

## 13. 了解 Agent 之间的通信方式吗？

**回答：**

常见方式有：

- **直接消息传递**：Agent A 把任务和上下文传给 Agent B，适合简单串联；
- **共享状态/黑板**：多个 Agent 读写统一任务状态，适合协作但要处理并发和数据覆盖；
- **编排器调度**：由 Supervisor 分派子任务并汇总结果，职责相对清晰；
- **事件总线或队列**：通过事件异步通信，适合长任务和解耦；
- **RPC/API 或标准协议**：将 Agent 封装为服务，便于跨进程、跨语言和权限管理。

设计时应约定消息 schema、任务 ID、超时、重试、幂等、错误传播、权限和上下文边界，避免 Agent 之间无限转发或重复工作。

## 14. 设计一个 Agent Loop，要注意什么？

**回答：**

一个基本循环是：接收目标 → 读取状态 → 请求模型 → 判断最终回答或工具调用 → 校验并执行工具 → 写回观察结果 → 继续循环。

重点注意：

1. 状态结构清晰，区分用户消息、模型消息、工具结果和业务状态；
2. 明确定义结束条件，不能只等待模型“自觉停止”；
3. 设置最大步数、总超时、Token/费用预算；
4. 对网络错误、模型错误和工具错误分类处理，重试要有上限；
5. 工具执行要有权限、参数校验、幂等和副作用保护；
6. 对重复工具调用、空转和相同结果循环进行检测；
7. 控制上下文长度，压缩历史并保留关键状态；
8. 全链路记录 trace，能够回放每一步；
9. 高风险任务支持人工确认和中途停止；
10. 通过离线评测和线上指标验证成功率、成本、延迟和安全性。

可以用伪代码概括：

```text
state = init(user_input)
for step in range(max_steps):
    response = model(state.messages, available_tools)
    if response.is_final:
        return response.answer
    call = validate_tool_call(response.tool_call)
    result = execute_with_policy(call)
    state = update(state, response, result)
    if timeout_or_budget_exceeded(state):
        return fallback_or_human_handoff(state)
return failure("达到最大步数")
```
