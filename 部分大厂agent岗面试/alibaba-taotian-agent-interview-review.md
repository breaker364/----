# 阿里淘天 Agent / Harness 面试复盘

> 适用场景：面试后复盘学习。本文根据题目截图整理，不代表候选人的真实项目经历。
>
> 标记说明：`[需替换]` 表示必须换成自己的项目事实；`[不确定]` 表示面试时不掌握具体实现，应诚实说明边界，不要为了显得熟悉而编造。

## 一、整体复盘思路

这组题的核心不是背某个 Agent 框架，而是看能否把“模型生成”变成一个可控的软件系统。回答时建议始终围绕四件事展开：

1. 任务如何拆解、路由和编排；
2. 工具调用、状态、重试、超时、恢复如何工程化；
3. 如何评测正确性、稳定性和成本；
4. 如何把一次失败定位到模型、Prompt、工具、数据或流程环节。

如果问到自己的项目，推荐使用：背景 → 目标 → 方案 → 关键难点 → 结果 → 复盘。没有真实数据时，可以说“这里我没有保留准确指标，不能确认具体数值；我当时主要通过……验证”。

## 二、问题逐题复盘

### 1. 你提到复杂任务会引入 Plan-and-Execute 模式，复杂任务能举个例子吗？

**考察点**：是否理解什么时候需要规划，是否能区分规划、执行和校验。

**复盘回答**：

复杂任务通常有多个依赖步骤、多个工具，或者中间结果会影响后续决策。例如“根据一份 PDF 需求文档生成一个前端页面并完成自测”：先解析文档和提取约束，再形成页面结构，再生成代码，随后运行构建和截图校验，最后根据失败结果修改。它不是让模型一次性输出最终答案，而是先得到一个可观察的任务计划，再逐步执行。

Plan-and-Execute 一般包含：

- Planner：把目标拆成有依赖关系的步骤，定义输入、输出和完成条件；
- Executor：按计划调用工具或子 Agent；
- Verifier：检查步骤结果，不合格时重试、修订计划或中止；
- State Store：保存计划、步骤状态、产物引用和错误信息。

它适合“步骤较多、可验证、执行时间较长”的任务；简单问答采用单轮 ReAct 往往更省 Token、更低延迟。

**需要补充**：`[需替换]` 你自己的真实任务、拆成了几步、每步使用什么工具、哪一步最容易失败。

### 2. 在提示词中设置好 Plan 的流程交给 Harness，做 Plan 有什么优缺点？

**复盘回答**：

把计划流程交给 Harness，优点是计划格式、状态流转、重试、超时和审计可以统一，模型只负责提出计划或局部决策，系统更容易测试和恢复。计划也能作为中间产物展示给用户，方便确认和追责。

缺点是固定流程可能限制模型对任务的适应能力；计划本身可能错，后续只是“按错计划稳定执行”；每个阶段都调用模型会增加延迟和成本；如果状态模型设计得不清楚，Prompt、Harness 和业务代码会互相重复。

更稳妥的做法是“模型负责语义规划，Harness 负责生命周期约束”：计划必须是结构化数据，步骤类型只能从白名单中选择，依赖关系和权限由 Harness 校验，执行中允许有限的 re-plan，但不能无条件无限改计划。

### 3. 你有对比过这两个方案吗？

这里的“两个方案”可能指 ReAct 与 Plan-and-Execute，也可能指把流程写进 Prompt 与由 Harness 编排。面试后复盘时不要直接假设面试官指的是哪两个，可以先确认：“您是想比较 ReAct 和 Plan-and-Execute，还是 Prompt 编排和 Harness 编排？”

一个通用对比是：

| 维度 | ReAct | Plan-and-Execute |
|---|---|---|
| 决策方式 | 边想边做 | 先规划再执行 |
| 适合 | 短任务、路径不确定 | 长任务、多依赖、可验收 |
| 优点 | 灵活、首字节快 | 可观测、可恢复、易展示 |
| 风险 | 循环、漂移、难复盘 | 计划错误、额外延迟 |
| 工程要求 | Loop、工具限制 | 计划 schema、状态机、重规划 |

不能只说“Plan-and-Execute 更先进”，要结合任务长度、失败代价和可验证性做选择。

### 4. 大模型会比较发散，你是通过什么方式将它的思考、行为收敛到想要的实现？

**复盘回答**：

我会把“收敛”拆成输入约束、输出约束、执行约束和结果校验四层：

1. 输入：明确目标、边界、不可做事项、已有上下文和验收标准；
2. 输出：使用 JSON Schema 或结构化字段，限定动作、参数和完成条件；
3. 执行：工具白名单、参数校验、权限控制、预算、超时和最大循环次数；
4. 校验：用测试、规则、数据库状态或第二个验证步骤检查结果，不把模型自称“完成”当成完成。

Prompt 只能降低概率，不能替代系统约束。对于高风险动作，还需要人工确认或审批。调参时会固定评测集，逐项比较 Prompt、模型、工具描述和上下文变化，避免凭几条样例感觉调优。

### 5. 项目中提到的 Multi-Agent 流程，主要面向什么样的需求？

**复盘回答**：

Multi-Agent 不是把一个任务随便拆给多个模型，而是在任务存在明显的角色边界、并行空间或专业知识差异时使用。例如一个 Agent 负责需求分析，一个负责代码实现，一个负责测试和审查；或者多个检索 Agent 并行获取不同来源，汇总 Agent 负责冲突消解。

引入前要问三个问题：单 Agent 加工具是否已经足够？拆分后是否能定义清晰的输入输出？多 Agent 带来的质量提升是否值得额外 Token、延迟和协调复杂度？如果角色之间共享大量上下文、没有独立验收标准，Multi-Agent 可能只是增加故障面。

### 6. 你在这个项目中主要负责什么？把整个过程画出来展示一下

不要把团队成果全部说成自己完成。推荐回答模板：

> 我主要负责 `[需替换：例如 Harness 状态机和执行链路]`，与 `[需替换：同事/团队]` 协作完成 `[其他部分]`。整体链路是：用户请求 → 任务分类 → 生成/校验计划 → 调度步骤 → 工具或 Agent 执行 → 结果校验 → 持久化与返回；任一步失败都会进入重试、修订计划或人工介入分支。

可以用下面的简图辅助说明：

```text
Request
  │
  ▼
Task Router ──简单任务──> Direct Answer
  │
  ▼
Planner → Plan Schema 校验 → Harness 调度器
                                      │
                 ┌────────────────────┼───────────────────┐
                 ▼                    ▼                   ▼
              Tool/Agent A        Tool/Agent B          Verifier
                 │                    │                   │
                 └────────────── State Store ◄────────────┘
                                      │
                         完成 / 重试 / Re-plan / 人工确认
```

### 7. 需求阶段中 PRD 有什么区别？文档内容是如何生成的？如何保证正确性？

**复盘回答**：

需求描述、PRD 和技术设计不是一回事。需求描述回答“为什么做、解决谁的问题”；PRD 将用户流程、功能范围、异常场景和验收标准具体化；技术设计进一步说明接口、数据、模块、状态和实现约束。

文档生成可以采用“提取事实 → 归纳结构 → 生成草稿 → 规则校验 → 人审”的流程。先把原始需求中的实体、约束和例外抽取出来，避免直接让模型自由发挥；生成时要求每条结论能追溯到原文或明确标注为假设；最后用字段完整性、术语一致性、链接有效性、示例可执行性和人工抽样检查。

“正确”至少包括事实正确、范围正确、逻辑正确和可执行。模型生成的 PRD 不能作为唯一事实源。

### 8. 针对前端需求的开发中，样式、UI、还原度这些是如何保证的？

**复盘回答**：

前端还原不能只依赖 Prompt。输入侧需要明确设计稿、屏幕尺寸、字体、颜色、间距、组件状态和交互；实现侧使用统一 Design Token 和组件库；验证侧通过固定视口截图与设计稿做视觉对比，并配合 DOM、像素或视觉模型检查。

对于模型生成代码，我会要求先分析布局和组件层级，再实现，再运行 lint/build 和截图检查。需要记录“设计稿缺失、字体不可得、素材比例不明”等不确定项。像素级一致性不一定是唯一目标，还要检查响应式、可访问性、键盘操作和真实数据下的溢出。

### 9. 简历中提到的异常恢复是如何实现的？

**复盘回答**：

异常恢复的关键是让步骤可重放、状态可判断、产物可定位。每个步骤至少记录 `task_id`、`step_id`、输入摘要、状态、尝试次数、开始/结束时间、产物引用和错误分类。错误分为可重试的临时错误、需要换参数或换模型的业务错误、不可重试的权限/参数错误。

恢复时先读取最后一个可信 checkpoint，判断该步骤是否已经产生副作用，再决定继续、补偿还是人工确认。不能简单地“从失败处再执行一次”，因为重复写入、重复扣费或重复发送消息可能造成更大问题。

### 10. 重试机制是怎么设置的？比如开发阶段长时间未返回消息，是怎么处理的？

重试要按错误类型配置，而不是所有异常都重试。常见策略包括有限次数、指数退避、随机抖动、总预算和熔断。模型调用通常要区分连接超时、服务端 5xx、限流、上下文超限、工具业务失败和模型输出格式错误。

长时间未返回时，先确认是客户端无响应、网关超时、模型仍在生成，还是下游工具卡住。链路上要有 request ID、阶段级心跳和超时日志。可以取消请求、保存中间状态、返回可恢复的任务 ID，或进入后台异步执行；不要盲目重试导致两个执行实例同时写入。

### 11. 如何判断是开发时间比较长还是已经超时或挂了？这时候怎么处理？

不能只用“超过 N 秒”判断。要结合阶段预算、心跳、事件流、工具进程状态和最后一次进展时间。一个任务可能在长时间编译，但仍有日志和 CPU 活动；另一个任务可能立即卡死，没有任何心跳。

可以为任务定义：总 deadline、阶段 timeout、heartbeat interval、最大无进展窗口。判断为卡住后先尝试取消和收集诊断信息，再根据步骤是否幂等决定恢复或重跑。用户侧返回“仍在执行/可查询状态/已失败并可重试”，而不是无限等待。

### 12. 你的幂等性体现在什么地方？

幂等性是重试和恢复的前提，至少体现在：

- 请求层：客户端重试使用幂等键；相同 key 返回同一任务结果；
- 步骤层：`task_id + step_id` 唯一，重复消费不会重复创建产物；
- 工具层：写操作带业务幂等键，或采用去重表/唯一约束；
- 事件层：消费者记录 event ID，重复事件只确认不重复处理；
- 外部副作用：不能保证幂等时使用状态查询、补偿操作或人工确认。

仅仅给每次请求加 UUID 不等于幂等；如果重试时生成了新的业务动作 ID，仍可能重复产生副作用。

### 13. 某个阶段性坏掉，重启的时候是如何恢复？

重启恢复可以按以下顺序：读取任务状态 → 找到最后一个 checkpoint → 查询该步骤的执行记录和外部副作用 → 将 `RUNNING` 但没有心跳的步骤标为 `UNKNOWN` → 对可确认已完成的步骤补记完成，对无法确认的步骤执行查询/补偿/人工确认 → 从安全边界继续。

状态设计不应只有成功/失败，建议至少有 `PENDING、RUNNING、SUCCEEDED、FAILED、CANCELED、TIMED_OUT、UNKNOWN、WAITING_APPROVAL`。进程重启与任务失败是两件事，恢复器要能处理“进程死了但外部请求其实成功”的情况。

### 14. 每个阶段的执行状态都会保存吗？保存在什么地方？

通常会保存，但保存粒度取决于成本和恢复要求。任务级和步骤级状态应进入可靠的持久化存储；大文本、日志和生成文件放对象存储；缓存和分布式锁放 Redis 一类的短期存储；关键状态变更写审计日志或事件表。

一种记录结构是：

```text
task(id, status, version, deadline, created_at)
step(task_id, step_id, status, attempt, input_ref, output_ref, error, heartbeat_at)
event(task_id, step_id, event_id, type, payload_ref, created_at)
```

要注意版本号、乐观锁、保留周期、脱敏和恢复时的一致性。`[不确定]` 如果不知道具体项目使用 MySQL、Redis、对象存储还是工作流引擎，不要猜；可以说“我需要确认当时的部署实现，但原则上任务状态与大产物会分离保存”。

### 15. 你提到流程通过 workflow script 驱动，为什么会有这样的设计？

Workflow script 的价值是把可变的业务流程从固定代码中抽出来，用声明式步骤描述依赖、输入输出、重试、超时和权限。这样新流程可以复用执行引擎，运营或研发也更容易审查流程差异。

代价是脚本语言/Schema 需要版本管理、静态校验、权限沙箱和调试工具；脚本过于自由会变成另一种难维护的编程语言。我的倾向是只开放有限 DSL，不允许任意代码执行；复杂逻辑通过受控插件实现。

### 16. 你是如何解决大模型幻觉的问题？

“解决”这个词要谨慎，大模型幻觉不能被彻底消除，只能降低并监控。方法包括：限定模型回答范围、检索并要求引用来源、结构化输出、工具查询真实状态、规则和程序校验、关键结果二次审核、低置信度转人工，以及对事实型/流程型/代码型任务分别建立评测集。

还要区分事实幻觉、工具参数幻觉、计划幻觉和完成状态幻觉。比如 Agent 声称文件已生成，但真正的校验应该是检查文件是否存在、能否打开、内容是否满足验收标准。评估时记录准确率、引用命中率、任务成功率、误操作率和人工介入率，而不是只看语言是否流畅。

### 17. 反问

可以准备 2～3 个与岗位相关的问题：

1. 团队当前更关注 Agent 的效果、稳定性、成本还是业务转化？
2. 这个岗位负责的是模型能力、Harness/平台能力，还是具体业务 Agent？边界如何划分？
3. 目前线上最棘手的失败类型是什么，团队如何做评测和 Badcase 闭环？

## 三、面试后自查清单

- 我能否画出任务从请求到恢复的状态流？
- 我是否能解释一次重试为什么安全，或者为什么必须人工确认？
- 我说的指标、组件和负责范围是否都有真实依据？
- 我是否把“模型建议”与“系统最终事实”区分开？
- 对不记得的内部实现，我是否明确说了不确定，而不是编造？
