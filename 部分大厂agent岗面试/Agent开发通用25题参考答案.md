# Agent 开发通用 25 题：问题与参考答案

> 来源：用户提供的 Agent 开发面试题整理，共 25 题，全部为技术题，覆盖五块：Agent 基本设计、工具调用、上下文与记忆、RAG 与 Agent、效果与上线。回答风格保持“先给结论，再给机制、边界和例子”。

## 一、Agent 基本设计

### Q1. ReAct 和 Plan-and-Execute 差在哪？实际项目为什么选这个不选那个？

ReAct 是走一步看一步：每轮“思考 → 行动 → 观察”，下一步完全基于最新观察重新决策。灵活、纠偏快，适合反馈密集的探索型任务（调试、搜索）；缺点是缺乏全局视野，长任务容易绕路，步数和成本不可控。

Plan-and-Execute 是先规划再执行：Planner 产出完整计划，Executor 逐步执行，必要时 Replanner 修正。长任务有全局结构、计划可审计、独立步骤可并行；缺点是计划可能过时，初期规划错误会向下游传导，且多一次规划开销。

选型看任务路径的可预判程度：步骤可预先分解且相对稳定选 Plan-and-Execute，开放探索、每步结果决定下一步选 ReAct。实践中常混合：Planner 粗粒度规划，执行阶段用 ReAct，检查点上判断是否需要重规划。

### Q2. Agent 从接问题到调工具再到出结果，中间具体走了哪几步？

完整链路五段：①输入处理——校验与澄清用户输入，组装系统提示、工具定义、历史状态；②规划——模型决定第一步动作（ReAct 中内化在每轮决策里）；③执行循环——模型产出思考与工具调用，网关做参数校验、权限校验、超时重试，执行工具，把结构化结果回填上下文，回到模型继续决策；④终止——满足完成条件，或触发最大步数/预算护栏后强制收尾；⑤后处理——程序化验收（测试、字段、引用校验），格式化输出，落状态与记忆，记录全链路 trace。

关键点在③④：每一步工具调用都要过校验和鉴权，不是模型说什么就执行什么；终止不能只信模型的“我做完了”，要有程序化验收。

### Q3. 怎么判断该继续调工具，还是直接收尾给答案？

两层机制。模型层：在提示里明确定义完成条件和终止信号，要求模型结构化输出（如 `final_answer` 或 `status=done`），并在收尾前列出“已完成什么、证据是什么、还有什么没解决”，逼它自查而不是凭感觉宣布完成。程序层：用可验证的验收标准判定——测试是否通过、必填字段是否齐全、引用是否存在、任务目标是否达成，不达标就带着缺失项回炉。

护栏兜底：最大步数、token/费用预算、连续重复动作检测，触发后强制收尾或转人工，避免无限循环烧钱。方向反过来也要防：信息明显不足时（缺参数、缺文件），先补齐再收尾，不产出没根据的答案。

### Q4. 多轮对话的 State 怎么存？哪些信息该放进当前上下文？

State 分层存：会话级（消息历史、会话 id）、任务级（当前计划、todo、中间结果、已做决策）、用户级（跨会话偏好与事实）。实现上通常是 messages 数组 + 结构化状态对象（JSON）+ 外部存储（DB/文件）三层，每步持久化以便崩溃恢复和断点续跑。

进当前上下文的判据是“这一轮决策需不需要它”：必进——系统提示与约束、当前任务目标和验收标准、近期消息窗口、关键结论与决策的摘要、本步骤依赖的工具结果；不进——完整历史原文、大体积工具原始输出、无关会话内容。大结果外置到文件或 DB，上下文只留引用（路径/id），需要时再取。核心是 token 预算意识：上下文是稀缺资源，按决策相关性分配。

### Q5. 单 Agent 调多个工具，和 Multi-Agent 协作，实际用起来区别在哪？

单 Agent + 多工具：一个上下文统一决策，状态天然一致、调试简单、成本低；问题是上下文随任务膨胀，工具一多（超过二三十个）选择准确率明显下降，不同子任务的职责和 prompt 挤在一起互相干扰。

Multi-Agent：按职责拆成独立 Agent（规划、执行、评审、检索），各自有独立上下文和专属工具集，可以并行、可以隔离探索（子代理跑一堆尝试只回收结论，不污染主上下文）、可以给不同 Agent 配不同模型；代价是通信开销、状态同步、错误传播链条变长、成本成倍增长。

实用判据：默认单 Agent；当上下文装不下、任务可并行、职责存在冲突（例如“写代码”和“审代码”必须隔离）时才拆多 Agent。拆分后必须有明确的输出契约和汇总机制，否则协调成本会吃掉收益。

### Q6. 碰到需要人工确认的操作，Human-in-the-Loop 怎么设计才不卡流程？

按风险分级执行：只读和低风险操作自动跑，写操作确认，高危操作（删除、资金、外发）强确认，阈值可配置。不卡流程的关键在减少确认次数而不是取消确认：同类操作批量确认一次；提供会话级预授权（“本次任务内允许执行 X 类操作”，带上限和有效期）；确认请求异步挂起，Agent 等待期间不阻塞其他任务，超时默认拒绝或降级。

确认交互本身要高效：展示将执行什么、关键参数、影响范围，让用户 10 秒能做决定，并支持“改个参数再确认”而不是只有同意/拒绝。所有确认、授权、超时行为进审计日志。

## 二、工具调用

### Q7. Function Calling 到底解决了啥？为啥不让模型直接吐 JSON？

直接吐 JSON 只解决了“输出结构化”这一层，Function Calling 是一整套协议：工具发现（模型从注册的工具列表里知道有哪些工具、各自干什么）、调用规范（结构化参数，运行时可按 Schema 校验）、闭环回传（call_id 把调用和结果对齐，支持并行调用）、职责解耦（模型只“提议”调用，执行权始终在运行时手里，校验、鉴权、审计都在网关层做）。

自己解析 JSON 要重复造这些轮子：格式错误没有标准处理路径、多工具并行没有 ID 对齐、流式增量解析麻烦、错误回传没有统一格式。本质区别是：Function Calling 把“模型提议动作”变成了可靠接口，模型与执行环境之间有了受控边界。

### Q8. 工具描述和参数 Schema 怎么写，模型才不容易选错？

工具名用动词+宾语，语义自明；描述写四件事：什么时候用、什么时候不该用、前置条件、返回内容和副作用。参数字段名自解释，写清类型、单位、格式约定（时间格式、路径是相对还是绝对）、必填与默认值，枚举值列全。

减少误选的关键动作：在相似工具的描述里互相说明区别（“全文模糊搜索，与精确查找 X 的 `search_exact` 相比适用于…”）；用一两个调用示例锚定用法；控制同屏工具数量，场景化动态加载（当前阶段只暴露相关工具组）。最重要的一条：描述必须与实际行为一致，描述夸大或过时是模型选错的最大来源，工具行为变了描述必须跟着改。

### Q9. 两个工具都能干同一件事，Agent 怎么决定调哪个？

理想情况在工具设计层消歧：两个工具应该有清晰的适用边界（粒度、成本、精确度差异），并把边界写进描述——如果模型经常选错，先怀疑工具职责重叠，重构工具边界比在提示里加规则有效。

模型层依据三个信号选：语义匹配度（哪个更贴合当前子任务）、参数可得性（哪个工具需要的参数现在已经拿到）、描述里的适用条件。工程层兜底：设置优先级或路由规则，主工具失败自动降级到备用工具；上线后按工具分桶统计调用成功率和被纠错率，用数据决定合并、拆分或下线。

### Q10. 工具报错、缺参数或者超时，是直接重试还是换条路？

先分类再决定，一律重试是错的：

- 参数缺失或校验失败：不重试，把具体校验错误结构化回传给模型，让它补参后重新调用；
- 瞬时错误（网络抖动、限流 429/503）：有限次数重试，指数退避加 jitter；
- 资源不存在、权限不足：重试无意义，直接回传原因，模型换路径或向用户澄清；
- 超时：区分工具慢还是挂了——慢任务改异步（返回任务 id 轮询），确认挂了走降级（备用工具、缓存结果、部分结果先行）。

硬约束：重试必须有上限；写操作必须幂等（幂等键）防止重复执行；每次失败与处置都进 trace，失败模式攒起来反哺工具设计。

### Q11. 涉及用户权限、敏感操作，怎么防止 Agent 乱调工具？

核心原则：权限在运行时强制校验，不指望 prompt 约束模型。工具网关按用户身份做鉴权——角色映射到工具白名单和数据范围，模型提议的每次调用都要过这道闸。分级执行：读操作自动，写操作确认，高危操作二次验证；参数层再加白名单（数据库用只读账号、文件访问限定目录、金额设上限）。

隔离手段：高风险工具跑在沙箱里，使用短 TTL 的最小权限临时凭证。注入防护要单独注意：工具返回的内容（网页、文件）可能携带恶意指令，来自工具结果的内容不能触发权限提升，模型基于它的输出仍要走正常授权。最后全量审计：谁、在什么会话、调了什么、参数是什么，可回放可追责。

## 三、上下文和记忆

### Q12. 短期记忆和长期记忆分别解决什么？项目里都怎么存？

短期（工作）记忆解决“本轮对话内”的连贯：当前消息历史、任务计划、todo、工具中间结果。存 messages 数组加结构化状态对象，放内存或 Redis，随会话存活，结束归档或丢弃。

长期记忆解决“下次还记得”：跨会话的用户偏好、确认过的事实、重要决策。存分层：结构化事实进 DB（带 id、来源、时间、置信度、作用域），语义内容进向量库；原始证据保留在对象存储里可回查。写入侧要有门禁：LLM 判断“值不值得跨会话保留”、去重合并、敏感信息过滤；读取侧按当前任务召回，不是全量注入。一句话判据：临时指令不进长期记忆，可从业务系统实时查到的状态也不进——那该查询，不该记忆。

### Q13. 聊天记录越堆越长，上下文塞不下了怎么办？

手段按顺序叠加：①工具结果瘦身——限长、分页、只回传任务需要的字段；②外置记忆——大结果写文件/DB，上下文只留路径或 id，用时再取；③滚动摘要（compaction）——旧历史压成结构化摘要（任务目标、已完成、关键决策、待办），近几轮保留原文；④子代理隔离——探索性工作交给子代理，主线只收结论；⑤RAG 化历史——老消息向量化，按当前问题召回相关片段而不是全量携带。

设计要点：压缩不能丢任务目标、已确认的结论和约束条件，这三样丢了任务就跑偏；摘要时机选在接近窗口上限或任务阶段切换时，一次摘要等于缓存全失效，频率也是成本。

### Q14. 为什么有时候做历史消息摘要，而不是一直保留完整对话？

三个原因。成本与延迟：token 随轮次线性增长，输入越长每轮都贵、首 token 越慢；注意力衰减：长上下文里模型对中部信息的利用率明显下降（lost in the middle），老信息放着不等于用得上；信息密度：对话里大量寒暄、重复、试错过程对后续决策无价值，压成“结论 + 决策 + 待办”的摘要对模型更好用。

摘要有丢细节的风险，所以配套做法是分家：叙事性的过程交给摘要，事实性的关键信息（用户偏好、确认过的参数、重要数字）单独结构化保存，不依赖摘要保留。触发时机通常是接近窗口上限或阶段切换需要 handoff 时。

### Q15. 长期记忆用向量库，什么内容值得存？怎么别召回一堆没用的？

值得存的：用户明确表达的稳定偏好、用户确认过的事实、重要决策及其原因、反复出现的工作模式。不该存的：一次性临时指令、可实时查询的业务状态（查库存、查订单该调接口）、敏感个人信息（合规红线）。

防召回污染主要在写入侧：写入前 LLM 抽取并判断价值，规范化表述，与已有记忆做相似度去重（相似就更新版本而不是新增一条），打上作用域、时间、置信度标签。召回侧：混合检索（向量 + 关键词 + 标签过滤），设相似度阈值和 Top-K 上限，召回后重排，按当前任务的作用域过滤。治理兜底：记忆带 TTL 可过期，用户可查看和删除自己的记忆，线上监控误召回和漏召回率。

## 四、RAG 和 Agent

### Q16. Agent+RAG 跟普通 RAG 问答，最大的区别是什么？

普通 RAG 是固定流水线：查询 → 检索一次 → 拼接 → 生成，检索是前置步骤，一次定输赢。Agent+RAG 把检索变成模型手里的工具，检索本身变成动态决策：查不查（简单问题不必查）、查什么（查询改写、把复杂问题拆成多个子查询）、查几轮（结果不够换关键词再查，多跳问题递进检索）、信不信（多个来源交叉验证）、要不要配合其他工具（检索后计算、查表）。

本质区别一句话：普通 RAG 里模型只消费检索结果，Agent 里模型对检索过程负责。换来的是能处理多跳问题、模糊查询和检索失败的恢复；代价是延迟和成本上升，需要最大检索轮数等护栏防打转。

### Q17. 什么时候走向量检索，什么时候关键词检索更合适？

向量检索赢在语义匹配：同义改写、口语化表述、跨语言（“怎么上线”能召回“部署流程”），适合自然语言问题和表述不精确的查询。关键词（BM25）赢在精确匹配：专有名词、产品型号、代码符号、错误码、人名 ID——这些高区分度的 token 向量容易糊，BM25 反而稳。

工程默认答案是混合检索：BM25 与向量并行召回，RRF 融合排序，再用元数据过滤收窄（时间、类目、权限）。只准选一个时看查询形态：含明确术语和编号走关键词，自然语言描述走向量。

### Q18. 检索结果不靠谱，先查哪块？切片、Embedding、Top-K 还是 Rerank？

先区分两类病灶：该召回的没进候选（漏检），还是进了候选排不上来（排序差）。判别方法是看 bad case 的 gold 片段处于链路哪一层，用标注的评测集量化每段指标：

- **漏检**往下查：切片是否破坏语义（表格被拦腰切断、上下文断裂）——看命中的切片是否完整可用；Embedding 对领域术语的表征质量——用固定评测集测 Recall@k，必要时领域内微调 embedding；查询本身不行——加查询改写；Top-K 太小——调大 K 或上混合检索；
- **排错**查 rerank：gold 在候选里但排不进前列，加或换 reranker；
- 两头都对还不行：内容根本不在库里，是数据源和更新管道的问题。

关键是别靠感觉调参，切片、召回、排序各自要有量化指标，改一处测一轮。

### Q19. 模型回答里的知识来源，怎么做可追溯？

链路上每一步都要留痕：切片入库时绑定元数据（文档 id、标题、页码/章节、url、版本、更新时间）；检索结果带元数据进上下文；生成时要求输出引用编号，答案与引用片段绑定。

输出侧：引用以可点击的来源列表展示，用户能点开核对原文；没有依据的论断要么标注“未在资料中找到”要么拒答。验证侧做程序化抽查：引用是否真实存在、答案句子能否在引用片段中找到依据（规则匹配或 NLI 模型自动核验）。trace 里记录“检索了什么、命中了什么、最终引用了什么”，bad case 可以完整回放。

## 五、效果与上线

### Q20. 怎么判断一个 Agent 好不好？除了“看着还行”，还有哪些硬指标？

分五组硬指标：

- **任务级**：任务完成率/成功率（程序判定优先，人工判定要有标注规范）、端到端准确率；
- **过程级**：工具调用成功率、参数合法率、平均/最大步数、检索 Recall@k、引用准确率；
- **效率成本**：P50/P95 延迟、每任务 token 成本、每任务工具调用次数；
- **稳定性**：同一任务多次运行的一致率、失败后自动恢复率；
- **安全**：越权操作拦截率、敏感内容漏检率。

落地前提是先建评测集：正常用例 + 边界用例 + 对抗用例，固定版本、固定判分脚本，每次改动跑回归。“看着还行”的 Demo 评测和这套指标的差距，就是上线风险的差距。

### Q21. 工具调用成功率怎么统计？任务完成率又怎么算？

工具调用成功率：分母是被执行的工具调用数（模型提议但被权限拦截的不算执行，单独统计），分子是返回预期结果的调用数；按工具分桶，并区分“执行成功”和“结果有效”——HTTP 200 但返回空数据对任务没用，要分开算。

任务完成率：先定义“完成”。能程序判定的用程序判定（测试通过、必填字段齐全、结果可验证）；不能的用判分模型打分，加人工抽检标定判分模型的准确率。分母是进入执行的任务数，同时区分失败原因：任务失败、超时、用户中途放弃要分开，因为优化手段完全不同。两个指标都要写清统计口径，口径不同数字没有可比性。

### Q22. Agent 响应很慢，一般从哪些地方开始排查？

先分段计时打点再优化：输入处理、检索/工具执行、每轮 LLM 调用、后处理各记耗时，看分布找大头。常见原因按频率排：LLM 输出太长（限 max_tokens、要求简洁、流式输出改善观感）；步数太多（ReAct 绕路——给计划、缓存中间结果、合并工具）；每轮上下文过长（压缩历史、外置大结果，输入长直接影响首 token 延迟）；工具慢（并行化独立调用、加超时、结果缓存）；检索慢（索引配置、向量库参数）；没开流式（真实耗时不变但用户观感差数倍）。

优化顺序：先流式改善体验，再针对打点出的最大耗时项做真实优化，改一项测一项。

### Q23. Token 烧得太快，你会从哪些环节压成本？

先建成本归因：按任务、环节、用户统计 token 消耗，找大头再动手。输入侧通常占大头：压缩历史、工具结果外置、只注入决策需要的内容、精简重复的 prompt 段落；同时做前缀稳定设计提高缓存命中率，命中部分成本降一个量级。输出侧：限制 max_tokens、要求简洁和结构化输出、避免重复生成。

策略侧：模型分级路由——意图识别、分类、简单抽取用小模型，复杂规划和生成才用大模型；减少无效轮数（一次给全上下文，避免模型反复补查）；相同查询走结果缓存。架构侧：能用 Workflow 固定流程的不上自主 ReAct，步数本身就是钱。

### Q24. 线上出 Bad Case，怎么定位是 Prompt、模型、工具还是 RAG 的问题？

前提是有完整 trace：每步的 prompt、模型原始输出、工具调用与返回、检索命中的切片都落盘，bad case 能回放。定位用控制变量：

1. 先看检索：gold 内容在不在命中的候选里？不在 → RAG 问题（回到 Q18 查切片/embedding/Top-K）；
2. 检索命中了但答案错，把 gold 片段人工放进 prompt 重跑：能答对 → 上下文组装或查询改写问题（Prompt/RAG 交界）；还答不对 → 看下一步；
3. 检查工具链路：参数对不对、返回对不对、模型有没有用错工具返回 → 工具定义/Schema 问题；
4. 信息都给对了还答错 → 模型能力问题（换更强模型对比验证）或 Prompt 任务描述不清（换表述对比验证）。

修复后把 case 进评测集防回归，同类 case 批量归因——单点修复前先确认是共性还是个例。

### Q25. Demo 准备真上线，还要补啥？日志、监控、重试、权限、限流这些怎么落地？

按六块补齐：

- **可观测**：request id 贯穿全链路的结构化日志，记录每步 prompt、工具调用、检索命中、token 消耗，敏感字段脱敏；大盘监控成功率、P95 延迟、成本、错误率，设阈值告警；
- **稳定性**：超时与有限重试（指数退避）、降级路径、写操作幂等、任务断点恢复；
- **限流与预算**：用户级和全局级的 QPS/并发限制，token/费用预算与超限熔断，防止异常任务烧穿成本；
- **权限与安全**：工具网关鉴权、敏感操作人工确认、审计日志、内容安全过滤、注入防护；
- **发布机制**：评测集回归通过才发布，灰度放量、A/B 对比、一键回滚，配置和模型版本支持热更新；
- **数据闭环**：用户反馈入口，bad case 收集 → 归因 → 进评测集，评测集驱动迭代。

Demo 和上线的差距不在功能，在于失败是常态：上面每一块都是在为“必然会出错”做准备。
